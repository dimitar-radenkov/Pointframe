## Desktop testing tools

### Desktop-testing driver and policy

- The opt-in desktop-testing driver registers its policy-gated observation and mutation MCP tools and routes physical input and UIA actions through a supervised MCP worker. Owned-key release is synchronous: the worker is attempted first, then the parent-side `DesktopControlGuard` fallback is used when the worker or pipe is unavailable. The native input adapter records only successfully injected keys that were not already down, so fallback release cannot release user-owned keys; failed native release is reported rather than fabricated as success. The tool layer must route every mutation through `IDesktopActionCoordinator` and the worker-backed input/UIA services; preflight failures must produce no input and uncertain dispatch must not be replayed. Do not claim Gate A, B, or C evidence from headless contract tests. UI Automation inspection runs in the worker too, reached through the `uia.inspect` operation and surfaced to the parent by `WorkerUiObservationProvider`. The parent must not construct a UI Automation backend of its own: creating FlaUI's `UIA3Automation` initializes COM inside whichever process creates it, and doing that in the process serving the MCP protocol made unrelated tools hang intermittently. At startup the parent sends `uia.ping`, which reads a desktop-root property on the worker's MTA executor; it abandons a worker that does not answer within five seconds and tries at most three workers before allowing the request to fail. This moves first-call UIA initialization ahead of the first observation. Observation is registered to the worker in `DesktopTestingServiceRegistration`; the parent's backend-less `WindowsUiAutomationProvider` must not serve observations, because it reports `ProviderUnavailable` with zero elements, so no `element_ref` or `window_ref` would be minted for `desktop_invoke`, `desktop_focus_window`, or `desktop_check_ui` to address.
- `desktop_invoke` resolves its element from the newest unexpired observation for the session process. With positive bounds and a valid same-process window reference, it foregrounds that window, releases owned input, then physically clicks the bounds center through the worker's normal input preflight, which checks that the point is on-screen and hit-tests to the target window; the response says `method: "click"`. If focus fails but the app process is already foreground, it skips focusing and allows the hit-test to land on any visible top-level window in that process, which supports owned popup menus. This path still releases owned input and requires the point to pass click preflight. If geometry is unavailable/off-screen or focus/click preflight rejects the target, it uses the UIA Invoke pattern or Toggle fallback and reports `method: "pattern"`. Native dispatch failures and uncertain worker failures are not replayed as patterns. UIA invoke and toggle calls run on a background MTA thread and wait at most `DesktopTestingLimits.InvokeReturnMilliseconds`; a call that is still running is reported as delivered (`InvokePending`, successful dispatch) because the provider accepted it, and its thread finishes naturally after the app returns. A `verify run` invoke step treats that successful pending dispatch as passed with a delivered message; following steps determine whether the app completed the interaction.
- desktop_press_keys resolves its target like the other input tools. A physical press takes an optional windowRef (must be of the session's process, and a member of the observationRef when both are given) and/or observationRef (stale refs fail with StaleObservation; with no windowRef the first image's bounds anchor it and the process must be foreground). The window must be valid, visible, owned by the process and the foreground window; the observation is consumed, and neither ref is an error (TargetRequired). A globalHotkeyId call is unchanged: policy-approved, no target, nothing consumed. desktop_verify's PressKeys step passes the resolved windowRef.
- A UIA inspection root mints a `window-{process_ref}-{hwnd}` reference and every descendant inherits it, so `desktop_focus_window`, window-scoped locators, and window checks address one actual top-level window rather than only the target process. The tool accepts a reference only when its embedded process reference matches the active session, then resolves the hexadecimal HWND. The parent sends that native handle to the worker as an integer through `DesktopAutomationWorkerProtocol.SerializePayload`/`DeserializePayload`; default `System.Text.Json` does not support `nint`/`IntPtr` serialization.
- The interactive gate harness creates its policy through `Pointframe.AutomationTests/Support/DesktopGatePolicyFactory.cs` and must launch the MCP executable with `--desktop-testing --desktop-policy <absolute-policy-path>`. The factory uses ordinary empty Pointframe arguments and writes the temporary policy beneath the configured evidence directory; `DesktopGatePolicyFactoryTests` verifies enabled tool registration without launching Pointframe. This registration check is not a desktop gate: the real Gate A workflow still needs a generic notification-area interaction and normal target exit before it can safely launch the target, while Gates B and C require their external visual/file evidence.
- Real desktop acceptance requires explicit operator approval of the chosen Windows account or machine. A dedicated account or machine is preferred, but a personal account is permitted with informed consent because normal settings and desktop state may change; the driver cannot prove that the environment is safe. Isolation is not implemented through target data-root overrides.
- `desktop_check_ui` evaluates its condition against a fresh worker inspection of the session's target (`WorkerUiCheckSource`), and `processExited` is answered by `IDesktopProcessController` instead, because an exited target has no element tree to read. It was previously wired to a stub that reported `StateAvailable: false` for everything, so every check came back inconclusive and no action tool's reported success could be contradicted by anything. The tool takes a flat condition (`kind` plus `automationId`/`role`+`name`, optional `windowRef`, optional `expected`) rather than the engine's abstract `DesktopUiCheckCondition`, which carries no JSON polymorphism metadata and so could not be constructed by a client at all; `DesktopTestingMcpTools.BuildCondition` maps one to the other and rejects an unknown kind or a missing `expected`/`windowRef`. Toggle expectations normalize `true`/`checked`/`on` to `On`, `false`/`unchecked`/`off` to `Off`, and `indeterminate` to `Indeterminate`; selection accepts `selected` or `notSelected`. Unknown values are rejected before observation. State checks return `actualValue` when exactly one element was read, and the recorded report message includes it for failures; sensitive text is never returned. `IDesktopUiCheckService.CheckAsync` now takes the target `DesktopProcessIdentity`: the tool used to discard its `sessionId`, so nothing identified which application to inspect. A `textEquals` check never matches an element reporting `IsSensitive`, because a password field withholds its value by design.
- `desktop_end_test_session` closes the main window of a session-launched target, waits up to three seconds, then terminates its process tree if graceful close did not exit. The process controller retains the launched `Process` instance and validates its executable path, start time, and hash before stopping it; attached targets are never stopped. Ending an already closed or unknown session returns the typed `SessionNotFound` result.

### Desktop observation and synthesized input

- `desktop_observe_app` returns the captured pixels, not only metadata: it answers with a `CallToolResult` carrying one `ImageContentBlock` per requested rectangle (assembled by `DesktopObservationResultBuilder`), alongside the unchanged structured payload, and `includeImages: false` suppresses them. `DesktopObservationService` encodes each capture with `CapturePreviewImage.CreateDownscaledPng`, bounded by `DesktopTestingLimits.MaxImageLongestEdge` (1600). Consequently `DesktopImageReference.Width`/`Height` are the *preview* dimensions the model sees and deliberately differ from `DesktopBoundsPixels`; `DesktopCoordinateMapper` rescales between the two, and its non-transform overload delegates to the transform one so no caller can skip the rescale. An agent that treated a preview coordinate as a desktop offset would click short of its target by the downscale factor.
- UI snapshots cross the worker pipe as one message: `DesktopAutomationWorkerProtocol.MaxMessageBytes` is 8 MiB, and `HandleInspect` answers `SnapshotTooLarge` before a write could fail and close the pipe. The walk is breadth-first to `MaxUiAutomationDepth` 32 (Chromium content is deeper than 8) and `MaxUiAutomationElements` 200. An element's `Text` is its Value pattern, or for a text control its Name. `FlaUiWindowsUiAutomationBackend.Inspect` finds the target's windows with native `EnumWindows` rather than a desktop-wide `ByProcessId` search (see the lesson [A desktop-wide UI Automation search by process id hangs on any other window](../../../lessons.md#a-desktop-wide-ui-automation-search-by-process-id-hangs-on-any-other-window)) and traces entry, desktop-root acquisition, target-window enumeration, and walk completion so a future hang identifies its last completed step. `WindowsProcessController` removes `ELECTRON_RUN_AS_NODE` from the launched app's environment. Checked on PKHeX (WinForms), dnGrep (WPF), and an Electron app.
- OCR on an observation is selected with `includeOcr` plus a zero-based `ocrImageIndex` into `captureBoundsPixels`. The earlier `ocrImageRef` parameter was unusable: it had to name an image from the observation the same call creates, so any value a caller could supply resolved to `ImageNotFound`. `DesktopObservationService` runs OCR on the full-resolution bitmap it captured for that image, before disposing it, and stores only the text with the observation; `DesktopOcrObservationProvider` maps that result and never captures. Until 2026-10-19 the provider captured the screen a second time, so a dialog or covering window that appeared in between gave OCR text absent from the returned screenshot. OCR requested from a service built without an OCR engine reports `unavailable` with `OcrEngineUnavailable`, not `empty`.
- `desktop_audit_ui(sessionId, observationRef)` (`DesktopUiAuditService`, rules behind one interface; v0 has only `placeholder-text` v1 in `PlaceholderTextAuditRule`) audits a stored observation of the session and never re-captures, re-inspects UIA, or writes to the report. Its findings are advisory (`advisory: true`): they do not change checks, criteria, verdicts, or the signed report, because their precision is not measured yet (owner plan 2026-10-19: measure on labelled screens before any verdict use; Axe.Windows rules come next behind the same interface). It reads UIA `Name`/`Text` of non-sensitive elements, skips Edit/Document roles (user content) and counts the skips in `coverage`, and adds low-confidence OCR-only findings when the observation was made with OCR. An unknown or expired ref returns `StaleObservation` and another session's ref `ObservationNotInSession`; it never re-observes.
- Synthesized input has to imitate hardware, not merely be accepted by `SendInput`. Every absolute mouse event carries `MOUSEEVENTF_VIRTUALDESK`, without which Windows maps normalized coordinates onto the primary monitor only and every secondary-monitor click lands elsewhere. A drag presses, moves through at least `MinDragMoveSteps` interpolated points, then releases, tracking the held button in `_ownedMouseButtons` so a failure cannot leave it down; two disconnected clicks are not a drag. A scroll moves the cursor to its point first, because the wheel goes to the window under the cursor rather than the focused one. A click emits move, press and release as separate events with a hold between them. `desktop_enter_text` clicks to place the caret before typing (it previously validated the point and never clicked, so characters went wherever focus happened to be) and paces characters in chunks, because one large `SendInput` batch is accepted and reported as success while the target's message pump drops the tail.

### Desktop test reports, evidence, and scenarios

- The session report is written by the server, never by the agent: `desktop_check_ui` records every check it evaluated (oracle `server-uia`) through `IDesktopTestReportService.RecordCheck`, and the coordinator records every action. Requests rejected before evaluation (unknown session, invalid condition, unknown criterion) are not recorded, because they say nothing about the application. `DesktopTestReportService.ComputeVerdict` gives `failed` for any failed check or any dispatched action whose verification failed; `inconclusive` for zero checks, an inconclusive check, a `Partial`/`Unknown` dispatch, or a criterion that is not `passed`; `passed` otherwise. Actions with dispatch `NotStarted` never touched the app, so they are ignored and can be retried. Until 2026-10-03 the tool recorded nothing and a report without checks finalized as `passed`, so every session report claimed success.
- `desktop_start_test_session` takes optional `criteria` (plain-text goals written before the work). `DesktopTestReportService.NormalizeCriteria` trims and bounds them (`MaxCriteria`, `MaxCriterionLength`) before launch; `Initialize` numbers them `C1..Cn`, stores `CriteriaSha256`, and refuses to replace them, so the target cannot move after the work. `desktop_check_ui` takes `criterionId`; each criterion's verdict is `failed` if any of its checks failed, `passed` if one passed, else `inconclusive` or `uncovered`. `expectFailure` marks a check as a negative control: `DesktopTestingResponseMapper.MapNegativeControl` turns the verdict around (a rejected wrong expectation passes; one that holds fails with `NegativeControlMatched`) but keeps `matches` as the oracle's raw answer. With criteria declared, `ComputeVerdict` needs at least one passing negative control, because an oracle that matches everything would also pass every criterion; negative controls never cover a criterion and do not count as checking the work. Together these make proof-of-work reports: evidence the agent cannot author, judged against goals it cannot change, from an oracle shown to reject a wrong answer.
- Evidence images come from `DesktopEvidenceRecorder`, set up per session from the policy's `artifactRoot` and `evidencePolicy` (`None`, `Failures`, `All`), which the loader required before anything read them. It finds the target process's windows with `IWindowDiscoveryService` (DWM extended frame bounds) and renders each from its own contents through `IWindowContentCapture` (`WindowContentCapture`: `PrintWindow` with `PW_RENDERFULLCONTENT`, cropped to the visible frame), painted bottom-most first onto a transparent canvas. A screen copy would show any window covering the target, and did: a relaunched app opened behind the editor and the evidence showed the editor. Evidence therefore holds nothing the policy did not approve, and one window that cannot be rendered fails the whole image as `CaptureFailed`. It writes `<artifactRoot>/<sessionRef>/evidence/NNNN-<kind>.png` and returns path, SHA-256 and bounds. A failed capture comes back as `Error` (`NoVisibleWindow`, `CaptureFailed`) instead of throwing, so missing evidence shows in the report and never fails the step it documents. Checks are captured after evaluation. Actions are captured in `DesktopTestingMcpTools.AnnotateActionAsync` after dispatch; anything that was not dispatched is skipped, and `NeedsActionEvidence` skips a replayed action ID, which returns its stored result without a new report entry. `Program.cs` registers the recorder with an explicit factory.
- `DesktopTestReportService.FinalizeAsync` seals every report with `DesktopProofService.Seal`: a SHA-256 chain over a header, the actions, the checks, and a summary (verdict, criteria), whose root is signed with ECDSA P-256 by `IDesktopProofSigner`. It re-seals on each finalize, so a report fetched again also covers later steps. Every hash is computed over `DesktopProofService.CanonicalJson` (web defaults, enums as names), and `Verify` deserializes with the same options. A report that went through the MCP serializer (camelCase) or a PascalCase file therefore still recomputes to the same hashes; `ReportStillVerifiesAfterAJsonRoundTrip` pins this, so add any new report field to that test's sample. `CngDesktopProofSigner` keeps a non-exportable per-user CNG key (`Pointframe.DesktopProof.v1`) and opens it lazily, so a key store failure fails only report signing, not every desktop tool. The verifier treats the report as untrusted input and refuses evidence paths outside the evidence folder. A valid proof shows provenance only; `keyId` is what separates this machine's reports from a report re-signed by someone else.
- `desktop_get_test_report` writes a proof bundle to the report's signed `SessionDirectory` (`<artifactRoot>/<sessionRef>/`) on every call: `report.json` (serialized with `CanonicalJson`, so it verifies from disk), the `evidence/` folder (`DesktopProofBundle.EvidenceFolderName`, shared with the recorder), and `index.html` from `DesktopProofBundle.RenderIndex`. The HTML encodes every report value and says it is not itself signed. The coordinator records each action as `DesktopTestReportService.UnannotatedActionDescription`; the tool then calls `AnnotateAction` once with the operation name (`click`, `enter_text`, ...) and any evidence. `IsActionUnannotated` stops a replayed action ID, which returns its stored result, from being annotated or captured twice. `desktop_restart_app` runs through the coordinator too and is recorded as `restart_app`, with a screenshot of the relaunched app; before 2026-10-03 it bypassed the coordinator, so a report showed checks before and after a restart with no restart between them.
- `desktop_export_scenario` reads an ordered recording ledger held by `DesktopTestReportService` for the same lifetime as the signed report. The MCP boundary adds an export step only after a completed dispatch (invoke locators are unique in their observation; semantic text needs a portable locator; global hotkeys are excluded) and after every evaluated check. Coordinate actions, window-scoped checks, and elements without a stable locator remain indexed unsupported entries. The tool emits a scenario wrapper with frozen session criteria and writes `scenario-<id>.json` beside `report.json`; it does not add a step kind to spec v1.
- Every recorded check carries a `DesktopCheckSpec` (kind, locator, expected, timeout) inside the signed entry. `desktop_replay_checks` re-runs a signed `report.json` in a fresh session through the same `EvaluateAndRecordCheckAsync` path as `desktop_check_ui`. It refuses a report outside the policy's `artifactRoot` (the server reads the file for the caller), a report that fails `Verify`, and a session whose executable hash differs. It skips checks scoped to a `windowRef`, because window refs belong to one session, and returns `matched` or `differs` per check and per criterion. Replay starts from a fresh launch, so it confirms only state that survives a restart; unsaved typed text correctly replays as `failed`.
