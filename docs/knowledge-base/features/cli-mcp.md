## Standalone CLI and MCP automation

### Overview, entry points, and invariants

**Responsibility.** Provide agent-facing desktop capture and whole-monitor recording without starting the WPF tray application or creating overlay windows. Both hosts call the shared `Pointframe.Engine` services directly and require an interactive Windows desktop session.

**Entry points.**

| Host | Entry point | Transport |
|---|---|---|
| CLI | `Pointframe.Cli/Program.cs` and `CliApplication.RunAsync` | Process arguments and stdout/stderr |
| MCP server | `Pointframe.Mcp/Program.cs`, `PointframeMcpTools`, and `PointframeMcpResources` | MCP stdio |

**Invariants.**

- Capture and recording must run in the logged-in interactive desktop session; Windows services in session 0 cannot capture the user desktop.
- Monitor names passed to CLI/MCP commands are exact Windows device names, such as `\\.\DISPLAY1`.
- Both standalone hosts set `<ApplicationManifest>` to `Pointframe/app.manifest`, so both are PerMonitorV2 and report true physical pixels. `Pointframe.Cli` lacked it until 2026-09-19 and was DPI-unaware, reporting a 2560x1440 monitor at 150% scaling as 1707x960 with `DpiScale` 1 while `Pointframe.Mcp` reported it correctly. Both hosts document the same monitor-local physical-pixel contract, so a region computed from one must mean the same rectangle in the other.
- Artifact paths and metadata are produced through the shared direct services under `%LOCALAPPDATA%\Pointframe`; recording also emits an event sidecar without bitmap data, OCR text, clipboard contents, or prompts.
- `Pointframe.Engine` targets `net10.0-windows10.0.18362.0` and can call WinRT APIs (`Windows.Media.Ocr`, `Windows.Graphics.Imaging`) directly without a WPF dependency. `WindowsOcrEngineService` converts from GDI+ `System.Drawing.Bitmap` (what the capture pipeline produces) straight to `SoftwareBitmap`, unlike the main WPF app's `WindowsOcrService`, which converts from WPF's `BitmapSource`. Do not introduce a WPF dependency into `Pointframe.Engine` to reuse the WPF OCR service; keep the two implementations separate.

Spec-driven verification (`pointframe verify`, F-39) and its decisions D-007 to D-014 live in [Verify](verify.md); this area owns the MCP server and the `desktop_*` tools it drives, and the CLI host that verify extends.

- Lesson: A stdio client must drain the MCP server's stderr

### Packaging and install

- `pointframe mcp install --client vscode` downloads the stable MCPB and checksum aliases, verifies SHA-256 before extraction, installs into `%LOCALAPPDATA%\Programs\Pointframe.Mcp\<version>`, writes `install-state.json` atomically, and adds the server to VS Code's user `mcp.json`. `VsCodeMcpConfigurator` accepts JSON comments and trailing commas, preserves unrelated values, makes one durable `mcp.json.pointframe.bak`, and atomically replaces the live file; `--dry-run` validates the package and proposed configuration without persistent writes. `mcp status` checks the CLI-managed state and configured command path. `mcp doctor` launches the installed executable over stdio and requires a successful initialize plus the exact direct tool set; desktop-testing tools remain disabled. MCP-management commands branch before capture/OCR service construction and return a single-line `McpCommandResponse` with stable error codes. VS Code is deliberately the only managed client in the first slice; other clients retain the documented manual setup.

**Packaging and configuration.**

`Pointframe.Cli` is released as a self-contained, single-file `win-x64` ZIP with a SHA-256 checksum. `packaging/build-cli-package.ps1` publishes it and creates the versioned archive. It has no WPF application or .NET runtime prerequisite. Users install it with `winget install DimitarRadenkov.Pointframe.Cli`, or extract the ZIP and run `Pointframe.Cli.exe`. The winget package is a `zip` installer with a nested `portable` `Pointframe.Cli.exe` and `PortableCommandAlias: pointframe`: winget extracts the whole ZIP and links only the exe onto `PATH`, and the exe still finds `e_sqlite3.dll` beside it because it runs from the extracted folder through that link. The package uses the versioned ZIP, never the stable `Pointframe.Cli-win-x64.zip` alias, whose content changes every release. `winget/manifests/d/DimitarRadenkov/Pointframe/Cli/` keeps the first manifest, which must be submitted to `microsoft/winget-pkgs` by hand; `.github/workflows/winget-release.yml` updates the package on later releases. The CD build does not bundle ffmpeg in the CLI ZIP, so `record` needs ffmpeg on the machine. An optional `-FfmpegPath` parameter bundles `ffmpeg.exe` into the package (mirroring the MCP package builder) so `record` works out of the box; when omitted, `record` still works if `ffmpeg.exe` is on `PATH` or `POINTFRAME_FFMPEG_PATH` is set on the target machine.

`Pointframe.Mcp` is published self-contained for `win-x64`. `packaging/build-mcp-package.ps1` copies the published executable and a supplied `ffmpeg.exe` into a versioned legacy ZIP and MCPB bundle, alongside `packaging/assets/mcp-icon.png` bundled as `icon.png` and referenced from the manifest's `icon` field so Claude Desktop's Extensions UI shows a Pointframe icon instead of the default placeholder. `mcp-icon.png` is a dedicated 512x512 asset (recreating the brand glyph on a dark rounded-square badge); it is separate from the 32x32 `website/app-icon.png` favicon because MCPB/Claude Desktop recommend 128-256px+ icons. If the glyph or brand colors change, re-export a new `mcp-icon.png` at 512x512 and rebuild the package. The build also emits a SHA-256 checksum and MCP Registry `server.json` metadata pointing at the GitHub Release MCPB asset. The standalone package contains no WPF application. VS Code and other MCP clients launch the executable as a local stdio server.

CI publishes the CLI and MCP executables and runs `packaging/test-mcp-stdio.ps1`, which verifies, on the single-file publish that ships, disabled and explicitly enabled discovery against the exact delivered tool set (the direct tools when disabled, plus the desktop-testing tools when enabled, both read from `$expectedTools` and `$enabledExpectedTools`) without starting WPF. With desktop testing enabled it also calls `desktop_list_apps`, because listing tools never constructs the desktop services and the single-file build once failed every desktop tool there (an empty `Assembly.Location`). The MCP package also includes a disabled-by-default policy schema example. Release qualification (`scripts/release-impact.ps1`, `check-released-desktop.ps1 -BuildCandidate`, `check-release-channels.ps1`) is described in [Release qualification and versioning](../tooling.md#release-qualification-and-versioning). CD attaches the CLI ZIP/checksum plus the MCPB, checksum, and registry metadata to the versioned GitHub Release, then publishes that `server.json` to the official MCP Registry as `io.github.dimitar-radenkov/pointframe-mcp`, so every master release is also a registry version. The publish step must run after the release exists, because `server.json` pins the release MCPB URL and its SHA-256 (MCP clients verify the hash before installing; the registry only requires that the URL contains "mcp"). It downloads `mcp-publisher` pinned to v1.8.1, runs `validate`, then `login github-oidc`, which needs `id-token: write` on the CD job and no secret because the OIDC token proves ownership of the `io.github.dimitar-radenkov/*` namespace, then `publish`. A rejected publish fails the CD run but leaves the already-created GitHub Release in place. Both standalone hosts remain Windows-only and require an interactive desktop session for capture and recording.

**Agent onboarding check.** `pwsh scripts/test-agent-onboarding.ps1 -Client claude-code|codex|vscode|claude-desktop [-AgentSmoke]` proves the install path end to end. It downloads and checksum-verifies the latest release MCPB (or uses `-ServerPath`, `-BundlePath`, or `-UseLocalBuild`), validates `manifest.json`, registers the server in an isolated client configuration (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or a temp `mcp.json`; the real client configuration is never touched), repeats the registration and checks that unrelated servers and settings survive, then drives the resolved launch command over stdio (`initialize`, `tools/list`, `list_displays`, `list_windows`, `capture_window` with the handle from discovery) against `Pointframe.DesktopTestFixture --scroll-fixture`. It checks the artifact SHA-256 and byte length, that the inline image decodes, and that the fixture's 48x48 magenta `captureProofMagentaPatch` is present. The server runs with `SNIPPINGTOOL_AUTOMATION_DATA_DIRECTORY` pointing at the work directory, so it never opens the user's `pointframe.db` (a running Pointframe app holds its migration lock and the capture call would hang). Server stderr must be drained, because the server logs heavily and an unread pipe blocks it. Claude Code's `claude mcp add` refuses an existing name, so an update is `claude mcp remove` then `add`; `codex mcp add` is idempotent. Desktop steps hold the exclusive `pointframe-desktop.lock` file in the temp directory. `-AgentSmoke` runs one `claude -p` (Haiku, budget $0.30) that must name the magenta patch. `-SelfTest` runs the offline parts.

### CLI commands

- The CLI accepts `displays`, `capture --monitor <exact Windows device name> [--region <x,y,width,height>]`, `ocr --monitor <exact Windows device name> [--region <x,y,width,height>]`, `record --monitor <exact Windows device name> --seconds <positive integer> [--fps <1-60>] [--redact <x,y,width,height>]...`, `--help`/`-h`, or `--version`/`-v`. `--monitor`, `--region`, `--seconds`, `--fps`, `--redact`, and `--output` each accept a short alias (`-m`, `-g`, `-s`, `-f`, `-r`, `-o`); both forms are interchangeable and can be mixed within one invocation, and `capture`/`ocr` flags may appear in either order (`CliCommandParser.TryParseCaptureLikeCommand` loops over tokens rather than requiring a fixed position). Any long-form flag also accepts inline `--flag=value` syntax (e.g. `--monitor=\\.\DISPLAY1`); `CliCommandParser.ExpandInlineFlagValues` splits these into two tokens before the rest of parsing runs, so both `--flag value` and `--flag=value` are equivalent everywhere. `--help`/`-h`/`--version`/`-v` take priority over any other arguments present and are detected anywhere in the argument list (e.g. `record --monitor X --help` prints help instead of attempting to parse `record`), not just when passed alone. Invalid or incomplete commands print usage to standard error and return exit code 2; runtime failures return exit code 1. A runtime failure also writes a single-line `DirectCaptureResponse` with `Success: false` and an `Error` carrying a stable `Code` (`target_not_found`, `target_not_capturable`, `invalid_region`, `canceled`, or `capture_failed`, mapped from the exception type by `CliApplication.ToErrorCode`) to standard output, so a script parses standard output the same way on both paths; the human-readable `Pointframe CLI failed: ...` line stays on standard error for interactive use. `--help`/`--version` (and bare `help`/`version`) write plain text rather than JSON to standard output, always exit 0, and skip constructing/invoking the capture and recording services entirely. `record` is a single blocking command scoped to one CLI process: it starts the recording, waits for the requested duration (or an earlier Ctrl+C, handled as a graceful stop rather than a hard kill), stops the recording, and writes one combined JSON response containing both the started `Session` and the finished `Artifact`. There is no separate CLI `stop-recording` command because a CLI invocation has no state that persists across two separate process launches; use the MCP server's `start_recording`/`stop_recording` tools for a start-now/stop-later workflow instead. `Pointframe.Engine.DirectRecordingResponse` (`SchemaVersion`, `Success`, `Error`, `Session`, `Artifact`) is the shared JSON response DTO used by both the CLI `record` command and `DirectRecordingMcpService`, so the two hosts serialize recording results identically.
- `pointframe mcp serve [--project <dir>] [--mcp <file>]` is the command a committed agent config runs (`DesktopToolsApplication.ServeAsync`): it finds the project, loads the spec, requires an `app`, runs the same trust pipeline as `verify run` (`VerificationApplication.EnsureTrustedAsync`), refuses an app or working folder that is lexically inside the project but resolves through a symlink or junction to somewhere outside it (`PathContainment`, code `app_outside_project`), resolves the server like `verify run`, writes the policy with `VerificationApplication.WritePolicy` under `%LOCALAPPDATA%\Pointframe\verify\projects\<16 hex>` (`VerificationStore.ProjectKey`), and runs `Pointframe.Mcp.exe --desktop-testing --desktop-policy <file>` with inherited stdio (`InheritedStdioMcpServerHost`, no redirection) and its exit code. It writes nothing to stdout (the CLI hands the verification code `TextWriter.Null`); refusals are one stderr line with a stable code (`spec_untrusted`, `approver_unavailable`, `spec_invalid`, `no_app`, `app_outside_project`, `mcp_not_found`, `mcp_start_failed`) and exit 1. A spec `isolation` is honoured: the app gets a fresh data folder under the project's folder, deleted when the server exits (a per-session policy file when isolation is by argument); without `isolation` the app uses its normal data. `desktop_list_apps` now returns the policy's profiles (`apps`: id, executable file name, allowed action count) and `PolicyUnavailable` when the policy cannot be loaded.
- Every command that writes a file (`capture`, `ocr`, `capture-window`, `ocr-window`, `record`) accepts `--output <file>` (`-o`) naming the exact artifact path. `DirectCaptureService.ResolveArtifactPath` and the explicit-path branch of `DirectRecordingService.Start` create missing parent directories, reject an existing directory as the target, and otherwise fall back to the generated `yyyyMMdd-HHmmss-<id>` name under `%LOCALAPPDATA%\Pointframe`. The capture methods on `IDirectCaptureService` therefore take `string? outputPath` before the cancellation token, and `DirectRecordingRequest` has `OutputPath` alongside `OutputDirectory` (an explicit path wins). The MCP tools deliberately do not expose this: their artifact locations stay server-controlled, so pass `cancellationToken:` by name at those call sites.

### Capture, OCR, and recording

- `capture`/`ocr` (CLI) and `capture_monitor`/`read_text_from_monitor` (MCP) accept an optional region limited to a sub-rectangle of the monitor: `Pointframe.Engine.CaptureRegion` (`X`, `Y`, `Width`, `Height`) is expressed in monitor-local physical pixels relative to the monitor's own top-left corner, not the virtual desktop. `CaptureRegion.ResolveWithin(monitorBoundsPixels)` validates positive width/height and that the region is fully contained by the monitor, then offsets it into absolute physical-pixel `PixelBounds`; an out-of-bounds or non-positive region throws `ArgumentOutOfRangeException` rather than being clipped, which both hosts surface as a runtime failure (CLI exit code 1; MCP tool error). `DirectCaptureService.ResolveCapturedMonitor` is the single place that applies this: with no region it captures the whole monitor via `IDisplayCaptureEngine.CaptureMonitor`; with a region it resolves the display via `GetDisplays()` and calls `IDisplayCaptureEngine.Capture` directly with the resolved bounds, so `IDisplayCaptureEngine.CaptureMonitor` itself never gained a region parameter. `ImageArtifactMetadata`/`McpImageArtifactMetadata` report both `MonitorBoundsPixels` (the full monitor) and `CaptureBoundsPixels` (what was actually captured), so a region capture is distinguishable from a whole-monitor one in the JSON response and metadata sidecar. The MCP tools take `region` as a `{x, y, width, height}` object (`McpCaptureRegion`), not a comma string, for real JSON-schema validation.
- OCR (`ocr` CLI command / `read_text_from_monitor` MCP tool) captures the monitor like `capture` does (including the optional region), then runs `Windows.Media.Ocr.OcrEngine` against the captured bitmap via `IOcrEngineService`/`WindowsOcrEngineService`. The response always includes the PNG artifact; `RecognizedText` is `null` when no text is found or no OCR language pack is installed for the user's profile languages. `DirectCaptureService.CaptureMonitorInternalAsync` is the shared helper behind both `CaptureMonitorAsync` and `CaptureMonitorTextAsync` so save/hash/metadata-sidecar logic isn't duplicated. `WindowsOcrEngineService.RecognizeDetailedAsync` bounds the attempt at `RecognitionTimeout` (30 seconds) and returns `OcrRecognitionStatus.Failed` rather than waiting forever: the Windows OCR stack can wedge indefinitely, and neither `OcrEngine.TryCreateFromUserProfileLanguages` nor `RecognizeAsync` is reliably cancellable, so an unbounded wait takes the whole host process with it. The recognition task owns and disposes the `SoftwareBitmap` copy, because on the timeout path the caller returns while that task is still reading it.
- Recording requires an explicit redaction-region array. Regions are capture-local physical pixels and are applied before frames reach ffmpeg.

### MCP tools and resources

- Desktop-testing MCP tools are named with an explicit `desktop_` prefix (`desktop_click`, `desktop_drag`, `desktop_observe_app`, ...) set through `Name` on `[McpServerTool]`. Their bare action names collided with tools from other MCP servers connected to the same client, which leaves a caller choosing between two indistinguishable `click` tools. The direct tools keep their unprefixed names because they are the released, published surface. Every tool method and every caller-supplied parameter on both tool types carries a `[Description]`; `Pointframe.Tests/Mcp/McpToolSurfaceTests.cs` fails the build when one is missing, because an MCP client selects tools from those descriptions and an undescribed tool is effectively invisible.
- The MCP resource `pointframe://commands` lists the supported command identifiers. `PointframeCommandCatalog` derives these identifiers by reflecting over `[McpServerTool]`-decorated methods on `PointframeMcpTools` and `DesktopTestingMcpTools` (converting the method name to snake_case and stripping an `Async` suffix, or using an explicit `Name` on the attribute), so the resource cannot drift out of sync with the registered tools the way a hand-maintained list could.
- The MCP resource `pointframe://server-info` reports `SchemaVersion`, `Version` (the server's `FileVersionInfo.ProductVersion`, resolved via `Environment.ProcessPath` the same way the CLI resolves `--version`, since `Assembly.Location` is empty for single-file publishes), `DesktopTestingEnabled` (from `DesktopTestingHostOptions.Enabled`), and `Ffmpeg` availability (`Found`, `Path`, `Source` — `EnvironmentVariable`, `Bundled`, `Path`, or `NotFound`, from `FfmpegDirectVideoWriterFactory.GetAvailability()`). This lets an MCP client check server health/version and whether recording will work before calling `start_recording`, without starting a process or attempting a real recording.
- MCP tools list displays, capture a named monitor (or an optional sub-region) to a PNG artifact, read text from a named monitor (capture plus OCR, optionally scoped to a sub-region) via `read_text_from_monitor`, start a no-microphone MP4 recording, stop that recording with finalized artifact and sidecar metadata, and check whether a recording is currently active via `get_recording_status` (returns `IsRecording`, and when true, the active `Session` and `Elapsed` duration; `Session`/`Elapsed` are omitted when nothing is recording). `get_recording_status` is read-only and does not require a prior `start_recording` call to be safe to invoke.
- The four capture/OCR MCP tools (`capture_monitor`, `capture_window`, `read_text_from_monitor`, `read_text_from_window`) return a `ModelContextProtocol.Protocol.CallToolResult` rather than a typed `McpCaptureResponse`. `StructuredContent` still carries the full `McpCaptureResponse` JSON and a `TextContentBlock` repeats it, so existing structured-content readers are unaffected; unless the caller passes `includeImage: false`, an `ImageContentBlock` with the captured PNG is appended so a client that cannot read the server's filesystem can still see the screenshot. `McpCaptureResultBuilder.Build` assembles the result and `Pointframe.Engine.CapturePreviewImage.CreateDownscaledPng` produces the inline copy — it returns the on-disk bytes unchanged when the longest edge is already within `CapturePreviewImage.DefaultMaxLongestEdgePixels` (1600) and otherwise downscales with high-quality interpolation, preserving aspect ratio. The full-resolution PNG is always still written to disk (`%LOCALAPPDATA%\Pointframe\Screenshots` or the server-controlled path). Trade-off: because a directly-returned `CallToolResult` bypasses the SDK's return-type schema generation, these four tools do not set `UseStructuredContent` and do not advertise an output schema in `tools/list`; `list_displays`, `list_windows`, and the recording tools keep their typed returns and output schemas.

**Tool annotations.** Every MCP tool has a `Title` and explicit `ReadOnly` and `Destructive` hints, enforced by `McpTelemetryTests`. Listing, searching, reading, and capture tools are read-only (a capture saves a PNG in Pointframe's own library, which the hint treats as observing). Recording start and stop write a file: `readOnlyHint` false, `destructiveHint` false. Desktop tools that send input into another application (`desktop_click`, `desktop_press_keys`, `desktop_drag`, `desktop_enter_text`, `desktop_invoke`, `desktop_scroll`) and `desktop_end_test_session`, which stops the application it launched, are destructive.

### Embedded guide and discovery size

`scripts/measure-mcp-payloads.ps1` inventories MCP discovery schemas and tool responses into timestamped JSON, CSV, and Markdown under `artifacts/mcp-payloads/`. Its pinned rough token estimate is UTF-8 text bytes divided by four. The desktop-enabled run uses a per-run policy restricted to `Pointframe.DesktopTestFixture.exe` and an isolated catalog data directory. It calls every advertised tool through a dependency-ordered fixture workflow (displays, a fixture desktop session, captures, the catalog, a 1-2 s recording, then click, drag, scroll, text, hotkey, checks, report, replay, and restart), records text versus structured-content bytes, flags text blocks that duplicate the structured content, and fails on a tool with no measurement and no allowed skip, on any unexpected error, or on failed cleanup. A physical `desktop_press_keys` names the observed window (`windowRef` plus the consumed `observationRef`) and the workflow closes the replay fixture with a physical Alt+F4 sent that way, so no global hotkey is needed for it. After the default workflow it starts a second server with `POINTFRAME_MCP_COMPACT_TEXT=1`, runs the compact variants (image cap and JPEG, compact observation and report, summary text) through a real click and invoke driven only by compact refs, asserts that the summary still states the dispatch outcome and that the full proof stays on disk, and prints a default-versus-compact table (wire bytes, text bytes, estimated image tokens at width x height / 750). `-BaselinePayloads <payloads.json>` adds a tools/list comparison against an earlier run. Run `-SelfTest` for its offline measurement fixtures.

- The resource `pointframe://guides/verify-desktop-work` serves `Pointframe.Mcp/Guides/verify-desktop-work.md`, embedded in the server assembly, so each install serves the steps that match its own tools: how an outside agent verifies its own desktop work (criteria first, act, check per criterion, negative control, signed report). `Program.cs` sets `ServerInstructions`, which clients show the agent at connect time, to point at it whether or not desktop testing is enabled. `.gitignore` ignores `*.md`, so the guide folder has its own negation. `VerifyDesktopWorkGuideTests` fails if the guide names a tool that does not exist, if its policy sample no longer loads, or if a server-info property it names is serialized differently.
- `maxImageEdge` (64 to 1600), `imageFormat: jpeg`, compact details, compact text, and full discovery are opt-in. By default `tools/list` omits only each tool's `outputSchema`; names, titles, descriptions, input schemas, annotations, defaults, callable tools, and call results are unchanged. The server flag `--full-discovery` restores the pre-change tool list with output schemas. `--compact-text` or `POINTFRAME_MCP_COMPACT_TEXT=1` (`McpOutputOptions`, `McpCompactTextFilter` registered as a call-tool filter in `Program.cs`) swaps the text block of an allowlist of status-style tools for a one-line summary and leaves `structuredContent` alone; lists, searches, observations, and replay keep full text because a client that shows only text blocks would otherwise lose the data. `maxImageEdge` and `imageFormat: jpeg` on the four capture and OCR tools go through `McpImageOptions` (invalid values return `invalid_image_options` before any capture); `CapturePreviewImage.CreateDownscaledJpeg` encodes JPEG at quality 80. Measured on this repo's fixture, an 800 px cap cuts a whole-monitor capture by about 64 percent of wire bytes and 75 percent of image tokens, JPEG cuts a whole-monitor capture by about 60 percent of bytes but is larger than PNG for the flat fixture window, and downscaling a flat UI window to 800 px makes the PNG larger while still cutting image tokens, which is why neither is a default. `desktop_observe_app` takes `detail: compact` (`DesktopTestingResponseMapper.ToCompact` to `DesktopObservationResultBuilder.BuildCompact`: same refs and identity, bounds as `[x, y, w, h]`, nulls omitted, a shared top-level `windowRef`, names and text capped at 200 characters with the omitted count) and `maxImageEdge` (`DesktopObservationRequest.MaxImageLongestEdge`; the stored image width and height are the capped ones, so `DesktopCoordinateMapper` still maps clicks correctly). `desktop_get_test_report` takes `detail: compact` (`DesktopTestReportCompaction`), which drops per-item evidence, check specs, and the whole `proof` from the response only (`sessionDirectory` points to the full `report.json` to verify): `DesktopProofBundle.WriteAsync` always receives the full report, so the signed `report.json` on disk is complete. The action summary keeps dispatch, verification, and error, and for a `Partial` or `Unknown` dispatch tells the agent not to resend and to call `desktop_get_action_result` with the action id, which is what prevents a duplicate input after an uncertain result. Tests: `Pointframe.Tests/Mcp/McpCompactModesTests.cs`, `Pointframe.Tests/Mcp/McpToolSurfaceTests.cs`.

### Desktop-testing driver and policy

- The opt-in desktop-testing driver registers its policy-gated observation and mutation MCP tools and routes physical input and UIA actions through a supervised MCP worker. Owned-key release is synchronous: the worker is attempted first, then the parent-side `DesktopControlGuard` fallback is used when the worker or pipe is unavailable. The native input adapter records only successfully injected keys that were not already down, so fallback release cannot release user-owned keys; failed native release is reported rather than fabricated as success. The tool layer must route every mutation through `IDesktopActionCoordinator` and the worker-backed input/UIA services; preflight failures must produce no input and uncertain dispatch must not be replayed. Do not claim Gate A, B, or C evidence from headless contract tests. UI Automation inspection runs in the worker too, reached through the `uia.inspect` operation and surfaced to the parent by `WorkerUiObservationProvider`. The parent must not construct a UI Automation backend of its own: creating FlaUI's `UIA3Automation` initializes COM inside whichever process creates it, and doing that in the process serving the MCP protocol made unrelated tools hang intermittently. At startup the parent sends `uia.ping`, which reads a desktop-root property on the worker's MTA executor; it abandons a worker that does not answer within five seconds and tries at most three workers before allowing the request to fail. This moves first-call UIA initialization ahead of the first observation. Observation is registered to the worker in `DesktopTestingServiceRegistration`; the parent's backend-less `WindowsUiAutomationProvider` must not serve observations, because it reports `ProviderUnavailable` with zero elements, so no `element_ref` or `window_ref` would be minted for `desktop_invoke`, `desktop_focus_window`, or `desktop_check_ui` to address.
- `desktop_invoke` resolves its element from the newest unexpired observation for the session process. With positive bounds and a valid same-process window reference, it foregrounds that window, releases owned input, then physically clicks the bounds center through the worker's normal input preflight, which checks that the point is on-screen and hit-tests to the target window; the response says `method: "click"`. If focus fails but the app process is already foreground, it skips focusing and allows the hit-test to land on any visible top-level window in that process, which supports owned popup menus. This path still releases owned input and requires the point to pass click preflight. If geometry is unavailable/off-screen or focus/click preflight rejects the target, it uses the UIA Invoke pattern or Toggle fallback and reports `method: "pattern"`. Native dispatch failures and uncertain worker failures are not replayed as patterns. UIA invoke and toggle calls run on a background MTA thread and wait at most `DesktopTestingLimits.InvokeReturnMilliseconds`; a call that is still running is reported as delivered (`InvokePending`, successful dispatch) because the provider accepted it, and its thread finishes naturally after the app returns. A `verify run` invoke step treats that successful pending dispatch as passed with a delivered message; following steps determine whether the app completed the interaction.
- desktop_press_keys resolves its target like the other input tools. A physical press takes an optional windowRef (must be of the session's process, and a member of the observationRef when both are given) and/or observationRef (stale refs fail with StaleObservation; with no windowRef the first image's bounds anchor it and the process must be foreground). The window must be valid, visible, owned by the process and the foreground window; the observation is consumed, and neither ref is an error (TargetRequired). A globalHotkeyId call is unchanged: policy-approved, no target, nothing consumed. desktop_verify's PressKeys step passes the resolved windowRef.
- A UIA inspection root mints a `window-{process_ref}-{hwnd}` reference and every descendant inherits it, so `desktop_focus_window`, window-scoped locators, and window checks address one actual top-level window rather than only the target process. The tool accepts a reference only when its embedded process reference matches the active session, then resolves the hexadecimal HWND. The parent sends that native handle to the worker as an integer through `DesktopAutomationWorkerProtocol.SerializePayload`/`DeserializePayload`; default `System.Text.Json` does not support `nint`/`IntPtr` serialization.
- The interactive gate harness creates its policy through `Pointframe.AutomationTests/Support/DesktopGatePolicyFactory.cs` and must launch the MCP executable with `--desktop-testing --desktop-policy <absolute-policy-path>`. The factory uses ordinary empty Pointframe arguments and writes the temporary policy beneath the configured evidence directory; `DesktopGatePolicyFactoryTests` verifies enabled tool registration without launching Pointframe. This registration check is not a desktop gate: the real Gate A workflow still needs a generic notification-area interaction and normal target exit before it can safely launch the target, while Gates B and C require their external visual/file evidence.
- Real desktop acceptance requires explicit operator approval of the chosen Windows account or machine. A dedicated account or machine is preferred, but a personal account is permitted with informed consent because normal settings and desktop state may change; the driver cannot prove that the environment is safe. Isolation is not implemented through target data-root overrides.
- `desktop_check_ui` evaluates its condition against a fresh worker inspection of the session's target (`WorkerUiCheckSource`), and `processExited` is answered by `IDesktopProcessController` instead, because an exited target has no element tree to read. It was previously wired to a stub that reported `StateAvailable: false` for everything, so every check came back inconclusive and no action tool's reported success could be contradicted by anything. The tool takes a flat condition (`kind` plus `automationId`/`role`+`name`, optional `windowRef`, optional `expected`) rather than the engine's abstract `DesktopUiCheckCondition`, which carries no JSON polymorphism metadata and so could not be constructed by a client at all; `DesktopTestingMcpTools.BuildCondition` maps one to the other and rejects an unknown kind or a missing `expected`/`windowRef`. Toggle expectations normalize `true`/`checked`/`on` to `On`, `false`/`unchecked`/`off` to `Off`, and `indeterminate` to `Indeterminate`; selection accepts `selected` or `notSelected`. Unknown values are rejected before observation. State checks return `actualValue` when exactly one element was read, and the recorded report message includes it for failures; sensitive text is never returned. `IDesktopUiCheckService.CheckAsync` now takes the target `DesktopProcessIdentity`: the tool used to discard its `sessionId`, so nothing identified which application to inspect. A `textEquals` check never matches an element reporting `IsSensitive`, because a password field withholds its value by design.
- `desktop_end_test_session` closes the main window of a session-launched target, waits up to three seconds, then terminates its process tree if graceful close did not exit. The process controller retains the launched `Process` instance and validates its executable path, start time, and hash before stopping it; attached targets are never stopped. Ending an already closed or unknown session returns the typed `SessionNotFound` result.

### Desktop observation and synthesized input

- `desktop_observe_app` returns the captured pixels, not only metadata: it answers with a `CallToolResult` carrying one `ImageContentBlock` per requested rectangle (assembled by `DesktopObservationResultBuilder`), alongside the unchanged structured payload, and `includeImages: false` suppresses them. `DesktopObservationService` encodes each capture with `CapturePreviewImage.CreateDownscaledPng`, bounded by `DesktopTestingLimits.MaxImageLongestEdge` (1600). Consequently `DesktopImageReference.Width`/`Height` are the *preview* dimensions the model sees and deliberately differ from `DesktopBoundsPixels`; `DesktopCoordinateMapper` rescales between the two, and its non-transform overload delegates to the transform one so no caller can skip the rescale. An agent that treated a preview coordinate as a desktop offset would click short of its target by the downscale factor.
- UI snapshots cross the worker pipe as one message: `DesktopAutomationWorkerProtocol.MaxMessageBytes` is 8 MiB, and `HandleInspect` answers `SnapshotTooLarge` before a write could fail and close the pipe. The walk is breadth-first to `MaxUiAutomationDepth` 32 (Chromium content is deeper than 8) and `MaxUiAutomationElements` 200. An element's `Text` is its Value pattern, or for a text control its Name. `FlaUiWindowsUiAutomationBackend.Inspect` finds the target's windows with native `EnumWindows` rather than a desktop-wide `ByProcessId` search (see the lesson [A desktop-wide UI Automation search by process id hangs on any other window](../../../lessons.md#a-desktop-wide-ui-automation-search-by-process-id-hangs-on-any-other-window)) and traces entry, desktop-root acquisition, target-window enumeration, and walk completion so a future hang identifies its last completed step. `WindowsProcessController` removes `ELECTRON_RUN_AS_NODE` from the launched app's environment. Checked on PKHeX (WinForms), dnGrep (WPF), and an Electron app.
- OCR on an observation is selected with `includeOcr` plus a zero-based `ocrImageIndex` into `captureBoundsPixels`. The earlier `ocrImageRef` parameter was unusable: it had to name an image from the observation the same call creates, so any value a caller could supply resolved to `ImageNotFound`.
- Synthesized input has to imitate hardware, not merely be accepted by `SendInput`. Every absolute mouse event carries `MOUSEEVENTF_VIRTUALDESK`, without which Windows maps normalized coordinates onto the primary monitor only and every secondary-monitor click lands elsewhere. A drag presses, moves through at least `MinDragMoveSteps` interpolated points, then releases, tracking the held button in `_ownedMouseButtons` so a failure cannot leave it down; two disconnected clicks are not a drag. A scroll moves the cursor to its point first, because the wheel goes to the window under the cursor rather than the focused one. A click emits move, press and release as separate events with a hold between them. `desktop_enter_text` clicks to place the caret before typing (it previously validated the point and never clicked, so characters went wherever focus happened to be) and paces characters in chunks, because one large `SendInput` batch is accepted and reported as success while the target's message pump drops the tail.

### Desktop test reports, evidence, and scenarios

- The session report is written by the server, never by the agent: `desktop_check_ui` records every check it evaluated (oracle `server-uia`) through `IDesktopTestReportService.RecordCheck`, and the coordinator records every action. Requests rejected before evaluation (unknown session, invalid condition, unknown criterion) are not recorded, because they say nothing about the application. `DesktopTestReportService.ComputeVerdict` gives `failed` for any failed check or any dispatched action whose verification failed; `inconclusive` for zero checks, an inconclusive check, a `Partial`/`Unknown` dispatch, or a criterion that is not `passed`; `passed` otherwise. Actions with dispatch `NotStarted` never touched the app, so they are ignored and can be retried. Until 2026-10-03 the tool recorded nothing and a report without checks finalized as `passed`, so every session report claimed success.
- `desktop_start_test_session` takes optional `criteria` (plain-text goals written before the work). `DesktopTestReportService.NormalizeCriteria` trims and bounds them (`MaxCriteria`, `MaxCriterionLength`) before launch; `Initialize` numbers them `C1..Cn`, stores `CriteriaSha256`, and refuses to replace them, so the target cannot move after the work. `desktop_check_ui` takes `criterionId`; each criterion's verdict is `failed` if any of its checks failed, `passed` if one passed, else `inconclusive` or `uncovered`. `expectFailure` marks a check as a negative control: `DesktopTestingResponseMapper.MapNegativeControl` turns the verdict around (a rejected wrong expectation passes; one that holds fails with `NegativeControlMatched`) but keeps `matches` as the oracle's raw answer. With criteria declared, `ComputeVerdict` needs at least one passing negative control, because an oracle that matches everything would also pass every criterion; negative controls never cover a criterion and do not count as checking the work. Together these make proof-of-work reports: evidence the agent cannot author, judged against goals it cannot change, from an oracle shown to reject a wrong answer.
- Evidence images come from `DesktopEvidenceRecorder`, set up per session from the policy's `artifactRoot` and `evidencePolicy` (`None`, `Failures`, `All`), which the loader required before anything read them. It finds the target process's windows with `IWindowDiscoveryService` (DWM extended frame bounds) and renders each from its own contents through `IWindowContentCapture` (`WindowContentCapture`: `PrintWindow` with `PW_RENDERFULLCONTENT`, cropped to the visible frame), painted bottom-most first onto a transparent canvas. A screen copy would show any window covering the target, and did: a relaunched app opened behind the editor and the evidence showed the editor. Evidence therefore holds nothing the policy did not approve, and one window that cannot be rendered fails the whole image as `CaptureFailed`. It writes `<artifactRoot>/<sessionRef>/evidence/NNNN-<kind>.png` and returns path, SHA-256 and bounds. A failed capture comes back as `Error` (`NoVisibleWindow`, `CaptureFailed`) instead of throwing, so missing evidence shows in the report and never fails the step it documents. Checks are captured after evaluation. Actions are captured in `DesktopTestingMcpTools.AnnotateActionAsync` after dispatch; anything that was not dispatched is skipped, and `NeedsActionEvidence` skips a replayed action ID, which returns its stored result without a new report entry. `Program.cs` registers the recorder with an explicit factory.
- `DesktopTestReportService.FinalizeAsync` seals every report with `DesktopProofService.Seal`: a SHA-256 chain over a header, the actions, the checks, and a summary (verdict, criteria), whose root is signed with ECDSA P-256 by `IDesktopProofSigner`. It re-seals on each finalize, so a report fetched again also covers later steps. Every hash is computed over `DesktopProofService.CanonicalJson` (web defaults, enums as names), and `Verify` deserializes with the same options. A report that went through the MCP serializer (camelCase) or a PascalCase file therefore still recomputes to the same hashes; `ReportStillVerifiesAfterAJsonRoundTrip` pins this, so add any new report field to that test's sample. `CngDesktopProofSigner` keeps a non-exportable per-user CNG key (`Pointframe.DesktopProof.v1`) and opens it lazily, so a key store failure fails only report signing, not every desktop tool. The verifier treats the report as untrusted input and refuses evidence paths outside the evidence folder. A valid proof shows provenance only; `keyId` is what separates this machine's reports from a report re-signed by someone else.
- `desktop_get_test_report` writes a proof bundle to the report's signed `SessionDirectory` (`<artifactRoot>/<sessionRef>/`) on every call: `report.json` (serialized with `CanonicalJson`, so it verifies from disk), the `evidence/` folder (`DesktopProofBundle.EvidenceFolderName`, shared with the recorder), and `index.html` from `DesktopProofBundle.RenderIndex`. The HTML encodes every report value and says it is not itself signed. The coordinator records each action as `DesktopTestReportService.UnannotatedActionDescription`; the tool then calls `AnnotateAction` once with the operation name (`click`, `enter_text`, ...) and any evidence. `IsActionUnannotated` stops a replayed action ID, which returns its stored result, from being annotated or captured twice. `desktop_restart_app` runs through the coordinator too and is recorded as `restart_app`, with a screenshot of the relaunched app; before 2026-10-03 it bypassed the coordinator, so a report showed checks before and after a restart with no restart between them.
- `desktop_export_scenario` reads an ordered recording ledger held by `DesktopTestReportService` for the same lifetime as the signed report. The MCP boundary adds an export step only after a completed dispatch (invoke locators are unique in their observation; semantic text needs a portable locator; global hotkeys are excluded) and after every evaluated check. Coordinate actions, window-scoped checks, and elements without a stable locator remain indexed unsupported entries. The tool emits a scenario wrapper with frozen session criteria and writes `scenario-<id>.json` beside `report.json`; it does not add a step kind to spec v1.
- Every recorded check carries a `DesktopCheckSpec` (kind, locator, expected, timeout) inside the signed entry. `desktop_replay_checks` re-runs a signed `report.json` in a fresh session through the same `EvaluateAndRecordCheckAsync` path as `desktop_check_ui`. It refuses a report outside the policy's `artifactRoot` (the server reads the file for the caller), a report that fails `Verify`, and a session whose executable hash differs. It skips checks scoped to a `windowRef`, because window refs belong to one session, and returns `matched` or `differs` per check and per criterion. Replay starts from a fresh launch, so it confirms only state that survives a restart; unsaved typed text correctly replays as `failed`.

The directory validator treats every arg after the command as a path, so flags there are blocked; the `.cmd` keeps the flags out of `.mcp.json` while the bypass still lets Windows PowerShell 5.1 run the script under the default Restricted policy. One path from `${CLAUDE_PLUGIN_ROOT}`, no other variable or inline code. The `.cmd` must not echo (stdout is the JSON-RPC stream). The script reads `server.lock.json` (version, asset URL, SHA-256 of `Pointframe.Mcp-<version>-win-x64.mcpb`), downloads it over TLS 1.2 on a cache miss, refuses a hash mismatch, extracts to `%LOCALAPPDATA%\Pointframe\plugin-mcp\<version>\server\`, writes `.verified.json` (archive hash and `Pointframe.Mcp.exe` hash) and runs the exe with inherited stdio. Every start re-hashes the exe against `.verified.json`, so a cached start needs no network. It writes nothing to stdout (that is the JSON-RPC stream) and fails closed with a message on stderr.
- **Hashing uses .NET, not `Get-FileHash`.** A Windows PowerShell 5.1 child started from PowerShell 7 inherits its `PSModulePath` and then cannot find `Get-FileHash`; a cache check that threw was silently treated as a miss.
- **Pinning before verification.** Every release comes from a merged pull request. Run `pwsh scripts/merge-pr.ps1 -PinOnly -Worktree <path>` before `verify.ps1`; it updates and commits the pin locally, without pushing. Then verify the pinned tree, push, create the PR, and run `merge-pr.ps1 -Auto -Worktree`; Auto checks that the receipt matches the PR head and current tree; if a newer release landed meanwhile, it commits and pushes the pin itself and accepts the older receipt because only the pin files changed. No bot PR or `PLUGIN_PIN_TOKEN` is needed (a `GITHUB_TOKEN` PR would start no checks). `ci.yml` has `paths-ignore: plugin/**` on its `push` trigger (pull requests still run all checks), so a plugin-only merge runs no CI and cuts no release.
- **Rules enforced offline.** `scripts/check-agent-discovery.ps1` (`Test-ClaudePlugin`, with a mutation self-test on a copy of the plugin) checks the manifest fields and name pattern, README length and required disclosures, the lock schema and its agreement with `plugin.json`, the `.mcp.json` shape, stdout cleanliness of the start script, skill front matter, file types and sizes, `ci.yml`'s `paths-ignore`, `plugin-pin.yml` and the submission draft `packaging/directory-submissions/claude-plugin-directory.txt`.
- **Acceptance.** `pwsh scripts/test-agent-onboarding.ps1 -Client claude-plugin` copies the plugin, runs its `.mcp.json` command (the `.cmd`) with a temporary `LOCALAPPDATA` against the real pinned release (tampered hash and failed download fail closed with an empty stdout; then initialize, `tools/list`, `list_displays`, `list_windows`, `capture_window` on the fixture under the desktop lock; then an offline start from the cache). `-SelfTest` also runs the offline script behaviour against a stand-in server.
- **The recipe.** The fastest first proof needs no MCP client restart: install the CLI, `pointframe verify init --app <exe> --hooks none`, add one desktop scenario with selectors, then `pointframe verify run`, which starts its own server and approves standard commands by policy. The first `verify run` (or `verify task start`) installs the checksum-verified server when none is installed and no `--mcp` or `POINTFRAME_MCP_EXECUTABLE` names one, through the same installer that updates an older server (`McpPackageInstaller` serializes activation with a per-user named mutex keyed by the install root, and a move collision with an already valid install counts as success, so two first runs at once both get the server); a failed install reports `mcp_not_found` with the installer error, and the next step is `pointframe verify setup`. `mcp serve`, `verify setup` and `verify init --explore` never install through this path (serve must start fast and keep stdout clean; setup has its own install step). Interactive `desktop_*` tools come after `verify setup` writes the project's MCP config with a policy built from the trusted spec, so nobody hand-writes a policy. A selector `role` is the one-word UI Automation control type name (`ListItem`, `MenuItem`, `Edit`), compared without case.
- **Generating a `verify-<app>` skill.** `create-desktop-verification-skill` follows pstack's `create-verification-skill` shape for Windows desktop apps: interview the repo, write one journey as a spec scenario with a negative control, write `verify-<app>/SKILL.md` and a `features/` map (one file per feature with the H2s Sub-features, How to get to it (user POV), Driving it with Pointframe, Gotchas) that names scenario ids, then prove it once with `verify run` as the last step: the pass is tied to the working tree, so writing the skill files (or any doc) after it makes `verify status` report `fresh: false` (a baseline trial failed exactly so on 2026-10-16). Executable steps live only in the spec. `samples/verify/wpf/reference/skill/verify-wpf-sample` is the worked example; trials exclude `reference/`.
- **Desktop testing is off** in the plugin's own server, because the directory forbids `userConfig` variables in the command. The README points to `verify setup`; a user who runs the server without a spec registers the same script with `--desktop-testing --desktop-policy`, and the script passes extra arguments through.
- Lesson: The directory validator reads every MCP arg after the command as a path
- Lesson: A selector role is the one-word UI Automation control type name

## The MCP command list resource must name every registered tool

**Rule.** `PointframeMcpResources.GetCommands()` returns `PointframeCommandCatalog.Create(...)`, which reflects over the `[McpServerTool]` methods on `PointframeMcpTools` and `DesktopTestingMcpTools` and derives each tool's snake_case identifier from its method name (or an explicit `Name` on the attribute) instead of a hand-maintained string list. Adding, renaming, or removing a `[McpServerTool]` method automatically changes the resource's output, so the resource needs no hand-kept list. The same change must still update the known-good identifier sets in `Pointframe.Tests/Mcp/DesktopTestingToolContractTests.cs`, `$expectedTools` in `packaging/test-mcp-stdio.ps1`, and the tool lists in `README.md` and `docs/mcp-desktop-testing/README.md`, which `Pointframe.Tests/DocsSync/McpToolDocumentationTests.cs` checks. The desktop-testing tools set `Name` explicitly to carry their `desktop_` prefix; the direct tools rely on the convention.

**Why.** MCP clients that call the `pointframe://commands` resource before `tools/list` use it as a cheap capability check. Before 2026-09-08 the identifiers were a hardcoded array that nothing kept in sync automatically; a new tool method compiled and worked over MCP even if the resource still listed only the older commands, silently telling callers the new capability did not exist. Reflection over the attribute removes that failure mode entirely, at the cost of assuming the MCP SDK's default tool-naming convention (PascalCase method name, `Async` suffix stripped, converted to snake_case) unless a method sets an explicit `Name`.

**Enforced by.** `Pointframe.Tests/Mcp/DesktopTestingToolContractTests.cs` asserts the reflected `DirectTools`/`DesktopTestingTools` catalogs exactly match the known-good tool identifier sets, and `packaging/test-mcp-stdio.ps1`'s `$expectedTools` list independently checks the live `tools/list` response against the same identifiers. If the MCP SDK's naming convention ever changes, or a tool method needs a name the convention would get wrong, set `Name` explicitly on that method's `[McpServerTool]` attribute.

**Symptoms when violated.** A client that gates on `pointframe://commands` never offers a tool to the user or agent even though calling it directly still succeeds — this was possible before the reflection-based rewrite; the contract tests above now catch a mismatch at build time.
