## Standalone CLI and MCP automation

### Packaging and configuration

`scripts/check-released-desktop.ps1` is the coordinator's post-release acceptance check. Run it after every GitHub release, from an unlocked interactive Windows desktop, with `pwsh scripts/check-released-desktop.ps1 -Version <x.y.z>` (or omit `-Version` to select the latest release). It downloads the versioned CLI ZIP and MCPB with their SHA-256 files, validates both hashes using .NET, and tests the released MCP stdio surface with desktop testing enabled. It then stages and commits the Release desktop fixture in an isolated project, runs the released CLI's `verify run` against the released MCP server, and, when `desktop_export_scenario` is present, checks the released-server record/export and released-CLI add/run round trip. The optional `-SelfTest` tests hash matching and mismatch rejection, the generated v1 verification spec, and the `result.json` shape without network or desktop access.

The check holds `%TEMP%\pointframe-desktop.lock` for desktop work, refuses a locked Windows session, records each step's status, duration, and detail in `result.json`, and stops work-directory CLI/MCP processes during cleanup. If the released MCP server does not list `desktop_export_scenario`, that round-trip step is recorded as skipped because the capability is absent from that release.

- Lesson: Assembly.Location is empty in the released single-file server
- Lesson: A stdio client must drain the MCP server's stderr

`scripts/measure-mcp-payloads.ps1` inventories MCP discovery schemas and tool responses into timestamped JSON, CSV, and Markdown under `artifacts/mcp-payloads/`. Its pinned rough token estimate is UTF-8 text bytes divided by four. The desktop-enabled run uses a per-run policy restricted to `Pointframe.DesktopTestFixture.exe` and an isolated catalog data directory. It calls every advertised tool through a dependency-ordered fixture workflow (displays, a fixture desktop session, captures, the catalog, a 1-2 s recording, then click, drag, scroll, text, hotkey, checks, report, replay, and restart), records text versus structured-content bytes, flags text blocks that duplicate the structured content, and fails on a tool with no measurement and no allowed skip, on any unexpected error, or on failed cleanup. A physical `desktop_press_keys` names the observed window (`windowRef` plus the consumed `observationRef`) and the workflow closes the replay fixture with a physical Alt+F4 sent that way, so no global hotkey is needed for it. After the default workflow it starts a second server with `POINTFRAME_MCP_COMPACT_TEXT=1`, runs the compact variants (image cap and JPEG, compact observation and report, summary text) through a real click and invoke driven only by compact refs, asserts that the summary still states the dispatch outcome and that the full proof stays on disk, and prints a default-versus-compact table (wire bytes, text bytes, estimated image tokens at width x height / 750). `-BaselinePayloads <payloads.json>` adds a tools/list comparison against an earlier run. Run `-SelfTest` for its offline measurement fixtures.

**Responsibility.** Provide agent-facing desktop capture and whole-monitor recording without starting the WPF tray application or creating overlay windows. Both hosts call the shared `Pointframe.Engine` services directly and require an interactive Windows desktop session.

**Entry points.**

| Host | Entry point | Transport |
|---|---|---|
| CLI | `Pointframe.Cli/Program.cs` and `CliApplication.RunAsync` | Process arguments and stdout/stderr |
| MCP server | `Pointframe.Mcp/Program.cs`, `PointframeMcpTools`, and `PointframeMcpResources` | MCP stdio |

**Capabilities.**

- The CLI accepts `displays`, `capture --monitor <exact Windows device name> [--region <x,y,width,height>]`, `ocr --monitor <exact Windows device name> [--region <x,y,width,height>]`, `record --monitor <exact Windows device name> --seconds <positive integer> [--fps <1-60>] [--redact <x,y,width,height>]...`, `--help`/`-h`, or `--version`/`-v`. `--monitor`, `--region`, `--seconds`, `--fps`, `--redact`, and `--output` each accept a short alias (`-m`, `-g`, `-s`, `-f`, `-r`, `-o`); both forms are interchangeable and can be mixed within one invocation, and `capture`/`ocr` flags may appear in either order (`CliCommandParser.TryParseCaptureLikeCommand` loops over tokens rather than requiring a fixed position). Any long-form flag also accepts inline `--flag=value` syntax (e.g. `--monitor=\\.\DISPLAY1`); `CliCommandParser.ExpandInlineFlagValues` splits these into two tokens before the rest of parsing runs, so both `--flag value` and `--flag=value` are equivalent everywhere. `--help`/`-h`/`--version`/`-v` take priority over any other arguments present and are detected anywhere in the argument list (e.g. `record --monitor X --help` prints help instead of attempting to parse `record`), not just when passed alone. Invalid or incomplete commands print usage to standard error and return exit code 2; runtime failures return exit code 1. Since 2026-09-09 a runtime failure also writes a single-line `DirectCaptureResponse` with `Success: false` and an `Error` carrying a stable `Code` (`target_not_found`, `target_not_capturable`, `invalid_region`, `canceled`, or `capture_failed`, mapped from the exception type by `CliApplication.ToErrorCode`) to standard output, so a script parses standard output the same way on both paths; the human-readable `Pointframe CLI failed: ...` line stays on standard error for interactive use. Before that only `record` reported failures as JSON and the capture path left standard output empty, contradicting the help text. `--help`/`--version` (and bare `help`/`version`) write plain text rather than JSON to standard output, always exit 0, and skip constructing/invoking the capture and recording services entirely. `record` is a single blocking command scoped to one CLI process: it starts the recording, waits for the requested duration (or an earlier Ctrl+C, handled as a graceful stop rather than a hard kill), stops the recording, and writes one combined JSON response containing both the started `Session` and the finished `Artifact`. There is no separate CLI `stop-recording` command because a CLI invocation has no state that persists across two separate process launches; use the MCP server's `start_recording`/`stop_recording` tools for a start-now/stop-later workflow instead. `Pointframe.Engine.DirectRecordingResponse` (`SchemaVersion`, `Success`, `Error`, `Session`, `Artifact`) is the shared JSON response DTO used by both the CLI `record` command and `DirectRecordingMcpService`, so the two hosts serialize recording results identically.
- `pointframe mcp install --client vscode` downloads the stable MCPB and checksum aliases, verifies SHA-256 before extraction, installs into `%LOCALAPPDATA%\Programs\Pointframe.Mcp\<version>`, writes `install-state.json` atomically, and adds the server to VS Code's user `mcp.json`. `VsCodeMcpConfigurator` accepts JSON comments and trailing commas, preserves unrelated values, makes one durable `mcp.json.pointframe.bak`, and atomically replaces the live file; `--dry-run` validates the package and proposed configuration without persistent writes. `mcp status` checks the CLI-managed state and configured command path. `mcp doctor` launches the installed executable over stdio and requires a successful initialize plus the exact direct tool set; desktop-testing tools remain disabled. MCP-management commands branch before capture/OCR service construction and return a single-line `McpCommandResponse` with stable error codes. VS Code is deliberately the only managed client in the first slice; other clients retain the documented manual setup.
- `pointframe mcp serve [--project <dir>] [--mcp <file>]` is the command a committed agent config runs (`DesktopToolsApplication.ServeAsync`): it finds the project, loads the spec, requires an `app`, runs the same trust pipeline as `verify run` (`VerificationApplication.EnsureTrustedAsync`), refuses an app or working folder that is lexically inside the project but resolves through a symlink or junction to somewhere outside it (`PathContainment`, code `app_outside_project`), resolves the server like `verify run`, writes the policy with `VerificationApplication.WritePolicy` under `%LOCALAPPDATA%\Pointframe\verify\projects\<16 hex>` (`VerificationStore.ProjectKey`), and runs `Pointframe.Mcp.exe --desktop-testing --desktop-policy <file>` with inherited stdio (`InheritedStdioMcpServerHost`, no redirection) and its exit code. It writes nothing to stdout (the CLI hands the verification code `TextWriter.Null`); refusals are one stderr line with a stable code (`spec_untrusted`, `approver_unavailable`, `spec_invalid`, `no_app`, `app_outside_project`, `mcp_not_found`, `mcp_start_failed`) and exit 1. A spec `isolation` is honoured: the app gets a fresh data folder under the project's folder, deleted when the server exits (a per-session policy file when isolation is by argument); without `isolation` the app uses its normal data. `desktop_list_apps` now returns the policy's profiles (`apps`: id, executable file name, allowed action count) and `PolicyUnavailable` when the policy cannot be loaded.
- `capture`/`ocr` (CLI) and `capture_monitor`/`read_text_from_monitor` (MCP) accept an optional region limited to a sub-rectangle of the monitor: `Pointframe.Engine.CaptureRegion` (`X`, `Y`, `Width`, `Height`) is expressed in monitor-local physical pixels relative to the monitor's own top-left corner, not the virtual desktop. `CaptureRegion.ResolveWithin(monitorBoundsPixels)` validates positive width/height and that the region is fully contained by the monitor, then offsets it into absolute physical-pixel `PixelBounds`; an out-of-bounds or non-positive region throws `ArgumentOutOfRangeException` rather than being clipped, which both hosts surface as a runtime failure (CLI exit code 1; MCP tool error). `DirectCaptureService.ResolveCapturedMonitor` is the single place that applies this: with no region it captures the whole monitor via `IDisplayCaptureEngine.CaptureMonitor`; with a region it resolves the display via `GetDisplays()` and calls `IDisplayCaptureEngine.Capture` directly with the resolved bounds, so `IDisplayCaptureEngine.CaptureMonitor` itself never gained a region parameter. `ImageArtifactMetadata`/`McpImageArtifactMetadata` report both `MonitorBoundsPixels` (the full monitor) and `CaptureBoundsPixels` (what was actually captured), so a region capture is distinguishable from a whole-monitor one in the JSON response and metadata sidecar. The MCP tools take `region` as a `{x, y, width, height}` object (`McpCaptureRegion`), not a comma string, for real JSON-schema validation.
- Every command that writes a file (`capture`, `ocr`, `capture-window`, `ocr-window`, `record`) accepts `--output <file>` (`-o`) naming the exact artifact path, added 2026-09-09. `DirectCaptureService.ResolveArtifactPath` and the explicit-path branch of `DirectRecordingService.Start` create missing parent directories, reject an existing directory as the target, and otherwise fall back to the previous generated `yyyyMMdd-HHmmss-<id>` name under `%LOCALAPPDATA%\Pointframe`. The capture methods on `IDirectCaptureService` therefore take `string? outputPath` before the cancellation token, and `DirectRecordingRequest` gained `OutputPath` alongside the pre-existing `OutputDirectory` (an explicit path wins). The MCP tools deliberately do not expose this: their artifact locations stay server-controlled, so pass `cancellationToken:` by name at those call sites.
- Desktop-testing MCP tools are named with an explicit `desktop_` prefix (`desktop_click`, `desktop_drag`, `desktop_observe_app`, ...) set through `Name` on `[McpServerTool]`, since 2026-09-09. Their bare action names collided with tools from other MCP servers connected to the same client, which leaves a caller choosing between two indistinguishable `click` tools. The direct tools keep their unprefixed names because they are the released, published surface. Every tool method and every caller-supplied parameter on both tool types carries a `[Description]`; `Pointframe.Tests/Mcp/McpToolSurfaceTests.cs` fails the build when one is missing, because an MCP client selects tools from those descriptions and an undescribed tool is effectively invisible.
- `Pointframe.Tests/DocsSync/` guards documentation against drifting out of sync with the code it describes: `McpToolDocumentationTests` asserts every name in `PointframeCommandCatalog.DirectTools`/`DesktopTestingTools` is mentioned in README.md/`docs/mcp-desktop-testing/README.md`; `CliDocumentationTests` asserts every command and long flag extracted from `CliCommandParser.HelpText` is mentioned in `docs/cli/README.md`; `McpPackagingScriptDocumentationTests` asserts `packaging/test-mcp-stdio.ps1`'s hand-maintained `$expectedTools`/`$enabledExpectedTools` arrays match the same catalog (a second, earlier line of defense in addition to that script's own runtime assertion in CI). The same test class asserts that the MCPB manifest `tools` list in `packaging/build-mcp-package.ps1` names exactly the direct tools, because Claude Desktop shows that list when the bundle is installed. These follow the same pattern as `Pointframe.Tests/Services/TelemetryDocumentationTests.cs`: fail a normal `dotnet test` run immediately when a tool or flag is added/renamed without updating its documentation, rather than relying on someone remembering to update docs by hand.
- The MCP resource `pointframe://commands` lists the supported command identifiers. `PointframeCommandCatalog` derives these identifiers by reflecting over `[McpServerTool]`-decorated methods on `PointframeMcpTools` and `DesktopTestingMcpTools` (converting the method name to snake_case and stripping an `Async` suffix, or using an explicit `Name` on the attribute), so the resource cannot drift out of sync with the registered tools the way a hand-maintained list could.
- The MCP resource `pointframe://server-info` reports `SchemaVersion`, `Version` (the server's `FileVersionInfo.ProductVersion`, resolved via `Environment.ProcessPath` the same way the CLI resolves `--version`, since `Assembly.Location` is empty for single-file publishes), `DesktopTestingEnabled` (from `DesktopTestingHostOptions.Enabled`), and `Ffmpeg` availability (`Found`, `Path`, `Source` — `EnvironmentVariable`, `Bundled`, `Path`, or `NotFound`, from `FfmpegDirectVideoWriterFactory.GetAvailability()`). This lets an MCP client check server health/version and whether recording will work before calling `start_recording`, without starting a process or attempting a real recording.
- The resource `pointframe://guides/verify-desktop-work` serves `Pointframe.Mcp/Guides/verify-desktop-work.md`, embedded in the server assembly, so each install serves the steps that match its own tools: how an outside agent verifies its own desktop work (criteria first, act, check per criterion, negative control, signed report). `Program.cs` sets `ServerInstructions`, which clients show the agent at connect time, to point at it whether or not desktop testing is enabled. `.gitignore` ignores `*.md`, so the guide folder has its own negation. `VerifyDesktopWorkGuideTests` fails if the guide names a tool that does not exist, if its policy sample no longer loads, or if a server-info property it names is serialized differently.
- MCP tools list displays, capture a named monitor (or an optional sub-region) to a PNG artifact, read text from a named monitor (capture plus OCR, optionally scoped to a sub-region) via `read_text_from_monitor`, start a no-microphone MP4 recording, stop that recording with finalized artifact and sidecar metadata, and check whether a recording is currently active via `get_recording_status` (returns `IsRecording`, and when true, the active `Session` and `Elapsed` duration; `Session`/`Elapsed` are omitted when nothing is recording). `get_recording_status` is read-only and does not require a prior `start_recording` call to be safe to invoke.
- Since 2026-09-09 the four capture/OCR MCP tools (`capture_monitor`, `capture_window`, `read_text_from_monitor`, `read_text_from_window`) return a `ModelContextProtocol.Protocol.CallToolResult` instead of a typed `McpCaptureResponse`. `StructuredContent` still carries the full `McpCaptureResponse` JSON and a `TextContentBlock` repeats it, so existing structured-content readers are unaffected; unless the caller passes `includeImage: false`, an `ImageContentBlock` with the captured PNG is appended so a client that cannot read the server's filesystem can still see the screenshot. `McpCaptureResultBuilder.Build` assembles the result and `Pointframe.Engine.CapturePreviewImage.CreateDownscaledPng` produces the inline copy — it returns the on-disk bytes unchanged when the longest edge is already within `CapturePreviewImage.DefaultMaxLongestEdgePixels` (1600) and otherwise downscales with high-quality interpolation, preserving aspect ratio. The full-resolution PNG is always still written to disk (`%LOCALAPPDATA%\Pointframe\Screenshots` or the server-controlled path). Trade-off: because a directly-returned `CallToolResult` bypasses the SDK's return-type schema generation, these four tools no longer set `UseStructuredContent` and no longer advertise an output schema in `tools/list`; `list_displays`, `list_windows`, and the recording tools keep their typed returns and output schemas.
- As of 2026-09-07, the opt-in desktop-testing driver registers its policy-gated observation and mutation MCP tools and routes physical input and UIA actions through a supervised MCP worker. Owned-key release is synchronous: the worker is attempted first, then the parent-side `DesktopControlGuard` fallback is used when the worker or pipe is unavailable. The native input adapter records only successfully injected keys that were not already down, so fallback release cannot release user-owned keys; failed native release is reported rather than fabricated as success. The tool layer must route every mutation through `IDesktopActionCoordinator` and the worker-backed input/UIA services; preflight failures must produce no input and uncertain dispatch must not be replayed. Do not claim Gate A, B, or C evidence from headless contract tests. UI Automation inspection runs in the worker too, reached through the `uia.inspect` operation and surfaced to the parent by `WorkerUiObservationProvider`. The parent must not construct a UI Automation backend of its own: creating FlaUI's `UIA3Automation` initializes COM inside whichever process creates it, and doing that in the process serving the MCP protocol made unrelated tools hang intermittently. At startup the parent sends `uia.ping`, which reads a desktop-root property on the worker's MTA executor; it abandons a worker that does not answer within five seconds and tries at most three workers before allowing the request to fail. This moves first-call UIA initialization ahead of the first observation. Before the worker operation existed, the parent registered `WindowsUiAutomationProvider` with no backend at all, so every observation reported `ProviderUnavailable` with zero elements and no `element_ref` or `window_ref` was ever minted for `desktop_invoke`, `desktop_focus_window`, or `desktop_check_ui` to address.
- `desktop_invoke` resolves its element from the newest unexpired observation for the session process. With positive bounds and a valid same-process window reference, it foregrounds that window, releases owned input, then physically clicks the bounds center through the worker's normal input preflight, which checks that the point is on-screen and hit-tests to the target window; the response says `method: "click"`. If focus fails but the app process is already foreground, it skips focusing and allows the hit-test to land on any visible top-level window in that process, which supports owned popup menus. This path still releases owned input and requires the point to pass click preflight. If geometry is unavailable/off-screen or focus/click preflight rejects the target, it uses the UIA Invoke pattern or Toggle fallback and reports `method: "pattern"`. Native dispatch failures and uncertain worker failures are not replayed as patterns. UIA invoke and toggle calls run on a background MTA thread and wait at most `DesktopTestingLimits.InvokeReturnMilliseconds`; a call that is still running is reported as delivered (`InvokePending`, successful dispatch) because the provider accepted it, and its thread finishes naturally after the app returns. A `verify run` invoke step treats that successful pending dispatch as passed with a delivered message; following steps determine whether the app completed the interaction.
- desktop_press_keys resolves its target like the other input tools. A physical press takes an optional windowRef (must be of the session's process, and a member of the observationRef when both are given) and/or observationRef (stale refs fail with StaleObservation; with no windowRef the first image's bounds anchor it and the process must be foreground). The window must be valid, visible, owned by the process and the foreground window; the observation is consumed, and neither ref is an error (TargetRequired). A globalHotkeyId call is unchanged: policy-approved, no target, nothing consumed. desktop_verify's PressKeys step passes the resolved windowRef.
- A UIA inspection root mints a `window-{process_ref}-{hwnd}` reference and every descendant inherits it, so `desktop_focus_window`, window-scoped locators, and window checks address one actual top-level window rather than only the target process. The tool accepts a reference only when its embedded process reference matches the active session, then resolves the hexadecimal HWND. The parent sends that native handle to the worker as an integer through `DesktopAutomationWorkerProtocol.SerializePayload`/`DeserializePayload`; default `System.Text.Json` does not support `nint`/`IntPtr` serialization.
- The interactive gate harness creates its policy through `Pointframe.AutomationTests/Support/DesktopGatePolicyFactory.cs` and must launch the MCP executable with `--desktop-testing --desktop-policy <absolute-policy-path>`. The factory uses ordinary empty Pointframe arguments and writes the temporary policy beneath the configured evidence directory; `DesktopGatePolicyFactoryTests` verifies enabled tool registration without launching Pointframe. This registration check is not a desktop gate: the real Gate A workflow still needs a generic notification-area interaction and normal target exit before it can safely launch the target, while Gates B and C require their external visual/file evidence.
- Real desktop acceptance requires explicit operator approval of the chosen Windows account or machine. A dedicated account or machine is preferred, but a personal account is permitted with informed consent because normal settings and desktop state may change; the driver cannot prove that the environment is safe. Isolation is not implemented through target data-root overrides.
- OCR (`ocr` CLI command / `read_text_from_monitor` MCP tool) captures the monitor like `capture` does (including the optional region), then runs `Windows.Media.Ocr.OcrEngine` against the captured bitmap via `IOcrEngineService`/`WindowsOcrEngineService`. The response always includes the PNG artifact; `RecognizedText` is `null` when no text is found or no OCR language pack is installed for the user's profile languages. `DirectCaptureService.CaptureMonitorInternalAsync` is the shared helper behind both `CaptureMonitorAsync` and `CaptureMonitorTextAsync` so save/hash/metadata-sidecar logic isn't duplicated. `WindowsOcrEngineService.RecognizeDetailedAsync` bounds the attempt at `RecognitionTimeout` (30 seconds) and returns `OcrRecognitionStatus.Failed` rather than waiting forever: the Windows OCR stack can wedge indefinitely, and neither `OcrEngine.TryCreateFromUserProfileLanguages` nor `RecognizeAsync` is reliably cancellable, so an unbounded wait takes the whole host process with it. The recognition task owns and disposes the `SoftwareBitmap` copy, because on the timeout path the caller returns while that task is still reading it.
- Recording requires an explicit redaction-region array. Regions are capture-local physical pixels and are applied before frames reach ffmpeg.
- `desktop_observe_app` returns the captured pixels, not only metadata: it answers with a `CallToolResult` carrying one `ImageContentBlock` per requested rectangle (assembled by `DesktopObservationResultBuilder`), alongside the unchanged structured payload, and `includeImages: false` suppresses them. `DesktopObservationService` encodes each capture with `CapturePreviewImage.CreateDownscaledPng`, bounded by `DesktopTestingLimits.MaxImageLongestEdge` (1600). Consequently `DesktopImageReference.Width`/`Height` are the *preview* dimensions the model sees and deliberately differ from `DesktopBoundsPixels`; `DesktopCoordinateMapper` rescales between the two, and its non-transform overload delegates to the transform one so no caller can skip the rescale. An agent that treated a preview coordinate as a desktop offset would click short of its target by the downscale factor.
- Compact modes are opt-in and every default is byte-for-byte unchanged. `maxImageEdge` (64 to 1600) and `imageFormat: jpeg` on the four capture and OCR tools go through `McpImageOptions` (invalid values return `invalid_image_options` before any capture); `CapturePreviewImage.CreateDownscaledJpeg` encodes JPEG at quality 80. Measured on this repo's fixture, an 800 px cap cuts a whole-monitor capture by about 64 percent of wire bytes and 75 percent of image tokens, JPEG cuts a whole-monitor capture by about 60 percent of bytes but is larger than PNG for the flat fixture window, and downscaling a flat UI window to 800 px makes the PNG larger while still cutting image tokens, which is why neither is a default. `desktop_observe_app` takes `detail: compact` (`DesktopTestingResponseMapper.ToCompact` to `DesktopObservationResultBuilder.BuildCompact`: same refs and identity, bounds as `[x, y, w, h]`, nulls omitted, a shared top-level `windowRef`, names and text capped at 200 characters with the omitted count) and `maxImageEdge` (`DesktopObservationRequest.MaxImageLongestEdge`; the stored image width and height are the capped ones, so `DesktopCoordinateMapper` still maps clicks correctly). `desktop_get_test_report` takes `detail: compact` (`DesktopTestReportCompaction`), which drops per-item evidence, check specs, and the whole `proof` from the response only (`sessionDirectory` points to the full `report.json` to verify): `DesktopProofBundle.WriteAsync` always receives the full report, so the signed `report.json` on disk is complete. The server option `--compact-text` or `POINTFRAME_MCP_COMPACT_TEXT=1` (`McpOutputOptions`, `McpCompactTextFilter` registered as a second call-tool filter in `Program.cs`) swaps the text block of an allowlist of status-style tools for a one-line summary and leaves `structuredContent` alone; lists, searches, observations, and replay keep full text because a client that shows only text blocks would otherwise lose the data. The action summary keeps dispatch, verification, and error, and for a `Partial` or `Unknown` dispatch tells the agent not to resend and to call `desktop_get_action_result` with the action id, which is what prevents a duplicate input after an uncertain result. Tests: `Pointframe.Tests/Mcp/McpCompactModesTests.cs`.
- `desktop_check_ui` evaluates its condition against a fresh worker inspection of the session's target (`WorkerUiCheckSource`), and `processExited` is answered by `IDesktopProcessController` instead, because an exited target has no element tree to read. It was previously wired to a stub that reported `StateAvailable: false` for everything, so every check came back inconclusive and no action tool's reported success could be contradicted by anything. The tool takes a flat condition (`kind` plus `automationId`/`role`+`name`, optional `windowRef`, optional `expected`) rather than the engine's abstract `DesktopUiCheckCondition`, which carries no JSON polymorphism metadata and so could not be constructed by a client at all; `DesktopTestingMcpTools.BuildCondition` maps one to the other and rejects an unknown kind or a missing `expected`/`windowRef`. Toggle expectations normalize `true`/`checked`/`on` to `On`, `false`/`unchecked`/`off` to `Off`, and `indeterminate` to `Indeterminate`; selection accepts `selected` or `notSelected`. Unknown values are rejected before observation. State checks return `actualValue` when exactly one element was read, and the recorded report message includes it for failures; sensitive text is never returned. `IDesktopUiCheckService.CheckAsync` now takes the target `DesktopProcessIdentity`: the tool used to discard its `sessionId`, so nothing identified which application to inspect. A `textEquals` check never matches an element reporting `IsSensitive`, because a password field withholds its value by design.
- `desktop_end_test_session` closes the main window of a session-launched target, waits up to three seconds, then terminates its process tree if graceful close did not exit. The process controller retains the launched `Process` instance and validates its executable path, start time, and hash before stopping it; attached targets are never stopped. Ending an already closed or unknown session returns the typed `SessionNotFound` result.
- The session report is written by the server, never by the agent: `desktop_check_ui` records every check it evaluated (oracle `server-uia`) through `IDesktopTestReportService.RecordCheck`, and the coordinator records every action. Requests rejected before evaluation (unknown session, invalid condition, unknown criterion) are not recorded, because they say nothing about the application. `DesktopTestReportService.ComputeVerdict` gives `failed` for any failed check or any dispatched action whose verification failed; `inconclusive` for zero checks, an inconclusive check, a `Partial`/`Unknown` dispatch, or a criterion that is not `passed`; `passed` otherwise. Actions with dispatch `NotStarted` never touched the app, so they are ignored and can be retried. Until 2026-10-03 the tool recorded nothing and a report without checks finalized as `passed`, so every session report claimed success.
- `desktop_start_test_session` takes optional `criteria` (plain-text goals written before the work). `DesktopTestReportService.NormalizeCriteria` trims and bounds them (`MaxCriteria`, `MaxCriterionLength`) before launch; `Initialize` numbers them `C1..Cn`, stores `CriteriaSha256`, and refuses to replace them, so the target cannot move after the work. `desktop_check_ui` takes `criterionId`; each criterion's verdict is `failed` if any of its checks failed, `passed` if one passed, else `inconclusive` or `uncovered`. `expectFailure` marks a check as a negative control: `DesktopTestingResponseMapper.MapNegativeControl` turns the verdict around (a rejected wrong expectation passes; one that holds fails with `NegativeControlMatched`) but keeps `matches` as the oracle's raw answer. With criteria declared, `ComputeVerdict` needs at least one passing negative control, because an oracle that matches everything would also pass every criterion; negative controls never cover a criterion and do not count as checking the work. Together these make proof-of-work reports: evidence the agent cannot author, judged against goals it cannot change, from an oracle shown to reject a wrong answer.
- Evidence images come from `DesktopEvidenceRecorder`, set up per session from the policy's `artifactRoot` and `evidencePolicy` (`None`, `Failures`, `All`), which the loader required before anything read them. It finds the target process's windows with `IWindowDiscoveryService` (DWM extended frame bounds) and renders each from its own contents through `IWindowContentCapture` (`WindowContentCapture`: `PrintWindow` with `PW_RENDERFULLCONTENT`, cropped to the visible frame), painted bottom-most first onto a transparent canvas. A screen copy would show any window covering the target, and did: a relaunched app opened behind the editor and the evidence showed the editor. Evidence therefore holds nothing the policy did not approve, and one window that cannot be rendered fails the whole image as `CaptureFailed`. It writes `<artifactRoot>/<sessionRef>/evidence/NNNN-<kind>.png` and returns path, SHA-256 and bounds. A failed capture comes back as `Error` (`NoVisibleWindow`, `CaptureFailed`) instead of throwing, so missing evidence shows in the report and never fails the step it documents. Checks are captured after evaluation. Actions are captured in `DesktopTestingMcpTools.AnnotateActionAsync` after dispatch; anything that was not dispatched is skipped, and `NeedsActionEvidence` skips a replayed action ID, which returns its stored result without a new report entry. `Program.cs` registers the recorder with an explicit factory.
- `DesktopTestReportService.FinalizeAsync` seals every report with `DesktopProofService.Seal`: a SHA-256 chain over a header, the actions, the checks, and a summary (verdict, criteria), whose root is signed with ECDSA P-256 by `IDesktopProofSigner`. It re-seals on each finalize, so a report fetched again also covers later steps. Every hash is computed over `DesktopProofService.CanonicalJson` (web defaults, enums as names), and `Verify` deserializes with the same options. A report that went through the MCP serializer (camelCase) or a PascalCase file therefore still recomputes to the same hashes; `ReportStillVerifiesAfterAJsonRoundTrip` pins this, so add any new report field to that test's sample. `CngDesktopProofSigner` keeps a non-exportable per-user CNG key (`Pointframe.DesktopProof.v1`) and opens it lazily, so a key store failure fails only report signing, not every desktop tool. The verifier treats the report as untrusted input and refuses evidence paths outside the evidence folder. A valid proof shows provenance only; `keyId` is what separates this machine's reports from a report re-signed by someone else.
- `desktop_get_test_report` writes a proof bundle to the report's signed `SessionDirectory` (`<artifactRoot>/<sessionRef>/`) on every call: `report.json` (serialized with `CanonicalJson`, so it verifies from disk), the `evidence/` folder (`DesktopProofBundle.EvidenceFolderName`, shared with the recorder), and `index.html` from `DesktopProofBundle.RenderIndex`. The HTML encodes every report value and says it is not itself signed. The coordinator records each action as `DesktopTestReportService.UnannotatedActionDescription`; the tool then calls `AnnotateAction` once with the operation name (`click`, `enter_text`, ...) and any evidence. `IsActionUnannotated` stops a replayed action ID, which returns its stored result, from being annotated or captured twice. `desktop_restart_app` runs through the coordinator too and is recorded as `restart_app`, with a screenshot of the relaunched app; before 2026-10-03 it bypassed the coordinator, so a report showed checks before and after a restart with no restart between them.
- `desktop_export_scenario` reads an ordered recording ledger held by `DesktopTestReportService` for the same lifetime as the signed report. The MCP boundary adds an export step only after a completed dispatch (invoke locators are unique in their observation; semantic text needs a portable locator; global hotkeys are excluded) and after every evaluated check. Coordinate actions, window-scoped checks, and elements without a stable locator remain indexed unsupported entries. The tool emits a scenario wrapper with frozen session criteria and writes `scenario-<id>.json` beside `report.json`; it does not add a step kind to spec v1.
- Every recorded check carries a `DesktopCheckSpec` (kind, locator, expected, timeout) inside the signed entry. `desktop_replay_checks` re-runs a signed `report.json` in a fresh session through the same `EvaluateAndRecordCheckAsync` path as `desktop_check_ui`. It refuses a report outside the policy's `artifactRoot` (the server reads the file for the caller), a report that fails `Verify`, and a session whose executable hash differs. It skips checks scoped to a `windowRef`, because window refs belong to one session, and returns `matched` or `differs` per check and per criterion. Replay starts from a fresh launch, so it confirms only state that survives a restart; unsaved typed text correctly replays as `failed`.
- UI snapshots cross the worker pipe as one message: `DesktopAutomationWorkerProtocol.MaxMessageBytes` is 8 MiB, and `HandleInspect` answers `SnapshotTooLarge` before a write could fail and close the pipe. The walk is breadth-first to `MaxUiAutomationDepth` 32 (Chromium content is deeper than 8) and `MaxUiAutomationElements` 200. An element's `Text` is its Value pattern, or for a text control its Name. `FlaUiWindowsUiAutomationBackend.Inspect` finds the target's windows with native `EnumWindows` rather than a desktop-wide `ByProcessId` search (see the lesson [A desktop-wide UI Automation search by process id hangs on any other window](../../../lessons.md#a-desktop-wide-ui-automation-search-by-process-id-hangs-on-any-other-window)) and traces entry, desktop-root acquisition, target-window enumeration, and walk completion so a future hang identifies its last completed step. `WindowsProcessController` removes `ELECTRON_RUN_AS_NODE` from the launched app's environment. Checked on PKHeX (WinForms), dnGrep (WPF), and an Electron app.
- OCR on an observation is selected with `includeOcr` plus a zero-based `ocrImageIndex` into `captureBoundsPixels`. The earlier `ocrImageRef` parameter was unusable: it had to name an image from the observation the same call creates, so any value a caller could supply resolved to `ImageNotFound`.
- Synthesized input has to imitate hardware, not merely be accepted by `SendInput`. Every absolute mouse event carries `MOUSEEVENTF_VIRTUALDESK`, without which Windows maps normalized coordinates onto the primary monitor only and every secondary-monitor click lands elsewhere. A drag presses, moves through at least `MinDragMoveSteps` interpolated points, then releases, tracking the held button in `_ownedMouseButtons` so a failure cannot leave it down; two disconnected clicks are not a drag. A scroll moves the cursor to its point first, because the wheel goes to the window under the cursor rather than the focused one. A click emits move, press and release as separate events with a hold between them. `desktop_enter_text` clicks to place the caret before typing (it previously validated the point and never clicked, so characters went wherever focus happened to be) and paces characters in chunks, because one large `SendInput` batch is accepted and reported as success while the target's message pump drops the tail.

**Packaging and configuration.**

`Pointframe.Cli` is released as a self-contained, single-file `win-x64` ZIP with a SHA-256 checksum. `packaging/build-cli-package.ps1` publishes it and creates the versioned archive. The winget package is a `zip` installer with a nested `portable` `Pointframe.Cli.exe` and `PortableCommandAlias: pointframe`: winget extracts the whole ZIP and links only the exe onto `PATH`, and the exe still finds `e_sqlite3.dll` beside it because it runs from the extracted folder through that link. ## Claude plugin

`plugin/pointframe/` is a Claude plugin, shaped for the Anthropic plugin directory: a manifest (`plugin.json` in the `.claude-plugin` folder), `.mcp.json`, `README.md`, `LICENSE`, `server.lock.json`, the launcher `plugin/pointframe/scripts/start-mcp.cmd`, the start script, `plugin/pointframe/.claude-plugin/icon.png` (copy of `packaging/assets/mcp-icon.png`, the one binary the directory wants), and two skills (`verify-desktop-work`, built from `Pointframe.Mcp/Guides/verify-desktop-work.md`, and `capture-screen`). Keep every other file a small text file under 256 KiB: the directory holds a plugin with binaries or larger files for a reviewer.

- **Launch.** `.mcp.json` is `{"command": "${CLAUDE_PLUGIN_ROOT}/scripts/start-mcp.cmd"}` with no args; the two-line CRLF `.cmd` runs `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%~dp0start-mcp.ps1" %*` and exits with its code (Claude Code spawns a `.cmd` stdio server directly). The directory validator treats every arg after the command as a path, so flags there are blocked; the `.cmd` keeps the flags out of `.mcp.json` while the bypass still lets Windows PowerShell 5.1 run the script under the default Restricted policy. One path from `${CLAUDE_PLUGIN_ROOT}`, no other variable or inline code. The `.cmd` must not echo (stdout is the JSON-RPC stream). The script reads `server.lock.json` (version, asset URL, SHA-256 of `Pointframe.Mcp-<version>-win-x64.mcpb`), downloads it over TLS 1.2 on a cache miss, refuses a hash mismatch, extracts to `%LOCALAPPDATA%\Pointframe\plugin-mcp\<version>\server\`, writes `.verified.json` (archive hash and `Pointframe.Mcp.exe` hash) and runs the exe with inherited stdio. Every start re-hashes the exe against `.verified.json`, so a cached start needs no network. It writes nothing to stdout (that is the JSON-RPC stream) and fails closed with a message on stderr.
- **Hashing uses .NET, not `Get-FileHash`.** A Windows PowerShell 5.1 child started from PowerShell 7 inherits its `PSModulePath` and then cannot find `Get-FileHash`; a cache check that threw was silently treated as a miss.
- **Pinning before verification.** Every release comes from a merged pull request. Run `pwsh scripts/merge-pr.ps1 -PinOnly -Worktree <path>` before `verify.ps1`; it updates and commits the pin locally, without pushing. Then verify the pinned tree, push, create the PR, and run `merge-pr.ps1 -Auto -Worktree`; Auto checks that the receipt matches the PR head and current tree; if a newer release landed meanwhile, it commits and pushes the pin itself and accepts the older receipt because only the pin files changed. No bot PR or `PLUGIN_PIN_TOKEN` is needed (a `GITHUB_TOKEN` PR would start no checks). `ci.yml` has `paths-ignore: plugin/**` on its `push` trigger (pull requests still run all checks), so a plugin-only merge runs no CI and cuts no release.
- **Rules enforced offline.** `scripts/check-agent-discovery.ps1` (`Test-ClaudePlugin`, with a mutation self-test on a copy of the plugin) checks the manifest fields and name pattern, README length and required disclosures, the lock schema and its agreement with `plugin.json`, the `.mcp.json` shape, stdout cleanliness of the start script, skill front matter, file types and sizes, `ci.yml`'s `paths-ignore`, `plugin-pin.yml` and the submission draft `packaging/directory-submissions/claude-plugin-directory.txt`.
- **Acceptance.** `pwsh scripts/test-agent-onboarding.ps1 -Client claude-plugin` copies the plugin, runs its `.mcp.json` command (the `.cmd`) with a temporary `LOCALAPPDATA` against the real pinned release (tampered hash and failed download fail closed with an empty stdout; then initialize, `tools/list`, `list_displays`, `list_windows`, `capture_window` on the fixture under the desktop lock; then an offline start from the cache). `-SelfTest` also runs the offline script behaviour against a stand-in server.
- **Desktop testing is off** in the plugin, because the directory forbids `userConfig` variables in the command. ## Spec-driven verification runs

**Responsibility.** `verify` checks a project against a spec it keeps in git (`verify.json` in its `.pointframe` folder) with no agent driving the app, and freezes a task's acceptance criteria before work starts. It turns an agent's hand-driven desktop session into a repeatable command with a verdict and an exit code. Pointframe keeps `.pointframe/verify.json` for the WinForms fixture and `.pointframe/verify-app.json` for the real WPF settings window; the latter builds the app and verifies that a saved setting survives restart.

**Initialization.** `pointframe verify init` runs from the project root and writes a starter `.pointframe/verify.json` after round-tripping it through `VerificationSpecLoader`. It detects root .NET solutions and test frameworks or supported scripts in a root `package.json`; Node commands use pnpm when `pnpm-lock.yaml` exists, yarn when `yarn.lock` exists, and npm otherwise. If multiple lockfiles exist, a recognized `packageManager` field in `package.json` selects the manager; otherwise pnpm, then yarn, then npm takes priority and init warns with the lockfiles found. A single .NET `WinExe` becomes the app candidate. App detection reads runtime identifier and platform properties from the project and applicable `Directory.Build.props`, prefers an existing framework/RID or x64 platform output, and uses the RID output path when it has not been built yet. `--explore` starts the built app through the same MCP server, `DesktopScenarioRunner`, and desktop semaphore as a verification run, polls observations for automation ids, then creates an `app-starts` scenario from the first id; when no IDs are exposed, it uses the first named element's role and name and warns about the fallback. `--mcp <file>` selects the server for exploration before the environment-variable and CLI-installed-server fallbacks. Optional Claude/Codex Stop hooks, an `AGENTS.md` instruction block, and the verification artifact ignore rule are merged idempotently. When hooks are enabled, init resolves `pointframe.exe` on PATH and runs `--version`, reporting a missing command (hook fail-open), a wrong command, a timeout, or a version mismatch in warnings/next steps. The `install` command copies a ZIP install to `%LOCALAPPDATA%\Programs\Pointframe.Cli`, adds that directory to the user PATH, and is idempotent. An existing spec is left byte-for-byte untouched unless `--force` is used, while hooks and optional onboarding files are still applied; init reports `unchanged` only when no file was written. When there is no existing spec and no gate or scenario can be generated, nothing is written.

The public onboarding guide for adopting verification in another project is [`docs/cli/verify.md`](../../cli/verify.md); its CI section describes running verification as a required check, the standard-command policy on fresh runners, spec review protection, and why desktop scenarios need an interactive runner. CLI releases, the spec schema, and the hook command have independent compatibility rules; see [D-012](#d-012-version-compatibility).

The input contract is frozen at `schemaVersion: 1`: its fields keep their meanings, and adding, removing, or reinterpreting an input field requires schemaVersion 2 and migration notes. The loader rejects unknown fields and versions as `spec_invalid`; it does not migrate or leniently ignore them. Verdict and review output may gain fields within v1, so readers must ignore output fields they do not recognize. See [D-013](#d-013-verification-spec-v1-is-frozen) and the [frozen v1 reference](../../cli/verify-spec.md).

**Flow of `verify run`.**

1. `VerificationSpecLoader` parses the spec strictly: unknown properties and steps are rejected, every criterion needs a check naming it, and a scenario with criteria needs a negative control (the report's own pass rules, checked before anything launches). Paths resolve from the folder that holds `.pointframe/`.
2. Trust: nothing runs unless this spec's gates and app (`SpecDigests.CommandsSha256`) are approved, checked on every run and task start, so removing a gate or repointing the app needs approval again. New or changed commands go through `CommandPolicy` fixed refusals, then its exact standard-command policy (`ApprovedBy = "policy"`), then `AgentApprover`; an unavailable approver reports `approver_unavailable`, while a refusal reports `spec_untrusted`, and both direct a person to `verify trust`. After trust checks and before gates, `verify run` checks whether a process has the spec app's executable as its main module path; a match fails with `app_running` and names the PID so the user can close it before a build locks its files. Policy approves a command's form, not the behavior of its script; gate scripts can delete files, so `.pointframe/` changes need code review. See [D-009](#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands) and [D-011](#d-011-standard-commands-are-approved-by-policy). Gates: `GateRunner` runs every gate through `cmd.exe` with a log and failure details (compiler errors, failed tests, `ERROR` lines); any failed gate marks the scenarios `skipped`.
3. Scenarios: under a machine-wide named semaphore, each scenario gets its own `Pointframe.Mcp.exe --desktop-testing` process, a policy written for the spec's `app`, and with `isolation` a fresh data folder passed by environment variable (the server's launched app inherits it) or by argument, deleted afterwards. `UserSettingsService` accepts the automation settings override as either the existing file-path form or a directory, where it writes `settings.json`; the real-app spec uses directory isolation so owner settings stay untouched.
4. `DesktopScenarioRunner` resolves `automationId` (or role and name) to an `element_ref` by polling `desktop_observe_app` for up to 15 seconds and calls the `desktop_*` tools. Before the first step, and after every `restart`, it waits up to the same 15 seconds for an observation with at least one UI element, else the launch (or restart) step fails `NoVisibleWindow`. A `restart` step retries `TargetStillRunning` every 250 ms for up to 10 seconds, because an app's own Close returns before its process exits; each retry is a separate `desktop_restart_app` call, so one stuck step shows as about 40 errors in `agent_operation` telemetry. When the wait runs out, the step's message says that `restart` never closes the app and how to fix the spec: agents in trials put `restart` first to "start fresh", which can never pass. An input step whose locator matches more than one element fails `AmbiguousLocator` before any input (candidates listed; checks keep the server's evaluation). `pressKeys` focuses the target window first; if focus is refused, the step fails `FocusRequired` with foreground guidance and recommends invoke steps with role and name. `ErrorOf` reads the raw tool result: an `isError` result with only a text block becomes `ToolError` carrying that text (first 500 characters), and `ElementNotFound` for an `automationId` adds a role-and-name hint when an observed element has that name. A missing menu item adds guidance that submenu items appear in UI Automation only after their parent menu is open, and that the parent should be invoked first. The MCP worker's UI Automation `invoke` action uses an element's Invoke pattern, or its Toggle pattern when Invoke is unavailable (for example, WPF checkboxes). An invoke result with dispatch `Complete` and error code `InvokePending` is recorded as a passed delivered step because the provider accepted it; later scenario steps observe the app's resulting state. The first failed step stops the scenario; the report is always fetched and the session always ended. A scenario passes only when every step passed, the report verdict is `passed`, `DesktopProofService.Verify` accepts the bundle from disk, and cleanup succeeded.
5. The verdict (`verdict.json` in the project's artifacts\pointframe-verify folder, and standard output) carries provenance: git head, the working-tree hash computed like `verify.ps1`, the CLI version, and the MCP server's hash. A run with one or more scenarios and no gates adds a warning and `noBuildGate: true`; the app may be stale even when its scenario passes. `verify status` never marks that pass fresh (`freshnessReason: no_build_gate`), and the Stop hook blocks with a build-gate next step. `pass` exits 0, `partial` (`--scenario` or `--only`) exits 0, `fail` exits 1, a bad spec or arguments exit 2. `verify status` reports `fresh` only for a `pass` on the current tree hash and when the verdict's `specSha256` matches the selected spec file's SHA-256. With an active task it also requires the verdict task id and `snapshotSha256` to match the stored active snapshot; other reasons are `verdict_for_another_spec`, `tree_changed`, `task_not_covered`, and `verdict_for_another_task`. Status adds `activeTask`, parsed `lastStop`, and `unverifiedStop` (true only when the most recent stop was unverified on the current tree).

Run verdicts, status, task-start responses, and setup responses include the structured `nextStep` record (`kind`, `command`, `retryAfterSeconds`, `text`). The single mapper in `VerificationNextSteps` maps status and error code to `fix_code`, `run_command`, `wait`, `needs_person`, or `none`; the Stop hook uses its text and command in block reasons and unverified system messages, and stores it in `last-stop.json`. This is additive output under v1; the input spec remains frozen.

**Interactive tools.** `verify setup [--client claude-code|codex|vscode|all]` (`DesktopToolsApplication.SetupAsync`) approves the spec through the same pipeline, installs the MCP server with `McpPackageInstaller` only when none resolves (never touching VS Code's user config), and merges project-scoped client config that runs `pointframe mcp serve` (`ProjectMcpClientConfig`): `.mcp.json` (`mcpServers`), `config.toml` in the project's `.codex` folder (`[mcp_servers.pointframe]`, edited as text so comments and other tables stay; only `command` and `args` are replaced), `.vscode/mcp.json` (`servers`, with `--project ${workspaceFolder}`). JSON is parsed with `VsCodeMcpConfigurator.ReadJsonObject` (comments and trailing commas accepted, not kept on rewrite), a file already holding the right entry is not rewritten, and the first rewrite keeps a `.pointframe.bak`. The smoke check launches `pointframe mcp serve` through `IMcpToolClientFactory`, requires `desktop_start_test_session` in `tools/list` and the spec's app id in `desktop_list_apps` (an unbuilt app is a warning), and prints one JSON line (`status`, `filesWritten`, `filesUnchanged`, `clients`, `profileId`, `serverPath`, `serverVersion`, `serverInstalled`, `tools`, `warnings`, `nextStep`); failures carry a code (`smoke_failed`, `smoke_tools_missing`, `smoke_app_not_listed`, `mcp_install_failed`, `mcp_not_found`, `client_config_invalid`, `pointframe_not_on_path`) and the files stay written. `verify init --explore` runs the same trust check on the generated spec before it launches the app and otherwise warns and skips exploring. See [D-014](#d-014-interactive-desktop-testing-reuses-verify-trust).

**Scenario import.** `pointframe verify scenario add --from <file> [--spec <file>] [--force]` accepts the exported wrapper or a bare scenario. `VerificationApplication.AddScenarioAsync` merges it into the selected spec, refuses case-insensitive duplicate ids unless forced, round-trips the merged document through `VerificationSpecLoader` before writing, and returns `added` or `replaced` as one JSON line. The spec remains the only approval source; adding a scenario changes no command/app approval digest.

**Tasks.** `verify task start <task-file>` runs `AgentExaminer` on the configured agent (`IAgentRunner`: Claude Code, Codex, or a command; see D-010) in an empty temp folder outside the repository, with only the Pointframe MCP server, no project settings or hooks, and a JSON schema for its proposal. The CLI parses the proposal with the spec rules and runs it on the unchanged app in fail-before mode (`continueAfterFailedChecks`); `FailBefore.Evaluate` rejects it when a criterion already holds or a negative control fails. A confirmed snapshot (task text, tree hash, a hash per gate and scenario) is stored by `VerificationStore`; `verify run --task <id>` adds it as scenario `task-<id>` and lists `specChanges` since the task started.

**Stop hook.** `verify hook stop` (`VerificationHook`) answers the Stop event of Claude Code and Codex (same input and `decision: block` answer) on stdout: it reuses the last verdict when the tree hash, spec hash, and active task (id and snapshot hash) are unchanged (a question-only turn costs nothing, an unchanged failure keeps blocking), otherwise runs `verify run` with the active task in-process. A failure the agent can fix returns `decision: block` with the failed gate details or `Expected ..., found ...`, ending with `Next step: ...`; a failure only a person can fix and the `--max-blocks` limit (default 5, counted per session in `hook-state.json`) let the agent stop with a `systemMessage`. Each allowed stop writes `last-stop.json` beside hook state with outcome, reason (`no_verdict`, `needs_person`, `block_limit`, or `hook_error`), error code, `nextStep`, tree/spec hashes, task id, and UTC time; a pass records `verified`, other allowed stops record `unverified` and their message starts `UNVERIFIED:` and includes the next step. A crash records `hook_error` best-effort. With `--review`, a pass on a tree not yet in `review.json` is followed by `AgentReviewer` (no MCP tools, the diff since the task's commit through a throwaway index), whose flags go to `review.json` and the person, never to the verdict. An `AgentException` is retried once; a final failure is recorded in `review.json` with `treeHash`, `baseCommit`, `failed`, and `error`, and is considered reviewed for that tree so it is reported once. `verify status` includes the resolved hook command, current tree's review state, and last stop record. The hook must run an installed or copied CLI: a running `Pointframe.Cli.exe` locks the output a project's build gate rebuilds.
**Invariants.**

- Pass or fail comes only from the server's signed report and the CLI's checks; no agent and no CLI code writes a check result.
- Command approval is fixed refusals, policy for exact standard forms, the approver agent, then a person; replacing a task snapshot always needs a person at a terminal. See [D-011](#d-011-standard-commands-are-approved-by-policy), [D-009](#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands), and [D-008](#d-008-verify-approvals-need-a-person-at-a-terminal-and-live-outside-the-repository).
- A failed check carries the found value (`actual`), so a wrong expectation is visible in one run.

## D-007 `verify run` drives the MCP server instead of sharing an Engine service

**Decided.** 2026-10-03.

**Context.** The plan was to move the act/check/record logic out of `DesktopTestingMcpTools` into `Pointframe.Engine` so the CLI could call it directly. But the UI Automation backend (FlaUI, the worker process, input) lives in `Pointframe.Mcp`, which the CLI does not reference.

**Decision.** The CLI is an MCP client: it starts `Pointframe.Mcp.exe` with a generated policy and calls the same `desktop_*` tools an agent calls.

**Consequences.** One implementation of sessions, checks, evidence, and signing; a CLI run and an agent session produce the same report, and every `verify run` exercises the agent path. The cost is a child process per run and a JSON boundary: a tool's argument or response change must be mirrored in `DesktopScenarioRunner`.

**Alternatives rejected.** Moving the backend and orchestration into the Engine (a large refactor of FlaUI and worker code, with two hosts to keep in step); referencing `Pointframe.Mcp` from the CLI (pulls the MCP host and FlaUI into the CLI package).

**Files.** `Pointframe.Cli/Verification/DesktopScenarioRunner.cs`, `Pointframe.Cli/Verification/McpStdioToolClient.cs`, `Pointframe.Mcp/Tools/DesktopTestingMcpTools.cs`.

## D-008 Verify approvals need a person at a terminal and live outside the repository

Superseded by D-009 for the approval of gate and app commands; it still holds for replacing a task snapshot and for where approvals are stored.

**Decided.** 2026-10-03.

**Context.** Gate commands run with the user's permissions, and a task's frozen criteria are what the worker agent is graded against. The worker runs as the same Windows user with a shell, so any plain approve command or `--yes` flag is one it can use itself.

**Decision.** `verify trust` and `verify task start --replace` approve only after a person types `yes` at an interactive terminal (`ConsoleConfirmation` refuses redirected input), with no flag to skip it. Approvals and task snapshots live under `%LOCALAPPDATA%\Pointframe\verify`, keyed by project folder, not in the repository. New criteria come from the examiner agent, never from the worker.

**Consequences.** An agent cannot approve its own gates or app, remove gates, or replace its own criteria through the CLI, and editing the repository does not change them. This is a consent boundary, not a sandbox: a worker with unrestricted file access could still edit the store, which only a sandbox that limits writes to the workspace prevents. Non-interactive CI needs its own trust mechanism (planned with CI support).

**Alternatives rejected.** An `ask` permission rule on the approve command (only Claude Code honours it); storing approvals in the repository (the worker can edit them); a `--yes` flag (the worker can pass it).

**Files.** `Pointframe.Cli/Verification/VerificationStore.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`.

## D-009 An approver agent behind fixed rules approves verify commands

Partly superseded by D-011 for standard commands.

**Decided.** 2026-10-04.

**Context.** Under D-008 every new or changed gate or app command waited for a person at a terminal. The owner wants agents to work autonomously and rejected a human step in the normal flow. Claude Code's auto-mode classifier refused to replace the person with an agent until the owner allowed it explicitly in the permission settings.

**Decision.** New or changed commands first face `CommandPolicy` fixed refusals (the app is a program inside the project and not a shell; working folders are inside the project; no URLs, network shares, download tools, deletes, encoded or inline payloads, system changes, or environment paths). Commands outside D-011's standard forms then go to `AgentApprover`: a separate run of the configured agent (D-010) started by the CLI, with no MCP tools and no project settings, that sees only the commands and the previously approved ones, treats them as untrusted data, and refuses when in doubt. Its yes is stored like a person's, with `ApprovedBy` and its reason; a person (`verify trust`) is needed after a refusal or an unavailable approver.

**Consequences.** Normal work never waits for a person. The approver can be talked into a wrong yes by text crafted for it; the fixed rules are the backstop for dangerous cases, and the verdict's `provenance.commandsApprovedBy` identifies an agent approval. An unavailable agent is distinguished from its refusal so the person knows the command was not judged.

**Alternatives rejected.** A person for every change (D-008: blocks autonomy); treating commands committed in HEAD as approved (blocked by the permission layer, and unsafe in cloned repositories and in workflows where agents commit); an approver without fixed rules (one wrong yes could run anything).

**Files.** `Pointframe.Cli/Verification/CommandApprover.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Cli/Verification/VerificationStore.cs`.

## D-011 Standard commands are approved by policy

**Decided.** 2026-10-04.

**Context.** M1 was blocked because a clean .NET project's `verify run` depended on an approver agent reaching its model API; the sandbox returned `ConnectionRefused` before the normal build gate could run. `verify init` emits a small set of conventional build and check commands.

**Decision.** `CommandPolicy.IsStandard` approves only command text that parses exactly as the supported `dotnet build|test|format|restore`, npm/pnpm/yarn test/install/run, or PowerShell project-script forms, with relative in-project paths, allowed options, and no shell metacharacters. When every gate is standard and the app passes its existing fixed rules with metacharacter-free arguments, `EnsureTrustedAsync` stores approval with `ApprovedBy = "policy"`. Any nonstandard command remains with the approver agent, then a person. This approves the command text only, not the behavior of the project's code it runs.

**Consequences.** Standard verification is offline and costs no agent call. A grammar change is a policy change and needs focused classification tests. `approver_unavailable` distinguishes missing or failing infrastructure from a real refusal (`spec_untrusted`); the Stop hook lets an agent stop and tells a person how to restore approval. Policy is intentionally narrow and does not sandbox gate processes.

**Alternatives rejected.** A structured command schema (requires changing the spec contract and generated forms); an offline human baseline (still blocks clean projects on a person); an approval service (adds an online dependency); a signed manifest (adds a signing and distribution lifecycle).

**Files.** `Pointframe.Cli/Verification/CommandApprover.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Cli/Verification/VerificationHook.cs`, `Pointframe.Tests/Cli/CommandApprovalTests.cs`, `Pointframe.Tests/Cli/VerificationHookTests.cs`, `Pointframe.Tests/Cli/VerificationInitTests.cs`, `docs/cli/README.md`.

## D-012 Version compatibility

**Decided.** 2026-10-04.

**Decision.** CLI release numbers, the spec's `schemaVersion`, and the hook command are independent. An unknown `schemaVersion` is rejected as `spec_invalid`; the CLI never silently migrates an unknown schema. The hook command `pointframe verify hook stop [--review]` is a stable contract across CLI upgrades. A CLI/hook version mismatch produces a warning only. For the CLI-installed fallback, a server older than the CLI is updated to the latest release or refused with `mcp_version_mismatch`; a newer server is used with a warning. Explicit server paths and `POINTFRAME_MCP_EXECUTABLE` are honored as chosen, with a stderr warning when that server's file version is older than the CLI (a stale variable from an old install silently ran a 6.7.71 server under CLI 6.7.85 in 2026-10 trials).

**Alternatives rejected.** Lockstep numbering; silent acceptance of unknown fields; automatic migrations; a version negotiation protocol.

**Files.** `Pointframe.Cli/Verification/VerificationSpecLoader.cs`, `Pointframe.Cli/Commands/CliCommandParser.cs`, `Pointframe.Cli/Verification/VerificationInit.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Tests/Cli/McpServerVersionTests.cs`, `Pointframe.Tests/Cli/VerificationRunTests.cs`, `Pointframe.Tests/Cli/VerificationInitTests.cs`, `Pointframe.Tests/Cli/VerificationTests.cs`.

See [D-013](#d-013-verification-spec-v1-is-frozen) for the frozen input contract and output compatibility rule.

## D-013 Verification spec v1 is frozen

**Decided.** 2026-10-04.

**Context.** Projects keep verification specs in source control, and tools need predictable input and output compatibility across CLI releases.

**Decision.** `schemaVersion: 1` is frozen: existing input fields keep their meanings, and no field is added, removed, or reinterpreted under version 1. A change to the input contract requires `schemaVersion: 2` and migration notes. The loader rejects unknown fields and versions with `spec_invalid`. Verdict and review output may gain fields while remaining version 1; consumers must ignore fields they do not recognize.

**Consequences.** A misspelled or newer input field fails before any command runs, so the user must update the spec or CLI deliberately. Output consumers can read fields they understand without failing when a later CLI adds fields.

**Alternatives rejected.** Lenient handling of unknown input fields would let typos change verification silently. Automatic migration would change a project's checked-in input without an explicit review.

**Files.** `Pointframe.Cli/Verification/VerificationSpecLoader.cs`, `Pointframe.Cli/Verification/VerificationSpec.cs`, `Pointframe.Cli/Verification/VerificationResults.cs`, `Pointframe.Tests/Cli/VerificationSpecV1CompatibilityTests.cs`, `docs/cli/verify-spec.md`. See [Spec-driven verification runs](#spec-driven-verification-runs) and [D-012](#d-012-version-compatibility).

## D-014 Interactive desktop testing reuses verify trust

**Decided.** 2026-10-05.

**Context.** A coding agent in another project needed a hand-written policy file and a manual `--desktop-testing --desktop-policy` registration to get interactive desktop tools. A policy file the agent writes would let it choose what the server may launch.

**Decision.** The CLI is the front door and the spec is the source: `pointframe mcp serve` builds the desktop policy from the project's `.pointframe/verify.json` `app` after the same trust check as `verify run` (D-008, D-009, D-011 semantics unchanged: the commands digest, fixed refusals, standard-command policy, approver agent, a person only through `verify trust`), and `pointframe verify setup` writes the project-scoped client config that runs it. The policy lives outside the repository under the verify store, keyed by the project path. Containment is decided on the resolved path, so a junction cannot lead the app out of the project. Isolation from the spec is honoured with a temporary data folder deleted on exit. `verify init --explore` needs the same trust before it launches the app.

**Consequences.** One command replaces the policy file and the registration. Changing the app or any gate stops the server from starting until it is approved again. A config that depends on the CLI being on `PATH` fails with `pointframe_not_on_path` at setup rather than silently later. `mcp serve` never asks a person, so first approval of a nonstandard spec happens in `verify trust` or `verify setup` with an approver.

**Alternatives rejected.** A policy file kept in the repository (an agent could edit what it may launch); a separate trust store for interactive tools (two approvals for one command); user-scope client config (it would apply to every project).

## D-010 Verify's agent roles run on any agent

**Decided.** 2026-10-04.

**Context.** The examiner, reviewer, and approver were hard-wired to `claude -p`, so a team using Codex or another agent could not use them. The owner wants verify usable with any agent.

**Decision.** The roles (instructions, answer schema, how the answer is checked) are separate from how an agent is started. `IAgentRunner` has three implementations: `ClaudeCodeAgentRunner` (`claude -p`, system prompt, built-in tools off, budget cap, `structured_output`), `CodexAgentRunner` (`codex --ask-for-approval never exec -`, instructions leading the prompt, `--output-schema`, `-o`, read-only sandbox, `--ephemeral`, MCP through `-c mcp_servers...` with `default_tools_approval_mode=approve` for that one server), and `CommandAgentRunner` (any program, with `{prompt_file}`, `{schema_file}`, `{output_file}`, `{mcp_config_file}` placeholders). `AgentSelection` reads the choice from the person's profile (`agent.json` under `%LOCALAPPDATA%\Pointframe\verify`), not the repository, and otherwise detects Claude Code, then Codex. npm `.cmd` shims are resolved to the real program so JSON arguments are not re-parsed by cmd.exe. The Stop hook already fits Codex, which uses the same hook input and answer.

Every answer schema is in strict form (each object closed with `additionalProperties: false`, every property required), which Codex requires and Claude Code accepts; examiner steps therefore come back as JSON text, parsed by `AgentExaminer.ParseProposal`.

**Consequences.** Any agent can play the roles; with no agent at all, the approver refuses (a person approves) and task start explains how to configure one. Codex runs have no budget cap and keep a read-only shell. Agents without Stop hooks are held only by their instructions and CI.

**Alternatives rejected.** Calling model APIs directly (the examiner needs an agent loop with MCP tools, which agent CLIs already provide); keeping the choice in the spec (the worker could pick its own judge).

**Files.** `Pointframe.Cli/Verification/AgentRunners.cs`, `Pointframe.Cli/Verification/Examiner.cs`, `Pointframe.Cli/Verification/Reviewer.cs`, `Pointframe.Cli/Verification/CommandApprover.cs`.
## The MCP command list resource must name every registered tool

**Rule.** `PointframeMcpResources.GetCommands()` returns `PointframeCommandCatalog.Create(...)`, which reflects over the `[McpServerTool]` methods on `PointframeMcpTools` and `DesktopTestingMcpTools` and derives each tool's snake_case identifier from its method name (or an explicit `Name` on the attribute) instead of a hand-maintained string list. Adding, renaming, or removing a `[McpServerTool]` method automatically changes the resource's output, so the resource needs no hand-kept list. The same change must still update the known-good identifier sets in `Pointframe.Tests/Mcp/DesktopTestingToolContractTests.cs`, `$expectedTools` in `packaging/test-mcp-stdio.ps1`, and the tool lists in `README.md` and `docs/mcp-desktop-testing/README.md`, which `Pointframe.Tests/DocsSync/McpToolDocumentationTests.cs` checks. The desktop-testing tools set `Name` explicitly to carry their `desktop_` prefix; the direct tools rely on the convention.

**Why.** MCP clients that call the `pointframe://commands` resource before `tools/list` use it as a cheap capability check. Before 2026-09-08 the identifiers were a hardcoded array that nothing kept in sync automatically; a new tool method compiled and worked over MCP even if the resource still listed only the older commands, silently telling callers the new capability did not exist. Reflection over the attribute removes that failure mode entirely, at the cost of assuming the MCP SDK's default tool-naming convention (PascalCase method name, `Async` suffix stripped, converted to snake_case) unless a method sets an explicit `Name`.

**Enforced by.** `Pointframe.Tests/Mcp/DesktopTestingToolContractTests.cs` asserts the reflected `DirectTools`/`DesktopTestingTools` catalogs exactly match the known-good tool identifier sets, and `packaging/test-mcp-stdio.ps1`'s `$expectedTools` list independently checks the live `tools/list` response against the same identifiers. If the MCP SDK's naming convention ever changes, or a tool method needs a name the convention would get wrong, set `Name` explicitly on that method's `[McpServerTool]` attribute.

**Symptoms when violated.** A client that gates on `pointframe://commands` never offers a tool to the user or agent even though calling it directly still succeeds — this was possible before the reflection-based rewrite; the contract tests above now catch a mismatch at build time.
