## Spec-driven verification runs

### Overview and run flow

**Responsibility.** `verify` checks a project against a spec it keeps in git (`verify.json` in its `.pointframe` folder) with no agent driving the app, and freezes a task's acceptance criteria before work starts. It turns an agent's hand-driven desktop session into a repeatable command with a verdict and an exit code. Pointframe keeps `.pointframe/verify.json` for the WinForms fixture and `.pointframe/verify-app.json` for the real WPF settings window; the latter builds the app and verifies that a saved setting survives restart.

The input contract is frozen at `schemaVersion: 1`: its fields keep their meanings, and adding, removing, or reinterpreting an input field requires schemaVersion 2 and migration notes. The loader rejects unknown fields and versions as `spec_invalid`; it does not migrate or leniently ignore them. Verdict and review output may gain fields within v1, so readers must ignore output fields they do not recognize. See [D-013](#d-013-verification-spec-v1-is-frozen) and the [frozen v1 reference](../../cli/verify-spec.md).

**Flow of `verify run`.**

1. `VerificationSpecLoader` parses the spec strictly: unknown properties and steps are rejected, every criterion needs a check naming it, and a scenario with criteria needs a negative control (the report's own pass rules, checked before anything launches). Paths resolve from the folder that holds `.pointframe/`.
2. Trust: nothing runs unless this spec's gates and app (`SpecDigests.CommandsSha256`) are approved, checked on every run and task start, so removing a gate or repointing the app needs approval again. New or changed commands go through `CommandPolicy` fixed refusals, then its exact standard-command policy (`ApprovedBy = "policy"`), then `AgentApprover`; an unavailable approver reports `approver_unavailable`, while a refusal reports `spec_untrusted`, and both direct a person to `verify trust`. After trust checks and before gates, `verify run` checks whether a process has the spec app's executable as its main module path; a match fails with `app_running` and names the PID so the user can close it before a build locks its files. Policy approves a command's form, not the behavior of its script; gate scripts can delete files, so `.pointframe/` changes need code review. See [D-009](#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands) and [D-011](#d-011-standard-commands-are-approved-by-policy). Gates: `GateRunner` runs every gate through `cmd.exe` with a log and failure details (compiler errors, failed tests, `ERROR` lines); any failed gate marks the scenarios `skipped`.
3. Scenarios: under a machine-wide named semaphore, each scenario gets its own `Pointframe.Mcp.exe --desktop-testing` process, a policy written for the spec's `app`, and with `isolation` a fresh data folder passed by environment variable (the server's launched app inherits it) or by argument, deleted afterwards. `UserSettingsService` accepts the automation settings override as either the existing file-path form or a directory, where it writes `settings.json`; the real-app spec uses directory isolation so owner settings stay untouched.
4. `DesktopScenarioRunner` sends `automationId` (or role and name) selectors straight to `desktop_invoke` and `desktop_enter_text`, retrying a missing element for up to 15 seconds, and calls the other `desktop_*` tools. Before the first step, and after every `restart`, it waits up to the same 15 seconds for an observation with at least one UI element, else the launch (or restart) step fails `NoVisibleWindow`. A `restart` step retries `TargetStillRunning` every 250 ms for up to 10 seconds, because an app's own Close returns before its process exits; each retry is a separate `desktop_restart_app` call. The runner marks wait polls, and a failed wait emits exactly one `desktop_restart_app` error event; a cancelled wait emits none. When the wait runs out, the step's message says that `restart` never closes the app and how to fix the spec: agents in trials put `restart` first to "start fresh", which can never pass. An input step whose locator matches more than one element fails `AmbiguousLocator` before any input (candidates listed; checks keep the server's evaluation). `pressKeys` focuses the target window first; if focus is refused, the step fails `FocusRequired` with foreground guidance and recommends invoke steps with role and name. `ErrorOf` reads the raw tool result: an `isError` result with only a text block becomes `ToolError` carrying that text (first 500 characters), and `ElementNotFound` for an `automationId` adds a role-and-name hint when an observed element has that name. A missing menu item adds guidance that submenu items appear in UI Automation only after their parent menu is open, and that the parent should be invoked first. The MCP worker's UI Automation `invoke` action uses an element's Invoke pattern, or its Toggle pattern when Invoke is unavailable (for example, WPF checkboxes). An invoke result with dispatch `Complete` and error code `InvokePending` is recorded as a passed delivered step because the provider accepted it; later scenario steps observe the app's resulting state. The first failed step stops the scenario; the report is always fetched and the session always ended. A scenario passes only when every step passed, the report verdict is `passed`, `DesktopProofService.Verify` accepts the bundle from disk, and cleanup succeeded.
5. The verdict (`verdict.json` in the project's artifacts\pointframe-verify folder, and standard output) carries provenance: git head, the working-tree hash computed like `verify.ps1`, the CLI version, and the MCP server's hash. A run with one or more scenarios and no gates adds a warning and `noBuildGate: true`; the app may be stale even when its scenario passes. `verify status` never marks that pass fresh (`freshnessReason: no_build_gate`), and the Stop hook blocks with a build-gate next step. `pass` exits 0, `partial` (`--scenario` or `--only`) exits 0, `fail` exits 1, a bad spec or arguments exit 2. `verify status` reports `fresh` only for a `pass` on the current tree hash and when the verdict's `specSha256` matches the selected spec file's SHA-256. With an active task it also requires the verdict task id and `snapshotSha256` to match the stored active snapshot; other reasons are `verdict_for_another_spec`, `tree_changed`, `task_not_covered`, and `verdict_for_another_task`. Status adds `activeTask`, parsed `lastStop`, and `unverifiedStop` (true only when the most recent stop was unverified on the current tree).

**Invariants.**

- Pass or fail comes only from the server's signed report and the CLI's checks; no agent and no CLI code writes a check result.
- Command approval is fixed refusals, policy for exact standard forms, the approver agent, then a person; replacing a task snapshot always needs a person at a terminal. See [D-011](#d-011-standard-commands-are-approved-by-policy), [D-009](#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands), and [D-008](#d-008-verify-approvals-need-a-person-at-a-terminal-and-live-outside-the-repository).
- A failed check carries the found value (`actual`), so a wrong expectation is visible in one run.

### Initialization, setup, and scenario import

**Initialization.** `pointframe verify init` runs from the project root and writes a starter `.pointframe/verify.json` after round-tripping it through `VerificationSpecLoader`. It detects root .NET solutions (or, with no solution and no `package.json`, a single root `*.csproj`, gated as `dotnet build <name>.csproj -c Release`) and test frameworks or supported scripts in a root `package.json`; Node commands use pnpm when `pnpm-lock.yaml` exists, yarn when `yarn.lock` exists, and npm otherwise. If multiple lockfiles exist, a recognized `packageManager` field in `package.json` selects the manager; otherwise pnpm, then yarn, then npm takes priority and init warns with the lockfiles found. A single .NET `WinExe` becomes the app candidate. App detection reads runtime identifier and platform properties from the project and applicable `Directory.Build.props`, prefers an existing framework/RID or x64 platform output, and uses the RID output path when it has not been built yet. `--explore` starts the built app through the same MCP server, `DesktopScenarioRunner`, and desktop semaphore as a verification run, polls observations for automation ids, then creates an `app-starts` scenario from the first id; when no IDs are exposed, it uses the first named element's role and name and warns about the fallback. `--mcp <file>` selects the server for exploration before the environment-variable and CLI-installed-server fallbacks. Optional Claude/Codex Stop hooks, an `AGENTS.md` instruction block, and the verification artifact ignore rule are merged idempotently. When hooks are enabled, init resolves `pointframe.exe` on PATH and runs `--version`, reporting a missing command (hook fail-open), a wrong command, a timeout, or a version mismatch in warnings/next steps. The `install` command copies a ZIP install to `%LOCALAPPDATA%\Programs\Pointframe.Cli`, adds that directory to the user PATH, and is idempotent. An existing spec is left byte-for-byte untouched unless `--force` is used, while hooks and optional onboarding files are still applied; init reports `unchanged` only when no file was written. When there is no existing spec and no gate or scenario can be generated, nothing is written.

The public onboarding guide for adopting verification in another project is [`docs/cli/verify.md`](../../cli/verify.md); its CI section describes running verification as a required check, the standard-command policy on fresh runners, spec review protection, and why desktop scenarios need an interactive runner. CLI releases, the spec schema, and the hook command have independent compatibility rules; see [D-012](#d-012-version-compatibility).

Run verdicts, status, task-start responses, and setup responses include the structured `nextStep` record (`kind`, `command`, `retryAfterSeconds`, `text`). The single mapper in `VerificationNextSteps` maps status and error code to `fix_code`, `run_command`, `wait`, `needs_person`, or `none`; the Stop hook uses its text and command in block reasons and unverified system messages, and stores it in `last-stop.json`. This is additive output under v1; the input spec remains frozen.

**Interactive tools.** `verify setup [--client claude-code|codex|vscode|all]` (`DesktopToolsApplication.SetupAsync`) approves the spec through the same pipeline, installs the MCP server with `McpPackageInstaller` only when none resolves (never touching VS Code's user config), and merges project-scoped client config that runs `pointframe mcp serve` (`ProjectMcpClientConfig`): `.mcp.json` (`mcpServers`), `config.toml` in the project's `.codex` folder (`[mcp_servers.pointframe]`, edited as text so comments and other tables stay; only `command` and `args` are replaced), `.vscode/mcp.json` (`servers`, with `--project ${workspaceFolder}`). JSON is parsed with `VsCodeMcpConfigurator.ReadJsonObject` (comments and trailing commas accepted, not kept on rewrite), a file already holding the right entry is not rewritten, and the first rewrite keeps a `.pointframe.bak`. The smoke check launches `pointframe mcp serve` through `IMcpToolClientFactory`, requires `desktop_start_test_session` in `tools/list` and the spec's app id in `desktop_list_apps` (an unbuilt app is a warning), and prints one JSON line (`status`, `filesWritten`, `filesUnchanged`, `clients`, `profileId`, `serverPath`, `serverVersion`, `serverInstalled`, `tools`, `warnings`, `nextStep`); failures carry a code (`smoke_failed`, `smoke_tools_missing`, `smoke_app_not_listed`, `mcp_install_failed`, `mcp_not_found`, `client_config_invalid`, `pointframe_not_on_path`) and the files stay written. `verify init --explore` runs the same trust check on the generated spec before it launches the app and otherwise warns and skips exploring. See [D-014](#d-014-interactive-desktop-testing-reuses-verify-trust).

**Scenario import.** `pointframe verify scenario add --from <file> [--spec <file>] [--force]` accepts the exported wrapper or a bare scenario. `VerificationApplication.AddScenarioAsync` merges it into the selected spec, refuses case-insensitive duplicate ids unless forced, round-trips the merged document through `VerificationSpecLoader` before writing, and returns `added` or `replaced` as one JSON line. The spec remains the only approval source; adding a scenario changes no command/app approval digest.

### Desktop UI checks and selector actions

Desktop UI checks preserve UI Automation inspection completeness (`WorkerUiCheckSource`). On a truncated tree (`IsTruncated`), only witnessed conclusions decide: a found element proves exists and refutes absent (the only kinds `DesktopUiCheckService` accepts at any match count). Everything else needs exactly one match and so the whole tree, including windowExists and windowAbsent, and is `inconclusive` with `error.code: InspectionIncomplete`: a missing target, apparent absence, and every state predicate and window check with fewer than two visible matches (two visible matches stay `AmbiguousTarget`), because an unseen duplicate could flip the uniqueness the predicate requires. A truncated evaluation is never inverted into a passing negative control (`MapNegativeControl`, shared by `desktop_replay_checks`). Process checks never read the tree. In `DesktopScenarioRunner` a truncated observation that lacks the element, or holds only one locator match, does not dispatch input and ends as an infrastructure failure with code `InspectionIncomplete`, never `ElementNotFound`, never an app defect and never `verification_failed` telemetry; the verdict `nextStep` then suggests a retry or a more specific `automationId` (spec v1 has no `windowRef`). Desktop check and action responses carry an optional additive `nextStep` (`kind`, `tool`, `arguments`, `retryAfterSeconds`, `reason`) from `DesktopTestingResponseMapper.RecoveryFor`. A hint with `arguments` is a complete call matching the tool's real parameters; a hint whose call needs input only the agent has (window ref, capture bounds) is guidance-only: `arguments` is null and `reason` says what to do (TargetStillRunning: close the app, `desktop_check_ui` processExited, then `desktop_restart_app`; stale observation and ElementNotFound: `desktop_observe_app`). A check whose inconclusive result stays recorded cannot be repaired inside a report-bearing session (criterion-bound check or a session with criteria), so its hint is `fresh_session` (the executable step is `desktop_get_test_report`; ending the session is guidance only, because `desktop_end_test_session` closes the app and may kill it, so the reason says to save state first and then start a new session with the same profile and criteria); otherwise it is a `diagnostic_retry` of the same check (criterionId kept) that states it cannot change the verdict. Action responses echo `actionId`. `verify setup` returns `firstCall` (`desktop_start_test_session` with the configured `profileId` and a fresh `actionId`). The `appRef` input of `desktop_start_test_session` is kept for compatibility, but the tool description and server instructions state that attaching to an already-running app is not supported.

Selector actions, chords, and observe without bounds (additive; old calls behave as before). `desktop_invoke` and `desktop_enter_text` accept either `elementRef` or a selector (`automationId`, or `role` with `name`, optionally scoped by `windowRef`); `DesktopSelectorResolver.ParseTarget` rejects both, neither, a half selector, or `windowRef` alone with `InvalidRequest` (a blank `elementRef` with nothing else keeps `ElementRequired`, and an old semantic `desktop_enter_text` that names an `observationRef` but no element keeps `ElementRequired`). A selector is resolved inside the action, against a fresh `IDesktopUiObservationProvider.Inspect` (never a cached tree), so a replayed `actionId` returns its recorded result instead of inspecting again. Exactly one visible match in a complete tree dispatches; zero is `ElementNotFound`; more than one, even in a truncated tree, is `AmbiguousTarget`; a truncated tree with fewer than two visible matches is `InspectionIncomplete` (an unseen duplicate could be the real target, so one visible match is not enough); an unavailable provider returns its own code. Each refusal is `NotStarted` and sends no input, and the actionId is spent, so the retry takes a new one. A selector click is bound to the element, not just its window: after foregrounding and releasing input, `RevalidateSelectedElement` inspects again, requires the same unique element (same automationId, role, name, and window; a moved element is clicked where it now is), and asks UI Automation (`uia.hit_test`, `IWindowsUiAutomationHitTestProvider`, the element under the point or one of its ancestors must be the selected element) whether the click point belongs to it; otherwise it refuses with `TargetChanged` or `TargetOccluded` and clicks nothing, and a missing hit-test provider fails closed. A selector `desktop_enter_text` never resolves an optional `observationRef`: it goes straight through the action ledger, so a replayed `actionId` still returns the recorded result after the observation expires, and a replayed `desktop_invoke` keeps its `method`. An omitted parameter is null; an explicitly empty or blank legacy reference keeps its old failure (`StaleObservation` for `observationRef`, `ElementRequired` for `elementRef`). `AmbiguousTarget` and `InspectionIncomplete` carry a guidance-only `nextStep`. The click, foreground, and hit-test safeguards of `desktop_invoke` are unchanged; an exported scenario step uses the selector as given (a `windowRef` makes the step unexportable, since window refs belong to one session). `desktop_enter_text` with `semanticValue: true` needs no `observationRef`, `imageRef`, `x`, or `y`, and accepts `""` (clears the field) and whitespace-only text; missing or null `text` is `InvalidRequest` before anything dispatches, and the worker's SetValue needs a string `value` (missing or null is `InvalidPayload`); `WindowsUiAutomationProvider.TrySetValue` checks null, not blank, because a blank-check thrown inside the action surfaced as `InputDispatchFailed`); coordinate typing still needs them and returns `InvalidRequest` without them, and a selector without `semanticValue` is `InvalidRequest`. `desktop_press_keys` takes `chord` (for example `Ctrl+S`: modifiers Ctrl, Shift, Alt, Win plus one letter, digit, F1 to F24, Enter, Esc, Tab, Space, Backspace, Delete, Home, End, PageUp, PageDown, or an arrow) or `virtualKeys`, exactly one; `DesktopKeyChordParser` turns the chord into the same virtual-key list (modifiers first), which then goes through the same target, foreground, and global-hotkey checks, and an unknown key or a chord and `virtualKeys` together is `InvalidRequest`, more than four keys `InvalidKeyCount`. `desktop_observe_app` makes `captureBoundsPixels` optional: omitted, it captures each visible top-level window of the target process (`IDesktopWindowBoundsProvider`, `GetWindowRect` in physical pixels clipped to the virtual screen, at most 16, so a window on a monitor with another scale needs no conversion), or fails `NoVisibleWindow`. Its optional `automationId`, `role`, `name` filter returns only the matching elements and the first element of each of their windows; `isTruncated` still reports an early-stopped walk, and the stored observation keeps the full tree so every returned `elementRef` resolves. `DesktopScenarioRunner` sends `desktop_invoke` and `desktop_enter_text` steps with the spec's selector directly, with no observation to find a ref; it retries `ElementNotFound`, `InspectionIncomplete`, and `ProviderUnavailable` with a new `actionId` each time until the 15 second element timeout, reports `AmbiguousTarget` as `AmbiguousLocator` (one attempt), and observes only after the timeout to build the ids-seen hint. `pressKeys` steps still observe to find a window. `InvalidRequest` is in `InvalidRequestCodes`. `scripts/measure-mcp-payloads.ps1` records a "first passing check" in the compact run: start, enter by selector, invoke by selector, check (the selector path) against the observe, focus, coordinate type, observe, invoke by ref, check path, with calls, bytes, token estimate, and unexpected errors per scenario; it also measures `desktop_export_scenario` before ending the main desktop session.

### Tasks, stop hook, and files

**Tasks.** `verify task start <task-file>` runs `AgentExaminer` on the configured agent (`IAgentRunner`: Claude Code, Codex, or a command; see D-010) in an empty temp folder outside the repository, with only the Pointframe MCP server, no project settings or hooks, and a JSON schema for its proposal. The CLI parses the proposal with the spec rules and runs it on the unchanged app in fail-before mode (`continueAfterFailedChecks`); `FailBefore.Evaluate` rejects it when a criterion already holds or a negative control fails. A confirmed snapshot (task text, tree hash, a hash per gate and scenario) is stored by `VerificationStore`; `verify run --task <id>` adds it as scenario `task-<id>` and lists `specChanges` since the task started.

**Stop hook.** `verify hook stop` (`VerificationHook`) answers the Stop event of Claude Code and Codex (same input and `decision: block` answer) on stdout: it reuses the last verdict when the tree hash, spec hash, and active task (id and snapshot hash) are unchanged (a question-only turn costs nothing, an unchanged failure keeps blocking), otherwise runs `verify run` with the active task in-process. A failure the agent can fix returns `decision: block` with the failed gate details or `Expected ..., found ...`, ending with `Next step: ...`; a failure only a person can fix and the `--max-blocks` limit (default 5, counted per session in `hook-state.json`) let the agent stop with a `systemMessage`. Each allowed stop writes `last-stop.json` beside hook state with outcome, reason (`no_verdict`, `needs_person`, `block_limit`, or `hook_error`), error code, `nextStep`, tree/spec hashes, task id, and UTC time; a pass records `verified`, other allowed stops record `unverified` and their message starts `UNVERIFIED:` and includes the next step. A crash records `hook_error` best-effort. With `--review`, a pass on a tree not yet in `review.json` is followed by `AgentReviewer` (no MCP tools, the diff since the task's commit through a throwaway index), whose flags go to `review.json` and the person, never to the verdict. An `AgentException` is retried once; a final failure is recorded in `review.json` with `treeHash`, `baseCommit`, `failed`, and `error`, and is considered reviewed for that tree so it is reported once. `verify status` includes the resolved hook command, current tree's review state, and last stop record. The hook must run an installed or copied CLI: a running `Pointframe.Cli.exe` locks the output a project's build gate rebuilds.

## D-007 `verify run` drives the MCP server instead of sharing an Engine service

**Decided.** 2026-10-03.

**Context.** The plan was to move the act/check/record logic out of `DesktopTestingMcpTools` into `Pointframe.Engine` so the CLI could call it directly. But the UI Automation backend (FlaUI, the worker process, input) lives in `Pointframe.Mcp`, which the CLI does not reference.

**Decision.** The CLI is an MCP client: it starts `Pointframe.Mcp.exe` with a generated policy and calls the same `desktop_*` tools an agent calls.

**Consequences.** One implementation of sessions, checks, evidence, and signing; a CLI run and an agent session produce the same report, and every `verify run` exercises the agent path. The cost is a child process per run and a JSON boundary: a tool's argument or response change must be mirrored in `DesktopScenarioRunner`.

**Alternatives rejected.** Moving the backend and orchestration into the Engine (a large refactor of FlaUI and worker code, with two hosts to keep in step); referencing `Pointframe.Mcp` from the CLI (pulls the MCP host and FlaUI into the CLI package).

**Files.** `Pointframe.Cli/Verification/DesktopScenarioRunner.cs`, `Pointframe.Cli/Verification/McpStdioToolClient.cs`, `Pointframe.Mcp/Tools/DesktopTestingMcpTools.cs`.

## D-008 Verify approvals need a person at a terminal and live outside the repository

Superseded by D-009 for the approval of gate and app commands; it still holds for replacing a task snapshot and for where approvals are stored.

**Decided.** 2026-10-03.

**Context.** Gate commands run with the user's permissions, and a task's frozen criteria are what the worker agent is graded against. The worker runs as the same Windows user with a shell, so any plain approve command or `--yes` flag is one it can use itself.

**Decision.** `verify trust` and `verify task start --replace` approve only after a person types `yes` at an interactive terminal (`ConsoleConfirmation` refuses redirected input), with no flag to skip it. Approvals and task snapshots live under `%LOCALAPPDATA%\Pointframe\verify`, keyed by project folder, not in the repository. New criteria come from the examiner agent, never from the worker.

**Consequences.** An agent cannot approve its own gates or app, remove gates, or replace its own criteria through the CLI, and editing the repository does not change them. This is a consent boundary, not a sandbox: a worker with unrestricted file access could still edit the store, which only a sandbox that limits writes to the workspace prevents. Non-interactive CI needs its own trust mechanism (planned with CI support).

**Alternatives rejected.** An `ask` permission rule on the approve command (only Claude Code honours it); storing approvals in the repository (the worker can edit them); a `--yes` flag (the worker can pass it).

**Files.** `Pointframe.Cli/Verification/VerificationStore.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`.

## D-009 An approver agent behind fixed rules approves verify commands

Partly superseded by D-011 for standard commands.

**Decided.** 2026-10-04.

**Context.** Under D-008 every new or changed gate or app command waited for a person at a terminal. The owner wants agents to work autonomously and rejected a human step in the normal flow. Claude Code's auto-mode classifier refused to replace the person with an agent until the owner allowed it explicitly in the permission settings.

**Decision.** New or changed commands first face `CommandPolicy` fixed refusals (the app is a program inside the project and not a shell; working folders are inside the project; no URLs, network shares, download tools, deletes, encoded or inline payloads, system changes, or environment paths). Commands outside D-011's standard forms then go to `AgentApprover`: a separate run of the configured agent (D-010) started by the CLI, with no MCP tools and no project settings, that sees only the commands and the previously approved ones, treats them as untrusted data, and refuses when in doubt. Its yes is stored like a person's, with `ApprovedBy` and its reason; a person (`verify trust`) is needed after a refusal or an unavailable approver.

**Consequences.** Normal work never waits for a person. The approver can be talked into a wrong yes by text crafted for it; the fixed rules are the backstop for dangerous cases, and the verdict's `provenance.commandsApprovedBy` identifies an agent approval. An unavailable agent is distinguished from its refusal so the person knows the command was not judged.

**Alternatives rejected.** A person for every change (D-008: blocks autonomy); treating commands committed in HEAD as approved (blocked by the permission layer, and unsafe in cloned repositories and in workflows where agents commit); an approver without fixed rules (one wrong yes could run anything).

**Files.** `Pointframe.Cli/Verification/CommandApprover.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Cli/Verification/VerificationStore.cs`.

## D-011 Standard commands are approved by policy

**Decided.** 2026-10-04.

**Context.** M1 was blocked because a clean .NET project's `verify run` depended on an approver agent reaching its model API; the sandbox returned `ConnectionRefused` before the normal build gate could run. `verify init` emits a small set of conventional build and check commands.

**Decision.** `CommandPolicy.IsStandard` approves only command text that parses exactly as the supported `dotnet build|test|format|restore`, npm/pnpm/yarn test/install/run, or PowerShell project-script forms, with relative in-project paths, allowed options, and no shell metacharacters. When every gate is standard and the app passes its existing fixed rules with metacharacter-free arguments, `EnsureTrustedAsync` stores approval with `ApprovedBy = "policy"`. Any nonstandard command remains with the approver agent, then a person. This approves the command text only, not the behavior of the project's code it runs.

**Consequences.** Standard verification is offline and costs no agent call. A grammar change is a policy change and needs focused classification tests. `approver_unavailable` distinguishes missing or failing infrastructure from a real refusal (`spec_untrusted`); the Stop hook lets an agent stop and tells a person how to restore approval. Policy is intentionally narrow and does not sandbox gate processes.

**Alternatives rejected.** A structured command schema (requires changing the spec contract and generated forms); an offline human baseline (still blocks clean projects on a person); an approval service (adds an online dependency); a signed manifest (adds a signing and distribution lifecycle).

**Files.** `Pointframe.Cli/Verification/CommandApprover.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Cli/Verification/VerificationHook.cs`, `Pointframe.Tests/Cli/CommandApprovalTests.cs`, `Pointframe.Tests/Cli/VerificationHookTests.cs`, `Pointframe.Tests/Cli/VerificationInitTests.cs`, `docs/cli/README.md`.

## D-012 Version compatibility

**Decided.** 2026-10-04.

**Decision.** CLI release numbers, the spec's `schemaVersion`, and the hook command are independent. An unknown `schemaVersion` is rejected as `spec_invalid`; the CLI never silently migrates an unknown schema. The hook command `pointframe verify hook stop [--review]` is a stable contract across CLI upgrades. A CLI/hook version mismatch produces a warning only. For the CLI-installed fallback, a server older than the CLI is updated from the CLI's own stable release or refused with `mcp_version_mismatch`; a newer server is used with a warning. Every CLI install of the server (`mcp install`, the `verify run` fallback, the older-server update) downloads the CLI's own release (`releases/download/v<version>/`, build metadata stripped); a release missing the asset fails with `mcp_release_asset_missing` and never falls back to latest, and every other build uses `latest`: the versioned release is chosen only when the CLI carries the `PointframeReleaseBuild` assembly metadata (set by `packaging/build-cli-package.ps1`) and a stable `x.y.z` version other than `0.0.0`, because a plain source build reports `1.0.0+<hash>` (amended 2026-10-17: a CLI pinned to 6.7.123 installed MCP 6.7.124 from `latest`, and every pinned trial scored invalid). Explicit server paths and `POINTFRAME_MCP_EXECUTABLE` are honored as chosen, with a stderr warning when that server's file version is older than the CLI (a stale variable from an old install silently ran a 6.7.71 server under CLI 6.7.85 in 2026-10 trials).

**Alternatives rejected.** Lockstep numbering; silent acceptance of unknown fields; automatic migrations; a version negotiation protocol.

**Files.** `Pointframe.Cli/Verification/VerificationSpecLoader.cs`, `Pointframe.Cli/Commands/CliCommandParser.cs`, `Pointframe.Cli/Verification/VerificationInit.cs`, `Pointframe.Cli/Verification/VerificationApplication.cs`, `Pointframe.Tests/Cli/McpServerVersionTests.cs`, `Pointframe.Tests/Cli/VerificationRunTests.cs`, `Pointframe.Tests/Cli/VerificationInitTests.cs`, `Pointframe.Tests/Cli/VerificationTests.cs`.

See [D-013](#d-013-verification-spec-v1-is-frozen) for the frozen input contract and output compatibility rule.

## D-013 Verification spec v1 is frozen

**Decided.** 2026-10-04.

**Context.** Projects keep verification specs in source control, and tools need predictable input and output compatibility across CLI releases.

**Decision.** `schemaVersion: 1` is frozen: existing input fields keep their meanings, and no field is added, removed, or reinterpreted under version 1. A change to the input contract requires `schemaVersion: 2` and migration notes. The loader rejects unknown fields and versions with `spec_invalid`. Verdict and review output may gain fields while remaining version 1; consumers must ignore fields they do not recognize.

**Consequences.** A misspelled or newer input field fails before any command runs, so the user must update the spec or CLI deliberately. Output consumers can read fields they understand without failing when a later CLI adds fields.

**Alternatives rejected.** Lenient handling of unknown input fields would let typos change verification silently. Automatic migration would change a project's checked-in input without an explicit review.

**Files.** `Pointframe.Cli/Verification/VerificationSpecLoader.cs`, `Pointframe.Cli/Verification/VerificationSpec.cs`, `Pointframe.Cli/Verification/VerificationResults.cs`, `Pointframe.Tests/Cli/VerificationSpecV1CompatibilityTests.cs`, `docs/cli/verify-spec.md`. See [Spec-driven verification runs](#spec-driven-verification-runs) and [D-012](#d-012-version-compatibility).

## D-014 Interactive desktop testing reuses verify trust

**Decided.** 2026-10-05.

**Context.** A coding agent in another project needed a hand-written policy file and a manual `--desktop-testing --desktop-policy` registration to get interactive desktop tools. A policy file the agent writes would let it choose what the server may launch.

**Decision.** The CLI is the front door and the spec is the source: `pointframe mcp serve` builds the desktop policy from the project's `.pointframe/verify.json` `app` after the same trust check as `verify run` (D-008, D-009, D-011 semantics unchanged: the commands digest, fixed refusals, standard-command policy, approver agent, a person only through `verify trust`), and `pointframe verify setup` writes the project-scoped client config that runs it. The policy lives outside the repository under the verify store, keyed by the project path. Containment is decided on the resolved path, so a junction cannot lead the app out of the project. Isolation from the spec is honoured with a temporary data folder deleted on exit. `verify init --explore` needs the same trust before it launches the app.

**Consequences.** One command replaces the policy file and the registration. Changing the app or any gate stops the server from starting until it is approved again. A config that depends on the CLI being on `PATH` fails with `pointframe_not_on_path` at setup rather than silently later. `mcp serve` never asks a person, so first approval of a nonstandard spec happens in `verify trust` or `verify setup` with an approver.

**Alternatives rejected.** A policy file kept in the repository (an agent could edit what it may launch); a separate trust store for interactive tools (two approvals for one command); user-scope client config (it would apply to every project).

**Files.** `Pointframe.Cli/Verification/DesktopToolsApplication.cs`, `Pointframe.Cli/Verification/PathContainment.cs`, `Pointframe.Cli/McpManagement/ProjectMcpClientConfig.cs`, `Pointframe.Cli/McpManagement/McpServerHost.cs`, `Pointframe.Tests/Cli/DesktopToolsTests.cs`. See [Spec-driven verification runs](#spec-driven-verification-runs), [D-008](#d-008-verify-approvals-need-a-person-at-a-terminal-and-live-outside-the-repository), [D-009](#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands), [D-011](#d-011-standard-commands-are-approved-by-policy).

## D-010 Verify's agent roles run on any agent

**Decided.** 2026-10-04.

**Context.** The examiner, reviewer, and approver were hard-wired to `claude -p`, so a team using Codex or another agent could not use them. The owner wants verify usable with any agent.

**Decision.** The roles (instructions, answer schema, how the answer is checked) are separate from how an agent is started. `IAgentRunner` has three implementations: `ClaudeCodeAgentRunner` (`claude -p`, system prompt, built-in tools off, budget cap, `structured_output`), `CodexAgentRunner` (`codex --ask-for-approval never exec -`, instructions leading the prompt, `--output-schema`, `-o`, read-only sandbox, `--ephemeral`, MCP through `-c mcp_servers...` with `default_tools_approval_mode=approve` for that one server), and `CommandAgentRunner` (any program, with `{prompt_file}`, `{schema_file}`, `{output_file}`, `{mcp_config_file}` placeholders). `AgentSelection` reads the choice from the person's profile (`agent.json` under `%LOCALAPPDATA%\Pointframe\verify`), not the repository, and otherwise detects Claude Code, then Codex. npm `.cmd` shims are resolved to the real program so JSON arguments are not re-parsed by cmd.exe. The Stop hook already fits Codex, which uses the same hook input and answer.

Every answer schema is in strict form (each object closed with `additionalProperties: false`, every property required), which Codex requires and Claude Code accepts; examiner steps therefore come back as JSON text, parsed by `AgentExaminer.ParseProposal`.

**Consequences.** Any agent can play the roles; with no agent at all, the approver refuses (a person approves) and task start explains how to configure one. Codex runs have no budget cap and keep a read-only shell. Agents without Stop hooks are held only by their instructions and CI.

**Alternatives rejected.** Calling model APIs directly (the examiner needs an agent loop with MCP tools, which agent CLIs already provide); keeping the choice in the spec (the worker could pick its own judge).

**Files.** `Pointframe.Cli/Verification/AgentRunners.cs`, `Pointframe.Cli/Verification/Examiner.cs`, `Pointframe.Cli/Verification/Reviewer.cs`, `Pointframe.Cli/Verification/CommandApprover.cs`.
