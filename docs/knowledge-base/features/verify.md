## Spec-driven verification runs

### Overview and run flow

**Responsibility.** `verify` checks a project against a spec it keeps in git (`verify.json` in its `.pointframe` folder) with no agent driving the app, and freezes a task's acceptance criteria before work starts. It turns an agent's hand-driven desktop session into a repeatable command with a verdict and an exit code. Pointframe keeps `.pointframe/verify.json` for the WinForms fixture and `.pointframe/verify-app.json` for the real WPF settings window; the latter builds the app and verifies that a saved setting survives restart.

The input contract is frozen at `schemaVersion: 1`: its fields keep their meanings, and adding, removing, or reinterpreting an input field requires schemaVersion 2 and migration notes. The loader rejects unknown fields and versions as `spec_invalid`; it does not migrate or leniently ignore them. Verdict and review output may gain fields within v1, so readers must ignore output fields they do not recognize. See [D-013](verify-decisions.md#d-013-verification-spec-v1-is-frozen) and the [frozen v1 reference](../../cli/verify-spec.md).

**Flow of `verify run`.**

1. `VerificationSpecLoader` parses the spec strictly: unknown properties and steps are rejected, every criterion needs a check naming it, and a scenario with criteria needs a negative control (the report's own pass rules, checked before anything launches). Paths resolve from the folder that holds `.pointframe/`.
2. Trust: nothing runs unless this spec's gates and app (`SpecDigests.CommandsSha256`) are approved, checked on every run and task start, so removing a gate or repointing the app needs approval again. New or changed commands go through `CommandPolicy` fixed refusals, then its exact standard-command policy (`ApprovedBy = "policy"`), then `AgentApprover`; an unavailable approver reports `approver_unavailable`, while a refusal reports `spec_untrusted`, and both direct a person to `verify trust`. After trust checks and before gates, `verify run` checks whether a process has the spec app's executable as its main module path; a match fails with `app_running` and names the PID so the user can close it before a build locks its files. Policy approves a command's form, not the behavior of its script; gate scripts can delete files, so `.pointframe/` changes need code review. See [D-009](verify-decisions.md#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands) and [D-011](verify-decisions.md#d-011-standard-commands-are-approved-by-policy). Gates: `GateRunner` runs every gate through `cmd.exe` with a log and failure details (compiler errors, failed tests, `ERROR` lines); any failed gate marks the scenarios `skipped`.
3. Scenarios: under a machine-wide named semaphore, each scenario gets its own `Pointframe.Mcp.exe --desktop-testing` process, a policy written for the spec's `app`, and with `isolation` a fresh data folder passed by environment variable (the server's launched app inherits it) or by argument, deleted afterwards. `UserSettingsService` accepts the automation settings override as either the existing file-path form or a directory, where it writes `settings.json`; the real-app spec uses directory isolation so owner settings stay untouched.
4. `DesktopScenarioRunner` sends `automationId` (or role and name) selectors straight to `desktop_invoke` and `desktop_enter_text`, retrying a missing element for up to 15 seconds, and calls the other `desktop_*` tools. Before the first step, and after every `restart`, it waits up to the same 15 seconds for an observation with at least one UI element, else the launch (or restart) step fails `NoVisibleWindow`. A `restart` step retries `TargetStillRunning` every 250 ms for up to 10 seconds, because an app's own Close returns before its process exits; each retry is a separate `desktop_restart_app` call. The runner marks wait polls, and a failed wait emits exactly one `desktop_restart_app` error event; a cancelled wait emits none. When the wait runs out, the step's message says that `restart` never closes the app and how to fix the spec: agents in trials put `restart` first to "start fresh", which can never pass. An input step whose locator matches more than one element fails `AmbiguousLocator` before any input (candidates listed; checks keep the server's evaluation). `pressKeys` focuses the target window first; if focus is refused, the step fails `FocusRequired` with foreground guidance and recommends invoke steps with role and name. `ErrorOf` reads the raw tool result: an `isError` result with only a text block becomes `ToolError` carrying that text (first 500 characters), and `ElementNotFound` for an `automationId` adds a role-and-name hint when an observed element has that name. A missing menu item adds guidance that submenu items appear in UI Automation only after their parent menu is open, and that the parent should be invoked first. The MCP worker's UI Automation `invoke` action uses an element's Invoke pattern, or its Toggle pattern when Invoke is unavailable (for example, WPF checkboxes). An invoke result with dispatch `Complete` and error code `InvokePending` is recorded as a passed delivered step because the provider accepted it; later scenario steps observe the app's resulting state. The first failed step stops the scenario; the report is always fetched and the session always ended. A scenario passes only when every step passed, the report verdict is `passed`, `DesktopProofService.Verify` accepts the bundle from disk, and cleanup succeeded.
5. The verdict (`verdict.json` in the project's artifacts\pointframe-verify folder, and standard output) carries provenance: git head, the working-tree hash computed like `verify.ps1`, the CLI version, and the MCP server's hash. A run with one or more scenarios and no gates adds a warning and `noBuildGate: true`; the app may be stale even when its scenario passes. `verify status` never marks that pass fresh (`freshnessReason: no_build_gate`), and the Stop hook blocks with a build-gate next step. `pass` exits 0, `partial` (`--scenario` or `--only`) exits 0, `fail` exits 1, a bad spec or arguments exit 2. `verify status` reports `fresh` only for a `pass` on the current tree hash and when the verdict's `specSha256` matches the selected spec file's SHA-256. With an active task it also requires the verdict task id and `snapshotSha256` to match the stored active snapshot; other reasons are `verdict_for_another_spec`, `tree_changed`, `task_not_covered`, and `verdict_for_another_task`. Status adds `activeTask`, parsed `lastStop`, and `unverifiedStop` (true only when the most recent stop was unverified on the current tree).

**Invariants.**

- Pass or fail comes only from the server's signed report and the CLI's checks; no agent and no CLI code writes a check result.
- Command approval is fixed refusals, policy for exact standard forms, the approver agent, then a person; replacing a task snapshot always needs a person at a terminal. See [D-011](verify-decisions.md#d-011-standard-commands-are-approved-by-policy), [D-009](verify-decisions.md#d-009-an-approver-agent-behind-fixed-rules-approves-verify-commands), and [D-008](verify-decisions.md#d-008-verify-approvals-need-a-person-at-a-terminal-and-live-outside-the-repository).
- A failed check carries the found value (`actual`), so a wrong expectation is visible in one run.

### Initialization, setup, and scenario import

**Initialization.** `pointframe verify init` runs from the project root and writes a starter `.pointframe/verify.json` after round-tripping it through `VerificationSpecLoader`. It detects root .NET solutions (or, with no solution and no `package.json`, a single root `*.csproj`, gated as `dotnet build <name>.csproj -c Release`) and test frameworks or supported scripts in a root `package.json`; Node commands use pnpm when `pnpm-lock.yaml` exists, yarn when `yarn.lock` exists, and npm otherwise. If multiple lockfiles exist, a recognized `packageManager` field in `package.json` selects the manager; otherwise pnpm, then yarn, then npm takes priority and init warns with the lockfiles found. A single .NET `WinExe` becomes the app candidate. App detection reads runtime identifier and platform properties from the project and applicable `Directory.Build.props`, prefers an existing framework/RID or x64 platform output, and uses the RID output path when it has not been built yet. `--explore` starts the built app through the same MCP server, `DesktopScenarioRunner`, and desktop semaphore as a verification run, polls observations for automation ids, then creates an `app-starts` scenario from the first id; when no IDs are exposed, it uses the first named element's role and name and warns about the fallback. `--mcp <file>` selects the server for exploration before the environment-variable and CLI-installed-server fallbacks. Optional Claude/Codex Stop hooks, an `AGENTS.md` instruction block, and the verification artifact ignore rule are merged idempotently. When hooks are enabled, init resolves `pointframe.exe` on PATH and runs `--version`, reporting a missing command (hook fail-open), a wrong command, a timeout, or a version mismatch in warnings/next steps. The `install` command copies a ZIP install to `%LOCALAPPDATA%\Programs\Pointframe.Cli`, adds that directory to the user PATH, and is idempotent. An existing spec is left byte-for-byte untouched unless `--force` is used, while hooks and optional onboarding files are still applied; init reports `unchanged` only when no file was written. When there is no existing spec and no gate or scenario can be generated, nothing is written.

The public onboarding guide for adopting verification in another project is [`docs/cli/verify.md`](../../cli/verify.md); its CI section describes running verification as a required check, the standard-command policy on fresh runners, spec review protection, and why desktop scenarios need an interactive runner. CLI releases, the spec schema, and the hook command have independent compatibility rules; see [D-012](verify-decisions.md#d-012-version-compatibility).

Run verdicts, status, task-start responses, and setup responses include the structured `nextStep` record (`kind`, `command`, `retryAfterSeconds`, `text`). The single mapper in `VerificationNextSteps` maps status and error code to `fix_code`, `run_command`, `wait`, `needs_person`, or `none`; the Stop hook uses its text and command in block reasons and unverified system messages, and stores it in `last-stop.json`. This is additive output under v1; the input spec remains frozen.

**Interactive tools.** `verify setup [--client claude-code|codex|vscode|all]` (`DesktopToolsApplication.SetupAsync`) approves the spec through the same pipeline, installs the MCP server with `McpPackageInstaller` only when none resolves (never touching VS Code's user config), and merges project-scoped client config that runs `pointframe mcp serve` (`ProjectMcpClientConfig`): `.mcp.json` (`mcpServers`), `config.toml` in the project's `.codex` folder (`[mcp_servers.pointframe]`, edited as text so comments and other tables stay; only `command` and `args` are replaced), `.vscode/mcp.json` (`servers`, with `--project ${workspaceFolder}`). JSON is parsed with `VsCodeMcpConfigurator.ReadJsonObject` (comments and trailing commas accepted, not kept on rewrite), a file already holding the right entry is not rewritten, and the first rewrite keeps a `.pointframe.bak`. The smoke check launches `pointframe mcp serve` through `IMcpToolClientFactory`, requires `desktop_start_test_session` in `tools/list` and the spec's app id in `desktop_list_apps` (an unbuilt app is a warning), and prints one JSON line (`status`, `filesWritten`, `filesUnchanged`, `clients`, `profileId`, `serverPath`, `serverVersion`, `serverInstalled`, `tools`, `warnings`, `nextStep`); failures carry a code (`smoke_failed`, `smoke_tools_missing`, `smoke_app_not_listed`, `mcp_install_failed`, `mcp_not_found`, `client_config_invalid`, `pointframe_not_on_path`) and the files stay written. `verify init --explore` runs the same trust check on the generated spec before it launches the app and otherwise warns and skips exploring. See [D-014](verify-decisions.md#d-014-interactive-desktop-testing-reuses-verify-trust).

**Scenario import.** `pointframe verify scenario add --from <file> [--spec <file>] [--force]` accepts the exported wrapper or a bare scenario. `VerificationApplication.AddScenarioAsync` merges it into the selected spec, refuses case-insensitive duplicate ids unless forced, round-trips the merged document through `VerificationSpecLoader` before writing, and returns `added` or `replaced` as one JSON line. The spec remains the only approval source; adding a scenario changes no command/app approval digest.

### Desktop UI checks and selector actions

Desktop UI checks preserve UI Automation inspection completeness (`WorkerUiCheckSource`). On a truncated tree (`IsTruncated`), only witnessed conclusions decide: a found element proves exists and refutes absent (the only kinds `DesktopUiCheckService` accepts at any match count). Everything else needs exactly one match and so the whole tree, including windowExists and windowAbsent, and is `inconclusive` with `error.code: InspectionIncomplete`: a missing target, apparent absence, and every state predicate and window check with fewer than two visible matches (two visible matches stay `AmbiguousTarget`), because an unseen duplicate could flip the uniqueness the predicate requires. A truncated evaluation is never inverted into a passing negative control (`MapNegativeControl`, shared by `desktop_replay_checks`). Process checks never read the tree. In `DesktopScenarioRunner` a truncated observation that lacks the element, or holds only one locator match, does not dispatch input and ends as an infrastructure failure with code `InspectionIncomplete`, never `ElementNotFound`, never an app defect and never `verification_failed` telemetry; the verdict `nextStep` then suggests a retry or a more specific `automationId` (spec v1 has no `windowRef`). Desktop check and action responses carry an optional additive `nextStep` (`kind`, `tool`, `arguments`, `retryAfterSeconds`, `reason`) from `DesktopTestingResponseMapper.RecoveryFor`. A hint with `arguments` is a complete call matching the tool's real parameters; a hint whose call needs input only the agent has (window ref, capture bounds) is guidance-only: `arguments` is null and `reason` says what to do (TargetStillRunning: close the app, `desktop_check_ui` processExited, then `desktop_restart_app`; stale observation and ElementNotFound: `desktop_observe_app`). A check whose inconclusive result stays recorded cannot be repaired inside a report-bearing session (criterion-bound check or a session with criteria), so its hint is `fresh_session` (the executable step is `desktop_get_test_report`; ending the session is guidance only, because `desktop_end_test_session` closes the app and may kill it, so the reason says to save state first and then start a new session with the same profile and criteria); otherwise it is a `diagnostic_retry` of the same check (criterionId kept) that states it cannot change the verdict. Action responses echo `actionId`. `verify setup` returns `firstCall` (`desktop_start_test_session` with the configured `profileId` and a fresh `actionId`). The `appRef` input of `desktop_start_test_session` is kept for compatibility, but the tool description and server instructions state that attaching to an already-running app is not supported.

Selector actions, chords, and observe without bounds (additive; old calls behave as before). `desktop_invoke` and `desktop_enter_text` accept either `elementRef` or a selector (`automationId`, or `role` with `name`, optionally scoped by `windowRef`); `DesktopSelectorResolver.ParseTarget` rejects both, neither, a half selector, or `windowRef` alone with `InvalidRequest` (a blank `elementRef` with nothing else keeps `ElementRequired`, and an old semantic `desktop_enter_text` that names an `observationRef` but no element keeps `ElementRequired`). A selector is resolved inside the action, against a fresh `IDesktopUiObservationProvider.Inspect` (never a cached tree), so a replayed `actionId` returns its recorded result instead of inspecting again. Exactly one visible match in a complete tree dispatches; zero is `ElementNotFound`; more than one, even in a truncated tree, is `AmbiguousTarget`; a truncated tree with fewer than two visible matches is `InspectionIncomplete` (an unseen duplicate could be the real target, so one visible match is not enough); an unavailable provider returns its own code. Each refusal is `NotStarted` and sends no input, and the actionId is spent, so the retry takes a new one. A selector click is bound to the element, not just its window: after foregrounding and releasing input, `RevalidateSelectedElement` inspects again, requires the same unique element (same automationId, role, name, and window; a moved element is clicked where it now is), and asks UI Automation (`uia.hit_test`, `IWindowsUiAutomationHitTestProvider`, the element under the point or one of its ancestors must be the selected element) whether the click point belongs to it; otherwise it refuses with `TargetChanged` or `TargetOccluded` and clicks nothing, and a missing hit-test provider fails closed. A selector `desktop_enter_text` never resolves an optional `observationRef`: it goes straight through the action ledger, so a replayed `actionId` still returns the recorded result after the observation expires, and a replayed `desktop_invoke` keeps its `method`. An omitted parameter is null; an explicitly empty or blank legacy reference keeps its old failure (`StaleObservation` for `observationRef`, `ElementRequired` for `elementRef`). `AmbiguousTarget` and `InspectionIncomplete` carry a guidance-only `nextStep`. The click, foreground, and hit-test safeguards of `desktop_invoke` are unchanged; an exported scenario step uses the selector as given (a `windowRef` makes the step unexportable, since window refs belong to one session). `desktop_enter_text` with `semanticValue: true` needs no `observationRef`, `imageRef`, `x`, or `y`, and accepts `""` (clears the field) and whitespace-only text; missing or null `text` is `InvalidRequest` before anything dispatches, and the worker's SetValue needs a string `value` (missing or null is `InvalidPayload`); `WindowsUiAutomationProvider.TrySetValue` checks null, not blank, because a blank-check thrown inside the action surfaced as `InputDispatchFailed`); coordinate typing still needs them and returns `InvalidRequest` without them, and a selector without `semanticValue` is `InvalidRequest`. `desktop_press_keys` takes `chord` (for example `Ctrl+S`: modifiers Ctrl, Shift, Alt, Win plus one letter, digit, F1 to F24, Enter, Esc, Tab, Space, Backspace, Delete, Home, End, PageUp, PageDown, or an arrow) or `virtualKeys`, exactly one; `DesktopKeyChordParser` turns the chord into the same virtual-key list (modifiers first), which then goes through the same target, foreground, and global-hotkey checks, and an unknown key or a chord and `virtualKeys` together is `InvalidRequest`, more than four keys `InvalidKeyCount`. `desktop_observe_app` makes `captureBoundsPixels` optional: omitted, it captures each visible top-level window of the target process (`IDesktopWindowBoundsProvider`, `GetWindowRect` in physical pixels clipped to the virtual screen, at most 16, so a window on a monitor with another scale needs no conversion), or fails `NoVisibleWindow`. Its optional `automationId`, `role`, `name` filter returns only the matching elements and the first element of each of their windows; `isTruncated` still reports an early-stopped walk, and the stored observation keeps the full tree so every returned `elementRef` resolves. `DesktopScenarioRunner` sends `desktop_invoke` and `desktop_enter_text` steps with the spec's selector directly, with no observation to find a ref; it retries `ElementNotFound`, `InspectionIncomplete`, and `ProviderUnavailable` with a new `actionId` each time until the 15 second element timeout, reports `AmbiguousTarget` as `AmbiguousLocator` (one attempt), and observes only after the timeout to build the ids-seen hint. `pressKeys` steps still observe to find a window. `InvalidRequest` is in `InvalidRequestCodes`. `scripts/measure-mcp-payloads.ps1` records a "first passing check" in the compact run: start, enter by selector, invoke by selector, check (the selector path) against the observe, focus, coordinate type, observe, invoke by ref, check path, with calls, bytes, token estimate, and unexpected errors per scenario; it also measures `desktop_export_scenario` before ending the main desktop session.

### Tasks, stop hook, and files

**Tasks.** `verify task start <task-file>` runs `AgentExaminer` on the configured agent (`IAgentRunner`: Claude Code, Codex, or a command; see D-010) in an empty temp folder outside the repository, with only the Pointframe MCP server, no project settings or hooks, and a JSON schema for its proposal. The CLI parses the proposal with the spec rules and runs it on the unchanged app in fail-before mode (`continueAfterFailedChecks`); `FailBefore.Evaluate` rejects it when a criterion already holds or a negative control fails. A confirmed snapshot (task text, tree hash, a hash per gate and scenario) is stored by `VerificationStore`; `verify run --task <id>` adds it as scenario `task-<id>` and lists `specChanges` since the task started.

**Stop hook.** `verify hook stop` (`VerificationHook`) answers the Stop event of Claude Code and Codex (same input and `decision: block` answer) on stdout: it reuses the last verdict when the tree hash, spec hash, and active task (id and snapshot hash) are unchanged (a question-only turn costs nothing, an unchanged failure keeps blocking), otherwise runs `verify run` with the active task in-process. A failure the agent can fix returns `decision: block` with the failed gate details or `Expected ..., found ...`, ending with `Next step: ...`; a failure only a person can fix and the `--max-blocks` limit (default 5, counted per session in `hook-state.json`) let the agent stop with a `systemMessage`. Each allowed stop writes `last-stop.json` beside hook state with outcome, reason (`no_verdict`, `needs_person`, `block_limit`, or `hook_error`), error code, `nextStep`, tree/spec hashes, task id, and UTC time; a pass records `verified`, other allowed stops record `unverified` and their message starts `UNVERIFIED:` and includes the next step. A crash records `hook_error` best-effort. With `--review`, a pass on a tree not yet in `review.json` is followed by `AgentReviewer` (no MCP tools, the diff since the task's commit through a throwaway index), whose flags go to `review.json` and the person, never to the verdict. An `AgentException` is retried once; a final failure is recorded in `review.json` with `treeHash`, `baseCommit`, `failed`, and `error`, and is considered reviewed for that tree so it is reported once. `verify status` includes the resolved hook command, current tree's review state, and last stop record. The hook must run an installed or copied CLI: a running `Pointframe.Cli.exe` locks the output a project's build gate rebuilds.
