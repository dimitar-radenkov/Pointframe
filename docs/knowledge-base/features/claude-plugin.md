## Claude plugin

`plugin/pointframe/` is a Claude plugin, shaped for the Anthropic plugin directory: a manifest (`plugin.json` in the `.claude-plugin` folder), `.mcp.json`, `README.md`, `LICENSE`, `server.lock.json`, the launcher `plugin/pointframe/scripts/start-mcp.cmd`, the start script, `plugin/pointframe/.claude-plugin/icon.png` (copy of `packaging/assets/mcp-icon.png`, the one binary the directory wants), and three skills: `verify-desktop-work`, `create-desktop-verification-skill`, and `capture-screen`. The embedded guide `Pointframe.Mcp/Guides/verify-desktop-work.md` is the only hand-edited copy of the desktop verification recipe: `scripts/sync-agent-guides.ps1` writes it as the `verify-desktop-work` skill body (front matter kept) and as `plugin/pointframe/skills/create-desktop-verification-skill/references/recipe.md`; it also copies `docs/cli/verify-spec.md` to `plugin/pointframe/skills/create-desktop-verification-skill/references/verify-spec.md`, so an agent with only the skill folder has the spec schema and never fetches docs from the web (the first gate trial lost four calls fetching it from a wrong branch). Its marked "Short path for coding agents" region (`<!-- short-path:begin -->` ... `end`) is also copied into marked regions of `README.md`, `docs/cli/verify.md` and `website/llms.txt`, so agents that learn Pointframe from the web read the same install, init, scenario, skill-format (`verify-<app>` folder and name, `features/` with the four exact H2s, files written before the run) and run-last steps; a new target needs the markers and an entry in `$RegionTargets`. The first ```json block of the guide must stay a complete spec (a test loads it); fragments use `jsonc`. `check-agent-discovery.ps1` also requires the step 1 and short-path install commands to be identical and present in every public copy, and fails on drift, so the MCP guide, the plugin and a skills-only install never teach different steps. Keep every other file a small text file under 256 KiB: the directory holds a plugin with binaries or larger files for a reviewer.

- **Launch.** `.mcp.json` is `{"command": "${CLAUDE_PLUGIN_ROOT}/scripts/start-mcp.cmd"}` with no args; the two-line CRLF `.cmd` runs `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%~dp0start-mcp.ps1" %*` and exits with its code (Claude Code spawns a `.cmd` stdio server directly). The directory validator treats every arg after the command as a path, so flags there are blocked; the `.cmd` keeps the flags out of `.mcp.json` while the bypass still lets Windows PowerShell 5.1 run the script under the default Restricted policy. One path from `${CLAUDE_PLUGIN_ROOT}`, no other variable or inline code. The `.cmd` must not echo (stdout is the JSON-RPC stream). The script reads `server.lock.json` (version, asset URL, SHA-256 of `Pointframe.Mcp-<version>-win-x64.mcpb`), downloads it over TLS 1.2 on a cache miss, refuses a hash mismatch, extracts to `%LOCALAPPDATA%\Pointframe\plugin-mcp\<version>\server\`, writes `.verified.json` (archive hash and `Pointframe.Mcp.exe` hash) and runs the exe with inherited stdio. Every start re-hashes the exe against `.verified.json`, so a cached start needs no network. It writes nothing to stdout (that is the JSON-RPC stream) and fails closed with a message on stderr.
- **Hashing uses .NET, not `Get-FileHash`.** A Windows PowerShell 5.1 child started from PowerShell 7 inherits its `PSModulePath` and then cannot find `Get-FileHash`; a cache check that threw was silently treated as a miss.
- **Pinning before verification.** Every release comes from a merged pull request. Run `pwsh scripts/merge-pr.ps1 -PinOnly -Worktree <path>` before `verify.ps1`; it updates and commits the pin locally, without pushing. Then verify the pinned tree, push, create the PR, and run `merge-pr.ps1 -Auto -Worktree`; Auto checks that the receipt matches the PR head and current tree; if a newer release landed meanwhile, it commits and pushes the pin itself and accepts the older receipt because only the pin files changed. No bot PR or `PLUGIN_PIN_TOKEN` is needed (a `GITHUB_TOKEN` PR would start no checks). `ci.yml` has `paths-ignore: plugin/**` on its `push` trigger (pull requests still run all checks), so a plugin-only merge runs no CI and cuts no release.
- **Rules enforced offline.** `scripts/check-agent-discovery.ps1` (`Test-ClaudePlugin`, with a mutation self-test on a copy of the plugin) checks the manifest fields and name pattern, README length and required disclosures, the lock schema and its agreement with `plugin.json`, the `.mcp.json` shape, stdout cleanliness of the start script, skill front matter, file types and sizes, `ci.yml`'s `paths-ignore`, `plugin-pin.yml` and the submission draft `packaging/directory-submissions/claude-plugin-directory.txt`.
- **Acceptance.** `pwsh scripts/test-agent-onboarding.ps1 -Client claude-plugin` copies the plugin, runs its `.mcp.json` command (the `.cmd`) with a temporary `LOCALAPPDATA` against the real pinned release (tampered hash and failed download fail closed with an empty stdout; then initialize, `tools/list`, `list_displays`, `list_windows`, `capture_window` on the fixture under the desktop lock; then an offline start from the cache). `-SelfTest` also runs the offline script behaviour against a stand-in server.
- **The recipe.** The fastest first proof needs no MCP client restart: install the CLI (the guide's one line resolves the newest agent release through the Releases API and falls back, with a warning, to the latest alias), `pointframe verify init --app <exe> --hooks none`, add one desktop scenario with selectors, then `pointframe verify run`, which starts its own server and approves standard commands by policy. The first `verify run` (or `verify task start`) installs the checksum-verified server when none is installed and no `--mcp` or `POINTFRAME_MCP_EXECUTABLE` names one, through the same installer that updates an older server (`McpPackageInstaller` serializes activation with a per-user named mutex keyed by the install root, and a move collision with an already valid install counts as success, so two first runs at once both get the server); a failed install reports `mcp_not_found` with the installer error, and the next step is `pointframe verify setup`. `mcp serve`, `verify setup` and `verify init --explore` never install through this path (serve must start fast and keep stdout clean; setup has its own install step). Interactive `desktop_*` tools come after `verify setup` writes the project's MCP config with a policy built from the trusted spec, so nobody hand-writes a policy. A selector `role` is the one-word UI Automation control type name (`ListItem`, `MenuItem`, `Edit`), compared without case.
- **Generating a `verify-<app>` skill.** `create-desktop-verification-skill` follows pstack's `create-verification-skill` shape for Windows desktop apps: interview the repo, write one journey as a spec scenario with a negative control, write `verify-<app>/SKILL.md` and a `features/` map (one file per feature with the H2s Sub-features, How to get to it (user POV), Driving it with Pointframe, Gotchas) that names scenario ids, then prove it once with `verify run` as the last step: the pass is tied to the working tree, so writing the skill files (or any doc) after it makes `verify status` report `fresh: false` (a baseline trial failed exactly so on 2026-10-16). Executable steps live only in the spec. `samples/verify/wpf/reference/skill/verify-wpf-sample` is the worked example; trials exclude `reference/`.
- **Desktop testing is off** in the plugin's own server, because the directory forbids `userConfig` variables in the command. The README points to `verify setup`; a user who runs the server without a spec registers the same script with `--desktop-testing --desktop-policy`, and the script passes extra arguments through.
- Lesson: The directory validator reads every MCP arg after the command as a path
- Lesson: A selector role is the one-word UI Automation control type name

## Packaging and release

### Packaging and install

- `pointframe mcp install --client vscode` downloads the MCPB and checksum from the CLI's own stable release (only release-packaged CLIs, marked with `PointframeReleaseBuild`; source and development builds take the newest agent release from the Releases API, with no token, and fall back to the `latest` aliases with a stderr warning on a rate limit or network error; a missing asset fails with `mcp_release_asset_missing`; see D-012 in [Verify decisions](verify-decisions.md#d-012-version-compatibility)), verifies SHA-256 before extraction, installs into `%LOCALAPPDATA%\Programs\Pointframe.Mcp\<version>`, writes `install-state.json` atomically, and adds the server to VS Code's user `mcp.json`. `VsCodeMcpConfigurator` accepts JSON comments and trailing commas, preserves unrelated values, makes one durable `mcp.json.pointframe.bak`, and atomically replaces the live file; `--dry-run` validates the package and proposed configuration without persistent writes. `mcp status` checks the CLI-managed state and configured command path. `mcp doctor` launches the installed executable over stdio and requires a successful initialize plus the exact direct tool set; desktop-testing tools remain disabled. MCP-management commands branch before capture/OCR service construction and return a single-line `McpCommandResponse` with stable error codes. VS Code is deliberately the only managed client in the first slice; other clients retain the documented manual setup.

**Packaging and configuration.**

`Pointframe.Cli` is released as a self-contained, single-file `win-x64` ZIP with a SHA-256 checksum. `packaging/build-cli-package.ps1` publishes it and creates the versioned archive. It has no WPF application or .NET runtime prerequisite. Users install it with `winget install DimitarRadenkov.Pointframe.Cli`, or extract the ZIP and run `Pointframe.Cli.exe`. The winget package is a `zip` installer with a nested `portable` `Pointframe.Cli.exe` and `PortableCommandAlias: pointframe`: winget extracts the whole ZIP and links only the exe onto `PATH`, and the exe still finds `e_sqlite3.dll` beside it because it runs from the extracted folder through that link. The package uses the versioned ZIP, never the stable `Pointframe.Cli-win-x64.zip` alias, whose content changes every release. `winget/manifests/d/DimitarRadenkov/Pointframe/Cli/` keeps the first manifest, which must be submitted to `microsoft/winget-pkgs` by hand; `.github/workflows/winget-release.yml` updates the package on later releases. The CD build does not bundle ffmpeg in the CLI ZIP, so `record` needs ffmpeg on the machine. An optional `-FfmpegPath` parameter bundles `ffmpeg.exe` into the package (mirroring the MCP package builder) so `record` works out of the box; when omitted, `record` still works if `ffmpeg.exe` is on `PATH` or `POINTFRAME_FFMPEG_PATH` is set on the target machine.

`Pointframe.Mcp` is published self-contained for `win-x64`. `packaging/build-mcp-package.ps1` copies the published executable and a supplied `ffmpeg.exe` into a versioned legacy ZIP and MCPB bundle, alongside `packaging/assets/mcp-icon.png` bundled as `icon.png` and referenced from the manifest's `icon` field so Claude Desktop's Extensions UI shows a Pointframe icon instead of the default placeholder. `mcp-icon.png` is a dedicated 512x512 asset (recreating the brand glyph on a dark rounded-square badge); it is separate from the 32x32 `website/app-icon.png` favicon because MCPB/Claude Desktop recommend 128-256px+ icons. If the glyph or brand colors change, re-export a new `mcp-icon.png` at 512x512 and rebuild the package. The build also emits a SHA-256 checksum and MCP Registry `server.json` metadata pointing at the GitHub Release MCPB asset. The standalone package contains no WPF application. VS Code and other MCP clients launch the executable as a local stdio server.

CI publishes the CLI and MCP executables and runs `packaging/test-mcp-stdio.ps1`, which verifies, on the single-file publish that ships, disabled and explicitly enabled discovery against the exact delivered tool set (the direct tools when disabled, plus the desktop-testing tools when enabled, both read from `$expectedTools` and `$enabledExpectedTools`) without starting WPF. With desktop testing enabled it also calls `desktop_list_apps`, because listing tools never constructs the desktop services and the single-file build once failed every desktop tool there (an empty `Assembly.Location`). The MCP package also includes a disabled-by-default policy schema example. Release qualification (`scripts/release-impact.ps1`, `check-released-desktop.ps1 -BuildCandidate`, `check-release-channels.ps1`) is described in [Release qualification and versioning](../tooling.md#release-qualification-and-versioning). CD attaches the CLI ZIP/checksum plus the MCPB, checksum, and registry metadata to the versioned GitHub Release, then publishes that `server.json` to the official MCP Registry as `io.github.dimitar-radenkov/pointframe-mcp`, so every master release is also a registry version. The publish step must run after the release exists, because `server.json` pins the release MCPB URL and its SHA-256 (MCP clients verify the hash before installing; the registry only requires that the URL contains "mcp"). It downloads `mcp-publisher` pinned to v1.8.1, runs `validate`, then `login github-oidc`, which needs `id-token: write` on the CD job and no secret because the OIDC token proves ownership of the `io.github.dimitar-radenkov/*` namespace, then `publish`. A rejected publish fails the CD run but leaves the already-created GitHub Release in place. Both standalone hosts remain Windows-only and require an interactive desktop session for capture and recording.

**Agent onboarding check.** `pwsh scripts/test-agent-onboarding.ps1 -Client claude-code|codex|vscode|claude-desktop [-AgentSmoke]` proves the install path end to end. It downloads and checksum-verifies the versioned MCPB of the newest agent release (`scripts/agent-release.ps1`; it prints the version it chose) (or uses `-ServerPath`, `-BundlePath`, or `-UseLocalBuild`), validates `manifest.json`, registers the server in an isolated client configuration (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or a temp `mcp.json`; the real client configuration is never touched), repeats the registration and checks that unrelated servers and settings survive, then drives the resolved launch command over stdio (`initialize`, `tools/list`, `list_displays`, `list_windows`, `capture_window` with the handle from discovery) against `Pointframe.DesktopTestFixture --scroll-fixture`. It checks the artifact SHA-256 and byte length, that the inline image decodes, and that the fixture's 48x48 magenta `captureProofMagentaPatch` is present. The server runs with `SNIPPINGTOOL_AUTOMATION_DATA_DIRECTORY` pointing at the work directory, so it never opens the user's `pointframe.db` (a running Pointframe app holds its migration lock and the capture call would hang). Server stderr must be drained, because the server logs heavily and an unread pipe blocks it. Claude Code's `claude mcp add` refuses an existing name, so an update is `claude mcp remove` then `add`; `codex mcp add` is idempotent. Desktop steps hold the exclusive `pointframe-desktop.lock` file in the temp directory. `-AgentSmoke` runs one `claude -p` (Haiku, budget $0.30) that must name the magenta patch. `-SelfTest` runs the offline parts.

### Release acceptance checks

`scripts/check-released-desktop.ps1` is the coordinator's post-release acceptance check. Run it after every GitHub release, from an unlocked interactive Windows desktop, with `pwsh scripts/check-released-desktop.ps1 -Version <x.y.z>` (or omit `-Version` to select the newest agent release). It downloads the versioned CLI ZIP and MCPB with their SHA-256 files, validates both hashes using .NET, and tests the released MCP stdio surface with desktop testing enabled. It then stages and commits the Release desktop fixture in an isolated project, runs the released CLI's `verify run` against the released MCP server, and, when `desktop_export_scenario` is present, checks the released-server record/export and released-CLI add/run round trip. The optional `-SelfTest` tests hash matching and mismatch rejection, the generated v1 verification spec, and the `result.json` shape without network or desktop access.

The check holds `%TEMP%\pointframe-desktop.lock` for desktop work, refuses a locked Windows session, records each step's status, duration, and detail in `result.json`, and stops work-directory CLI/MCP processes during cleanup. If the released MCP server does not list `desktop_export_scenario`, that round-trip step is recorded as skipped because the capability is absent from that release.
