## Recording pipeline

### Recording flow and entry points

**Responsibility.** Record a screen region to MP4 (and optionally GIF) while the user can pause, resume, stop, toggle the microphone, and draw on the live desktop. Keep every visual (border, HUD, annotation surface, cursor effects) aligned with the exact pixels being captured on mixed-DPI multi-monitor setups.

**Entry points.**

| Trigger | Path |
|---|---|
| Overlay "Record" on a selection | The `OverlayWindow.Recording.cs` partial hides the selection overlay, starts the optional camera, then the recorder (no countdown) |
| Hotkey full-screen record | `ICaptureLaunchService.StartWholeScreenRecord` |
| Post-recording trim | `TrimRecordingRequestedMessage` opens `TrimWindow` with a `TrimViewModel` built by `Func<string, TrimViewModel>` |

**Flow.**

1. There is no pre-roll: neither recording entry point opens `CountdownWindow` (it serves the snip capture delay only, F-04). Region recording hides the selection overlay and starts the recorder; whole-screen recording starts it directly. Everything visible inside the capture rectangle is burned into the frames: the dashed border sits outside it (`RecordingBorderOffset`), while live annotations and the camera bubble are inside on purpose. When `RecordCamera` is on, both entry points first run `RecordingCameraStartup.BeginAsync` on the UI thread (bounded wait of 3 s, never inside the recorder's `Task.Run`) and hand the session to the overlay, which then owns and disposes it.
2. `RecordingSessionGeometry` is computed once for the target monitor: host and capture bounds in physical pixels, the same in DIPs, work area, monitor name, scale X and Y. Every consumer maps through its `Map*` methods. Compute it only after the monitor-scoped host window has settled.
3. `IScreenRecordingService.Start(x, y, width, height, outputPath)` (transient `ScreenRecordingService`) truncates width and height to even numbers, starts the capture loop, and writes frames through `IVideoWriterFactory` to `FFMpegVideoWriter`, which pipes into an ffmpeg process located by `FfmpegResolver`.
4. `RecordingOverlayWindow` hosts the border, HUD, and annotation surface for that monitor in PerMonitorV2 context. `RecordingHudCoordinator`, `RecordingAnnotationSurfaceCoordinator`, and `RecordingMousePassthroughCoordinator` place them and toggle click-through; `RecordingOverlayNativeInterop` holds the Win32 calls.
5. `RecordingHudViewModel` (one per session through `Func<IScreenRecordingService, string, RecordingHudViewModel>`) drives pause, resume, stop, microphone, and tool selection. `RecordingMicrophoneSession` restores the device's original mute state on stop.
6. ffmpeg writes a fragmented MP4 (`+frag_keyframe+empty_moov+default_base_moof`, `-flush_packets 1`) to a hidden `.{name}.recording.mp4` next to the output. Stop contains worker and finalization failures inside `ScreenRecordingService`, disposes the pipeline/writer, and restores the microphone's initial mute state. `RecordingRecovery` then remuxes the intermediate (`-c copy -movflags +faststart`) into the output and deletes the intermediate only after the output has a readable duration. `LastStopResult` is complete, partial (a failure after at least one fragment: the user keeps a playable file) or failed, with the artifact path and the duration read from the file. A partial or failed stop emits one diagnostic `recording_failed` event (with `recovered`) and logs local exception details and recent ffmpeg stderr. Complete and partial stops publish `RecordingCompletedMessage` once (a partial first shows "Recording stopped early. Saved the first m:ss."; the HUD window closes after the toast); a failed stop shows the failure toast and publishes nothing. `GifExportService` and `VideoTrimService` post-process through ffmpeg. `WatermarkTokenResolver` expands watermark text templates. See [Recording transcription](transcription.md#recording-transcription).
7. Committed blur elements retain their `RecordingRedactionRegion` identity. Recording annotation undo removes that exact region from the frame redaction snapshot, and redo restores it. The event sidecar uses an unbounded producer queue so event bursts do not fail before recording cleanup.

`FfmpegResolver` order: `AppContext` data key override, `ffmpeg.exe` next to the binary, `Assets\ffmpeg\ffmpeg.exe`, then `PATH`. See [Runtime paths](../references.md#runtime-paths-and-external-binaries).

### Recording invariants, files, tests, and lessons

**Invariants.**

- One geometry model per session; see [D-003](#d-003-recording-uses-one-authoritative-session-geometry). Never recompute DPI conversions in a consumer.
- Even width and height before ffmpeg starts; see [Recording width and height are even](#recording-width-and-height-are-even).
- Border and annotation windows are positioned in physical pixels, not DIPs.
- When "Record microphone" is on but no compatible device exists, both recording starts (whole screen in `CaptureLaunchService`, region in `OverlayWindow.Recording.cs`) call `IMicrophoneWarningService.ReportIfUnavailable`. It tracks `microphone_unavailable` every time, but shows the Yes/No dialog at most once per app run; Yes saves `RecordMicrophone = false`, No keeps it on. The recording continues without microphone audio either way.
- Microphone enumeration uses WASAPI (`MicrophoneDeviceService`); WinMM names are truncated and do not match ffmpeg device names.
- The ffmpeg process must end when the video input ends, or it keeps running on the audio input alone. `-shortest` gets `-shortest_buf_duration 0.5` when the `-h long` probe shows the build supports it (FFmpeg 6.0+), or ffmpeg holds up to 10 s of video and a killed microphone recording leaves nothing to recover; older builds keep plain `-shortest`.
- After at least one complete fragment a recording is never lost: a failed remux keeps the fragmented file as a visible `name.recovered.mp4`; nothing recoverable leaves no `.mp4` behind; a leftover intermediate older than the session is recovered once at startup. `phase` in `recording_failed` names where the failure started (a later finalize failure never overwrites it).
- ffmpeg option semantics differ between builds. `FFMpegVideoWriter` probes the resolved ffmpeg once per path (`-h filter=drawtext` for the watermark, `-h long` for whether `-thread_queue_size` is still an input option and whether `-shortest_buf_duration` exists) and leaves out what that build rejects, because users may have any ffmpeg on `PATH` or from an older install.

## System audio is captured to a WAV and mixed in at finalize

**Rule.** With `RecordSystemAudio` on, `ScreenRecordingService` starts `ISystemAudioCaptureService` (WASAPI loopback of the default playback device through NAudio `WasapiRecorder`, created lazily through a `Func<ISystemAudioCaptureService>` only when the setting is on) beside the unchanged ffmpeg video(+microphone) pipeline, writing a hidden `.{name}.sysaudio.wav` next to the output. After `RecordingRecovery` has produced the final MP4, `ISystemAudioMixer` stream-copies the video and adds the audio in a second ffmpeg pass: the system track padded with endless silence (`apad`) with `-shortest`, so the video defines the output length; with a microphone, `amix` of the padded microphone and system tracks into one AAC track. The ffmpeg recording arguments are the same with the setting on or off.

**Why.** Loopback has no clock shared with ffmpeg's dshow microphone input, and it delivers nothing while nothing plays. A separate WAV lets the video pipeline, its fragmented-MP4 crash recovery, and the finalize-failure fix stay exactly as they were, and a failed mix cannot damage the recording.

**Invariants.**

- Never lose the video. A loopback start failure, a device loss or write failure mid-recording, or a mix failure leaves the recording as it was, without system audio. `ScreenRecordingService` reports each recording's first failure once to `ISystemAudioNoticeService`: telemetry `system_audio_unavailable` (`reason` code and `phase` `start`/`capture`/`mix`, never a device name); `recording_started` carries `system_audio` true/false every time, and a tray balloon at most once per app run (no modal dialog on the start paths).
- The mix replaces the MP4 only after ffmpeg wrote a non-empty file (`.{name}.sysaudio.mp4`) whose duration is within 750 ms of the original (`-i` probe); any failure or mismatch deletes the temporary file and keeps the original. Only a complete, remuxed recording is mixed; a partial recording (`.recovered.mp4`) is left without system audio.
- A/V sync is `SystemAudioTimeline`: packets are placed by their own QPC capture timestamp (not callback arrival, so batched late packets create no false silence), a gap of 20 ms or more gets silence (including lead padding when audio starts after the capture clock), the WAV is padded to the active elapsed time at stop, and audio captured while paused is trimmed by timestamp even if delivered after resume. The timeline origin is the first captured video frame (the video's frame-count timestamps start there): the loopback device starts first, and the pipeline's `FirstFrameCaptured` option calls `BeginTimeline()` right after the first capture, so neither device initialization nor a late first frame shifts the audio. A packet whose WASAPI timestamp is flagged as uncertain (`TimestampError`) is placed right after the previous packet only when its arrival time agrees (within 100 ms); otherwise at its arrival time minus its duration. `Pause`/`Resume` forward to the capture.
- The audio follows the written-frame timeline, not the wall clock. When ffmpeg is busy (opening the dshow microphone blocks it for about 1.1 s) the pipeline's bounded channel drops the frames captured meanwhile, so the video loses that span and `PadToElapsedDuration` adds frozen frames only at the end. `RawFrameRecordingOptions.FrameDropped` reports each dropped frame's due time (QPC) and one frame period; `ScreenRecordingService` forwards them to `ISystemAudioCaptureService.ExcludeSpan`, and `SystemAudioTimeline` treats them exactly like pauses (consecutive drops coalesce). Without this, system audio with a microphone ran late by the dropped duration. The audio is still padded to the video length at the end (`apad`). The Engine option is optional, so the CLI and MCP recording path is unchanged.
- The capture thread is joined by NAudio on stop; `WasapiSystemAudioCaptureService.Shutdown` stops and disposes the source outside `_gate`, which the callbacks take, or stop would deadlock. Start, stop and dispose are serialized by a separate `_lifecycle` lock that callbacks never take, so a concurrent dispose or restart cannot delete or replace a session's WAV mid-stop. The WAV is written as RF64 so recordings past 4 GB (about 3 hours) keep their audio.
- The WAV is deleted on every path (mixed, mix failed, capture failed, video not recoverable, start exception). A WAV left by a killed app is not recovered or cleaned automatically.
- Transcription is unchanged: it still runs only for recordings that had microphone audio, on the finished MP4. With both on, the transcript hears the mixed track, so speech in system audio is transcribed too; system audio alone produces no transcript.
- The CLI and MCP recording path (`DirectRecordingService`) does not capture system audio.

## The camera bubble is an overlay element captured by the existing screen capture

**Rule.** With `RecordCamera` on, a round, mirrored camera bubble is an element of `RecordingOverlayWindow` inside the capture rectangle, so the unchanged BitBlt capture records it (the same mechanism that burns live annotations into the video). Nothing in the recorder, the Engine, ffmpeg arguments, the CLI or MCP changes. With the setting off nothing is created: `RecordingCameraStartup.BeginAsync` returns null before the factory is called and no camera API is touched.

**Why.** Compositing camera pixels into the frames would couple an optional device to the process that holds the valuable recording; the overlay already composes everything the user sees, so face and screen stay in sync by construction.

**Invariants.**

- Never lose or delay the recording. `RecordingCameraSession` (one per recording, owned by the overlay window after hand-off, disposed in `OnClosed` and by the entry point on any pre-overlay failure) swallows every failure: the bubble hides, `ICameraNoticeService` tracks `camera_unavailable` (`reason`, `phase`, never a device name or id) every time and shows one tray balloon per app run, and the recording continues. The notice never uses `ShowRecordingFailureToast`, which closes the overlay and stops the recording. Access denied names the Windows steps (Settings > Privacy & security > Camera > Let desktop apps access your camera); the balloon is not clickable.
- Threading: start (device enumeration, `MediaCapture.InitializeAsync`) is awaited on the UI thread with a 3 s bound; a late camera keeps starting and its bubble appears when frames arrive. Frames arrive on a `MediaFrameReader` worker thread (shared read-only mode, so Teams or Zoom keep the camera; BGRA at about 640 px wide, at most 30 fps, one frame converted at a time, very large modes subsampled), land in a one-slot latest-frame mailbox with a pooled buffer, and one queued Render-priority update writes the latest frame into one reusable `WriteableBitmap`. All state is under one lock; events are raised outside it; callbacks after dispose or close are ignored.
- No frame for 2 s hides the bubble (never a frozen face) and reports `stalled` once; frames resuming show it again. A lost device reports `lost` and releases the camera. The camera service is stopped exactly once per start (toggle off, failure, or dispose).
- A saved `CameraDeviceId` that is not present at start is never replaced by another camera: no bubble, reason `device_missing`. The device is stored by id, not index; the Settings picker shows only with more than one camera and keeps a saved but disconnected id selectable.
- Placement is the pure `CameraBubblePlacement.Calculate` in physical pixels through `RecordingSessionGeometry` (so mixed DPI, negative monitor origins and the even-size truncation of the capture rectangle hold): 16 DIP inside the chosen corner of the captured rectangle, diameter Small 128 / Large 192 DIP capped at a third of the shorter captured side, omitted below 64 DIP. HUD rule: when the HUD (with an 8 DIP gap) overlaps the bubble's corner, the bubble slides along the side edge away from the HUD; if that does not fit it slides along the top or bottom edge away from the HUD; if neither fits it is omitted. The overlay recalculates it whenever the HUD is positioned.
- The bubble is a child of the overlay root (not of `RecordingAnnotationCanvas`, so undo and clear cannot remove it), above annotations and cursor effects, below the HUD and the toast, and `IsHitTestVisible=false`. The passthrough hit regions are only the HUD panels and, when drawing is armed, the capture rectangle, so the bubble needs no exclusion: input falls through it to the annotation canvas.
- The HUD camera button exists only when the feature is on. Off stops the camera and hides the bubble; on starts a new capture. Pause keeps the camera running. There is no device switching mid-recording.
- Not done (decisions): no dragging, no other shapes or sizes, no background blur, no CLI or MCP camera, no camera-only recording.

## Recording width and height are even

**Rule.** `ScreenRecordingService.Start` truncates an odd width or height by one pixel and aborts with a logged error if the result is too small. Anything that positions a visual against the capture (border, annotation surface, cursor mapping) uses the same even size, not the user's raw selection.

**Why.** Frames are handed to ffmpeg as JPEG, whose minimum coded unit needs even dimensions, and the MP4 encoder's 4:2:0 chroma subsampling needs the same. An odd dimension makes the encoder fail or produce corrupt output.

**Enforced by.** `Pointframe.Tests/Services/ScreenRecordingServiceTests.cs`: `Start_WithOddDimensions_TruncatesToEven` and `Start_OddDimensions_TruncatesToEvenBeforeFactory`. `RecordingSessionGeometry` does not round for you; callers pass the truncated size in.

**Symptoms when violated.** ffmpeg exits immediately, or the MP4 has green or shifted edges. The recording border is one pixel wider than the recorded area.

**Files.** `Pointframe/Services/Recording/ScreenRecordingService.cs`, `Pointframe/Models/RecordingSessionGeometry.cs`. See [Recording pipeline](#recording-pipeline) and [D-003](#d-003-recording-uses-one-authoritative-session-geometry).

## D-003 Recording uses one authoritative session geometry

Decided 2026-04-09.

**Context.** Mixed-DPI multi-monitor bugs kept recurring: the border, the HUD, the annotation surface, and the recorder each converted DIPs to pixels with their own idea of the scale, so they drifted apart by a few pixels or by a whole monitor offset.

**Decision.** `RecordingSessionGeometry` is computed once per recording session and carries host bounds and capture bounds in both physical pixels and DIPs, the work area, the monitor name, and the X and Y scale. Consumers call its `Map*` methods (`MapHostDipPointToScreenPixels`, `MapScreenPixelRectToHostDips`, `MapCaptureLocalDipRectToScreenPixels`, and the rest). No consumer reads `PresentationSource` DPI or `SystemParameters` to place recording visuals.

**Consequences.** A new recording visual takes the geometry as input and adds a `Map*` method if none fits. The geometry is computed after the monitor-scoped host window has settled, or every consumer inherits the wrong scale. `Pointframe.Tests/Models/RecordingSessionGeometryTests.cs` pins the mapping math; extend it with each new method.

**Alternatives rejected.** Per-window DPI reads with shared helper functions: still produced disagreements because each window's HWND could sit on a different monitor at read time.

**Files.** `Pointframe/Models/RecordingSessionGeometry.cs`, `Pointframe/Services/Recording/ScreenRecordingService.cs`. See [Recording pipeline](#recording-pipeline) and [DPI coordinate systems](../composition.md#dips-and-physical-pixels-are-converted-explicitly-per-monitor).

**Lessons.**

- Lesson: Recording mode must use one authoritative geometry model
- Lesson: Mixed-DPI multi-monitor capture features need PerMonitorV2 process DPI awareness
