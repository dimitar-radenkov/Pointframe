# Repository tooling

How the repository builds, tests, releases, and versions itself: workflows, local gates, merge and release scripts, and the installer and packaging rules. No user-facing features live here.

Part of the [Pointframe knowledge base](knowledge-base.md).

## CI, CD, and versioning

### Workflows

**Workflows.**

| Workflow | Trigger | Does |
|---|---|---|
| `.github/workflows/ci.yml` | push to `master` unless it changes only `plugin/**`; PR to `master` (feature branches run once, through their PR; a newer push cancels the older PR run, a master push is never cancelled) | two parallel jobs, both required checks (keep the names). `unit-tests`: restore and build `Pointframe.Tests` and `Pointframe.Agent.Tests` in Release, MCP contract and discovery tests (in `Pointframe.Agent.Tests`), `dotnet test` of both projects with `--filter "Category!=Integration"`, upload the Cobertura file as an artifact. `package-checks`: restore `Pointframe`, `Pointframe.Mcp` and `Pointframe.Cli`, `dotnet format Pointframe/Pointframe.csproj --verify-no-changes --no-restore`, publish the MCP server and CLI, MCP stdio smoke test, knowledge base check, workflow script check, agent discovery check. `~/.nuget/packages` is cached (key: hash of every `*.csproj`, `Directory.*.props/targets`, `global.json`, `dotnet-tools.json`; saved by `unit-tests`, only restored by `package-checks`; the win-x64 runtime packs are excluded and downloaded by restore). ### Local gates and merging

**Gates a change must pass locally.** One command runs what CI's unit job runs, and a change is ready only when it passes:

```powershell
pwsh scripts/verify.ps1                                    # preflight, build, format, tests, kb, workflows; exit 0 only when all pass
pwsh scripts/verify.ps1 -Filter "FullyQualifiedName~Foo"   # narrow tests while iterating; the verdict is "partial"
pwsh scripts/verify.ps1 -Skip kb,format                    # leave gates out while iterating; also "partial"
```

- `scripts/verify.ps1`, `merge-pr.ps1`, `record-review.ps1`, `status.ps1`, `agent-run.ps1`, `codex-ask.ps1`, `check-workflow-scripts.ps1` and `package.ps1` are thin wrappers around the vendored kit tools in `scripts/agent-workflow/tools/`. Gates, required checks, base ref, state folder, status paths and executor budgets come from `agent-workflow.json`; the plugin pin is `hooks.pin` (`docs/knowledge-base/hooks/pin.ps1`) with its files in `pinException.paths`. merge-pr and record-review read that configuration from the main checkout of the worktree they check, never from the pull request's own copy, and merge-pr refuses a receipt that lacks a configured gate (or doctor). The package runner takes its hooks (`hooks.pin`, `hooks.qualify`, `hooks.channels`), its build, format and test commands (`package.commands`, `package.testFilter`) and the pin files from the same main-checkout configuration; a null `qualify` or `channels` hook is recorded as `not-configured`, never as passed. A gate's `timeoutMinutes` is enforced (exit 124), and each gate runs in a job object, so a leftover child process is stopped and named.
- Wrappers render `scripts/agent-workflow/templates/wrapper.ps1` (`doctor.ps1 -Root . -WriteWrappers` after an upgrade). The doctor gate fails on a changed vendored file or wrapper, a lost `-text` attribute, or an install leftover; `-Source <kit clone>` also proves the lock. A `-Candidate` install is for trying a kit commit; merge-pr and ship refuse it.
- verify reuses a stored complete pass for identical content (tree, gate config, kit, verify tool; `-NoReuse` runs the gates), and merge-pr binds a receipt to the head's tree. A standalone clone as `-Worktree` is refused; ship refuses a main checkout behind `origin/<base>`, so run `merge-pr.ps1 -SyncMain` after every merge.
- Gates run in order: preflight (no running process holds the `bin/Release` output), doctor (the vendored kit still equals `agent-workflow.lock.json`), Release builds of `Pointframe.Tests` and `Pointframe.Agent.Tests` (gates `build`, `build-agent`), `dotnet format --verify-no-changes` on the main project, the unit lanes (`Category!=Integration`; gates `tests` and `tests-agent`), `scripts/kb.ps1 selftest` then `scripts/kb.ps1 check -NoFix`, and the workflows gate (`scripts/check-workflow-scripts.ps1`: its `-SelfTest` against the kit fixtures, then a parse of every `shell: pwsh` or `powershell` `run:` block in `.github/workflows/*.yml` after replacing each `${{ ... }}` with a placeholder; CI runs the same two commands in the "Workflow script check" step), and the discovery gate (`scripts/check-agent-discovery.ps1`: its `-SelfTest`, then the offline checks; CI runs both in the "Agent discovery check" step), and the scripts gate (`scripts/test-scripts.ps1`: the offline `-SelfTest` of every coordinator and release script, and no git-ignored file under `scripts/tests`, since a fixture the `*.md` rule ignored once existed only in the worktree that wrote it; CI runs it on a clean checkout in the "Script self-tests" step). The package.ps1 self-test runs only when a path under scripts/ differs from the merge base with -BaseRef (default origin/master: committed, staged, unstaged or untracked) or with -All, and is otherwise printed as SKIP; by default it is `-SelfTest -Quick` (under three minutes: every command's dispatch, state round-trip, refusals, review, recovery and one ship), and `-All` runs the full suite (about 25 minutes); any doubt about the merge base runs everything. CI passes -BaseRef on pull requests and -All on master pushes, and script-selftests-daily.yml runs -All every day outside the CI workflow, so it never triggers CD. The workflows gate catches syntax errors only, such as `"$tag:"`; a runtime mistake such as a tolerated native failure with no `exit 0` still needs review. Tests are skipped when the build fails; the other gates always run, so one pass reports every problem.
- It builds Release, like CI, so the editor's MCP connector holding the Debug output does not block it.
- It writes verdict.json and one log per gate into the gitignored artifacts/verify folder. The verdict holds each gate's status and failure details (compiler errors, format diffs, failed test names with their assert message, kb errors) and `treeHash`, the git tree of the working tree it verified, so a verdict from before a later edit is detectable as stale.
- Only `status: pass` (`complete: true`) is a final verdict. `partial` means gates were skipped or tests filtered.

**Merging a pull request.** Order: commit work -> `pwsh scripts/merge-pr.ps1 -PinOnly -Worktree <path>` -> `pwsh scripts/verify.ps1` -> `pwsh scripts/record-review.ps1` -> push and `gh pr create` -> `pwsh scripts/merge-pr.ps1 -Pr <number|branch> -Worktree <path> -Auto`. `-PinOnly` updates and commits the plugin pin locally before verification. Both waiting merge and `-Auto` require `-Worktree`, artifacts/verify/verdict.json complete/pass and matching the PR head and current working-tree hash, and a passing independent review record for the head (see [Agent workflow](workflow.md#review)); there is no bypass switch. Waiting mode requires every configured check to be present with none pending, then squash-merges with `--match-head-commit`; cleanup occurs only after GitHub says MERGED. A receipt for an ancestor still counts when the only later change is the files in `pinException.paths` and the pin hook validates them, so when a release lands after verification `-Auto` commits and pushes the pin itself instead of forcing another `verify.ps1`. `-Auto` prints `AUTO-MERGE ENABLED (not merged yet)` on success. Add `-WaitMerged` to poll through merge and clean up; it stops on CLOSED, failed/cancelled checks, or timeout. A merge never updates the main checkout: cleanup prints where it was left and the sync command, because a fast-forward there stops every package that is running (`blocked-main-mutated`). `pwsh scripts/merge-pr.ps1 -SyncMain` (`-DryRun` to preview) fast-forwards it to `origin/<base>` only when no package is running or reviewing; it takes `main-sync.lock` under git's common directory exclusively, while package run, review and fix hold it shared. Exit 1: receipt refusal, failed/cancelled check, timeout, closed PR, or merge not completed; 2: gh missing or unauthenticated, or bad arguments; 3: conflicting PR, or `-SyncMain` refused with its blockers named; 4: the `-SyncMain` fast-forward failed. `-SelfTest` covers decision and receipt fixtures under the kit's `fixtures/gates/merge-pr`.

Status lives in plan/status.json; `scripts/status.ps1 -Publish` renders GitHub issue #186 and the owned handoff region. Publish at every stage change.

Every Codex executor run goes through `scripts/agent-run.ps1`; Sonnet subagent briefs are checked with `-ValidateOnly`. Each run appends one cost record to the local, gitignored agent-runs.jsonl under plan/, the cost source for the weekly retro.

The format gate covers the main project only. Do not run `dotnet format` on `Pointframe.Tests` or `Pointframe.Agent.Tests`; it would rewrite many unrelated files.

- Lesson: PowerShell variable names are case-insensitive, so a local can collide with a switch parameter

### Work package runner

**Work package runner.** `scripts/package.ps1 new|run|check|show` keeps one package's state under git's common directory (`pointframe/packages/<slug>.json`, atomic writes, one lock). `new` snapshots the brief and the check manifest, creates `pkg/<slug>` from the fetched `origin/master` and preflight-builds the check targets. `run -Executor codex|claude-sonnet|claude-haiku` launches the executor suspended inside a kill-on-close job object, bounds time and input tokens from outside (cumulative across `-Resume -PromptFile`; an interrupted run is charged an upper bound or blocks the resume), verifies the process tree is gone, and guards the main checkout with a raw-content fingerprint (a change stops the package at `blocked-main-mutated`; nothing is reverted; `recover -Id <slug> -Reason <text>` is the only way out: it records the reason and the main checkout's state, invalidates every check, review PASS and acceptance, and returns to the stage after the last run). `check` also fails, naming the files, when a tracked file's raw bytes differ from the commit although git reports it clean (an executor's edit and revert under autocrlf). Claude runs use `claude -p` (the npm shim resolved to `bin\claude.exe`) with the worktree as working directory, the prompt on stdin, `--setting-sources ""`, an explicit `--tools` list without PowerShell (Claude Code refuses a nested `pwsh` from that tool), a generated allowlist and empty strict MCP; the runner never adds a bypass flag or accepts runner-owned extra arguments, records denials in `permissionDenials[]` and never retries with wider permissions. The allowlist guards against accidental actions (commit, push, `gh`, network), not a malicious executor, because the worktree is writable and builds run executor-written code; the main-checkout guard, job containment and review are the real controls. Outcomes are `completed` (exit 0, both artifacts, verified containment), `env-blocked` (an explicit `ENV-BLOCKED:` line and nothing else failed) or `impl-failed` (including "mixed" and "scope"); `completed` is never acceptance. `check` runs mutating steps first, then build and focused tests, and a result is fresh only for the tree it ran on. Tokens and cost are what the CLI reports, not an invoice.

**Review, fix and accept.** `commit` (coordinator-owned, after a fresh passing check) commits on `pkg/<slug>` with a trailer listing every executor run that started, fetches and rebases, and re-runs `check` when the tree changed; executors never commit. `review -Level light|heavy` reviews exactly that committed head in a detached, read-only snapshot worktree the host observes at start and end and then removes. The snapshot must hold the raw bytes the covering check ran on (no line-ending tolerance). Heavy means codex-sol at high effort or claude-opus, also with `-Reviewer`, and the reviewer differs from every executor model in the package, failed runs included. Claude reviewers get Read, Glob and Grep only and read host-prepared inputs (log, stat, a diff without external diff or textconv, the brief); Codex reviewers run under `codex-ask -Sandbox read-only`. Inputs and prompt are hashed before launch and rechecked at completion and at `accept` (the diff regenerated, the brief byte-compared). The reviewer's final message is the verdict: the kit's `scripts/agent-workflow/review/package-verdict.schema.json` plus host checks decide (a strict tokenizer rejects comments, trailing commas and repeated properties; head, tree and base are host-observed; every brief acceptance case is a criterion; PASS only with all criteria passing, no blocking finding and a fresh check). Anything else is `invalid`, never PASS. A round is spent before the reviewer starts, 3 per package, persisted (at most 2 refunds per package; `recover` also moves the package's review records to `reviews/invalidated/`, where merge-pr does not accept them); only `-ResetBudget -Reason` resets it, and the reset is recorded. A round lost to the environment (the reviewer cannot start, the CLI or Codex exits nonzero before any verdict, a review abandoned before the reviewer produced any output) is refunded and shown in `show`; a malformed, empty or schema-invalid verdict, and a review abandoned after output existed, still cost a round; `review` refuses without spending a round when the executor's report differs from its recorded hash. A `claude` CLI older than the model needs (`package.minCliVersions`; claude-opus-5-5 needs 2.1.280) refuses the round before it is spent. The review inputs also hold the fresh check summary (`check-summary.json`) and the executor's report, both hashed and rechecked at `accept`, and `new` warns about acceptance cases a reviewer cannot observe. A Claude reviewer starts every round fresh, with the previous verdict and findings in its prompt; a Codex reviewer is resumed. A FAIL without findings gets a fix path through `fix -Findings <file>` (coordinator-written, hashed and recorded). `disposition` records the coordinator's accept or reject per finding, and `fix` continues the latest run of the same kind with its model and effort (a Claude session is resumed; Codex starts a new run with the previous report appended), then check, commit and review again. `accept -Reason` is a separate recorded step for a valid PASS bound to the current head, tree, base, brief, manifest and criteria; it writes the review record through `record-review.ps1` from state values only. Any later head change invalidates the PASS and the acceptance, except a change of the two plugin pin files alone, proved per file and validated (JSON, matching versions, checksum shape, offline discovery check). A real end-to-end run (Haiku executor, Codex luna reviewer, `accept`) passed on 2026-10-18; a reviewer copying the schema's `$schema` line is why that one key is tolerated.

**Ship.** `ship -Id <slug> [-Title] [-AllowDesktop] [-NoWait]` takes an accepted package to a merged PR under a repository-wide ship lock (a `ship.lock` file in the `pointframe` folder under git's common directory; one release in flight; a leftover lock of another package is reported, never stolen). Its steps are recorded in state and a rerun resumes after the last completed one: base (rebase; only a proven no-op keeps the acceptance, any other change re-runs `check` and sets `needs-review`), pin (`merge-pr.ps1 -PinOnly`; only the pin-file exception keeps the acceptance), verify (receipt bound to head and tree), record (the record `accept` wrote must cover the head), qualify (`hooks.qualify` = `docs/knowledge-base/hooks/qualify.ps1`: `-Action Impact` runs the main checkout's `scripts/release-impact.ps1`, `-Action Run` the worktree's `scripts/check-released-desktop.ps1 -BuildCandidate`; a null hook records `not-configured`; a passing desktop qualification is reused only for the same head, tree and candidate hashes; without `-AllowDesktop` the stage is `desktop-required`), push (once; a remote tip the runner did not push is never overwritten), pr (an open PR is reused; the body is generated from state with a "What was not tested" section), merge (`merged` only when GitHub reports MERGED; `-NoWait` stops at `auto-merge-enabled`) and channels (`hooks.channels` = `docs/knowledge-base/hooks/channels.ps1`, which runs `scripts/check-release-channels.ps1` after a bounded wait for the release of the merge commit; failed channels and a stale pin are reported, no pin PR is opened; a null hook records `not-configured`). Budgets: `-MaxInputTokens` (default 20M) counts cache reads, so a package that edits a large script needs more; PR4's executor reached 20M in 83 turns on the 4,500-line `package.ps1`.

### Fresh-agent trials

**Fresh-agent trials.** `pwsh scripts/trial.ps1 -App pkhex|dngrep|electron|wpf-sample [-Version x.y.z] [-OutDirectory <dir>]`, or `-Matrix` for the three OSS apps in sequence (Claude only), is the quality metric for the CLI and MCP: a coding agent that has never seen Pointframe adds a small UI change to an app and must set up verification from the public docs. App definitions (pinned commit or `localPath`, change prompt, workaround patterns) are in `scripts/trials/apps.json`. `wpf-sample` is local: the harness copies `samples/verify/wpf` without `reference/`, `bin` and `obj`, and its git baseline commit stands in for the pinned commit. The harness scores, not the agent, and writes `result.json` plus one summary line. `result.json` holds `metrics` (`toolCalls`, `totalInputTokens` with cache reads and creation counted, `minutes`) and, with `-MaxToolCalls`, `-MaxInputTokens` or `-MaxMinutes`, a `limits` record that never changes the outcome; an unmeasured limit is `notMeasured`, never within limits. The agent gets an allowlisted environment (no `POINTFRAME_*`, no `ELECTRON_RUN_AS_NODE`, no Pointframe PATH entry; probed in a real child), the agent is Claude Code (`claude-sonnet-5-5`, `-AgentModel` overrides) with project settings and an empty strict MCP config, and every run has a 30 minute limit. `-Agent codex` runs `codex exec` with full access, so the script refuses it unless `-AllowCodexFullAccess` is passed; the owner approves that per package. `-Task create-skill` (apps opt in; today `wpf-sample`) asks the agent to create a verification skill and prove it once; it is `pass-clean` only with an agent-written `SKILL.md` named `verify-*`, a `features/` file with the four pstack H2s naming a scenario in the spec, a fresh pass with a criterion and a negative control, evidence that exists after the run, and a failing defect variant described in `apps.json`. Skills copied in by `-Skills` never count as the agent's work. Create-skill runs also get a `gate` (pass-clean and within the default 15 calls, 786,000 total input tokens, 10 minutes). `-ClaudePluginDir` loads a plugin and allows the `Skill` tool; Claude create-skill runs need `-AllowClaudeBypassPermissions` (`--permission-mode bypassPermissions`), because `claude -p` refuses writes under `.claude/` with allow rules, absolute rules, `acceptEdits` or Bash, and the owner approves it per package like Codex full access; `-Repeat N` runs one configuration N times with a summary table. `-FreshMachine` hides the real `Programs\Pointframe.Cli` and `Programs\Pointframe.Mcp` folders under the known-folder LocalAppData by renaming them for the run, because the .NET CLI resolves that folder through the Windows API and ignores a `LOCALAPPDATA` override; an older install would otherwise be auto-updated and hide the fresh-machine path. A recovery marker is written before each rename and removed only after a successful restore; the agent's own installs move into the trial output as evidence; a harness start under the desktop lock restores markers left by a crash. The user PATH is put back to its raw baseline value and kind only when the run changed it by additions alone. `-PromptPrefix` prepends text such as `/create-verification-skill` to the task prompt (the pstack entry run). Create-skill runs need `-Configuration installed` (a Pointframe skill or plugin is present; the prompt says it may be used, with the public docs as a fallback, and never commands it) or `cold` (no Pointframe skill; pstack's own skill is allowed; the prompt points at the public docs). `skillActivated` records whether a Pointframe skill was invoked or its `SKILL.md` or `references` were read, and `otherSkillsActivated` lists other skills used. Without `-Version` the harness resolves the latest release before the run, keeps the version out of the prompt, and scores release drift (a newer release, or agent CLI/MCP versions that differ) `invalid`; `-Version` is a compatibility exercise and is labelled so. `toolCalls` counts every completed tool event: every Claude `tool_use`, and Codex `command_execution`, `mcp_tool_call`, `web_search` and file-change items (other item types are listed in `unknownItemTypes`, not counted). `-Rescore <folder>` recomputes metrics, limits and gate from a stored transcript into `rescore.json`. A run is `pass-clean` only when `verify status` is pass and fresh, a passed criterion names the new element, a negative control passed, every report proof verifies, nothing the run started is still running, the CLI and MCP versions the agent used equal the requested release, and the defect check fails: the final project, with everything but the Pointframe config put back to the pinned commit, must fail `verify run` at the missing change. A diff with workaround patterns (`BeginInvoke`, `Thread.Sleep`, ...) the prompt did not ask for is `pass-workaround`; leaked environment, a version mismatch or an inconclusive defect check is `invalid`. Only `pass-clean` counts as a pass; the others are never counted as clean. Cleanup kills only processes the run recorded, matched by PID and start time. `-SelfTest` is offline and scores the fixtures in `scripts/tests/trial/`; it is not part of `scripts/verify.ps1`, which wires each script's self-test by hand.

**Entry point.** `-Entry web` (default) keeps the public documentation prompt. `-Entry readme -DocsRef <git ref>` exports a snapshot of `README.md`, `docs/`, `website/llms.txt`, `PRIVACY.md` and the tracked top-level Markdown files at that ref into the trial output (`git archive --format=zip`, never a bare `tar`, which resolves to Git's tar under Git Bash and reads `C:` as a host). `-DocsRef` is validated before any setup (exit 2 when missing or not a commit). The run records the resolved commit and an ordinal-sorted SHA-256 of the snapshot, and the prompt points the agent at the local `README.md` only. Metrics count `docsLocalReads` and `docsWebFetches` from tool inputs only, never tool output; release binary downloads are not docs fetches. A docs fetch in a readme run sets `docsWebFetchViolation` and is named in the summary line, without aborting the run. Compare two READMEs only through the same entry mode with the same agent, model, release and task, because the docs behind the links are pinned too.

**Weekly canary.** `pwsh scripts/weekly-trial.ps1` runs locally at the Monday retro (it takes over the desktop for 10-15 minutes). It resolves the latest release and the `origin/master` SHA once, runs `trial.ps1 -App wpf-sample -Entry readme -DocsRef <sha> -Version <v> -FreshMachine -Repeat 3` into `plan/trials/weekly/<date>`, classifies each run (`pass-clean`, `pass-workaround`, `fail`, `timeout`, `invalid`) and compares with the retained `baseline.json`. Fewer clean passes than the baseline with at least one scored failure (`fail`, `timeout` or `pass-workaround`) is **triage** (exit 1) and comments on, or opens, the one open `weekly-trial` issue, also when the runs are incomparable with the baseline; a shortfall without any scored failure (invalid runs, missing repetitions, missing identity fields) is **environment** (exit 2), never a product regression. A median `toolCalls` or `totalInputTokens` more than 30% above the baseline, on comparable pass-clean runs only, is a **warning**. Three runs are a canary, not a statistic. `last-run.json` drives the **overdue** notice (more than 8 days). The baseline changes only through `-PromoteBaseline <folder>`, which accepts an all-`pass-clean` comparable run and keeps the previous one. `-DryRun` runs nothing, `-Analyze <folder>` scores an existing output, `-NoIssue` skips GitHub; `-SelfTest` is offline and listed in `scripts/test-scripts.ps1`.

### Release qualification and versioning

**Release qualification.** Every merge to master cuts a release, so qualify risky changes before merging and watch the channels after. Before merging a PR, run `pwsh scripts/release-impact.ps1`; it prints `desktop-qualification: required` when the diff touches the shipping projects, `packaging/**`, `cd.yml`, project files, or central build configuration. When required, run `pwsh scripts/check-released-desktop.ps1 -BuildCandidate` on the interactive desktop: it builds both packages as version `0.0.0-candidate` (ffmpeg from `$env:FFMPEG_PATH` or `PATH`), hashes them, and runs the same desktop steps as a release check, labelled `candidate` in `result.json`. `-CandidateDirectory <dir>` tests packages you already have, and `-PackageOnly` stops after the packages are built or located and hashed, without touching the desktop. After each release, run `pwsh scripts/check-release-channels.ps1 -Version <x> -Watch` under a watchdog. It reports one state per channel (the GitHub release, each winget package, the MCP Registry, the plugin pin) and exits 1 on any failed channel, so report a failed channel at once: a failed Winget Release run otherwise goes unnoticed.

**Versioning.**

- `version.json` holds `major.minor`. Nerdbank.GitVersioning adds the patch from commit height, so a full clone (`fetch-depth: 0`) is required.
- `publicReleaseRefSpec` marks `master` and `v*` tags as public; other branches get a pre-release suffix.
- Bump `version.json` to start a new minor; never hand-edit a patch.
- `dotnet-tools.json` pins `nbgv` and `dotnet-ef`; run `dotnet tool restore` after cloning.

### Installer and packaging

**Installer and packaging.**

- `installer/Pointframe.iss` is the Inno Setup script; `installer/build-installer.ps1` and `installer/test-installer.ps1` build and check it locally. Its ARP `AppPublisher` is the source of truth that the winget manifests must mirror.
- `winget/` holds the first manifest of each winget package (`DimitarRadenkov.Pointframe`, `DimitarRadenkov.Pointframe.Cli`). The MCP server is listed in the official MCP Registry, published by CD; see [Packaging and install](features/cli-mcp.md#packaging-and-install).
- CD publishes both immutable versioned CLI/MCP assets and stable aliases (`Pointframe.Cli-win-x64.zip`, `Pointframe.Mcp-win-x64.mcpb`, and matching `.sha256` files). Use the aliases for `releases/latest/download` links and Shields.io badges; they prevent release-version changes from breaking those links.
- Renaming anything in the delivery path (exe name, installer name, package id) touches the workflows, the installer, the winget manifests, and the updater's asset-name expectation together.
- Lesson: A floating action tag moved upstream and broke every release
